閲覧の判定は前のセッションで固めてあった。 残っていたのは、それを使う側である。 作る、名前を変える、公開設定を切り替える、畳む、消す、非公開の顔ぶれを決める。 誰がどれを行えるのかを決めるのが、この回のほとんどだった。

誰が何を変えられるか

役割は三つある。組織管理者、プロジェクト管理者、ただのメンバー。

一度、線を引き間違えた

最初はメンバーの出し入れだけをプロジェクト管理者に残し、 設定の四つを組織管理者に寄せていた。 理由は「閲覧の範囲を決める人が二段になると、誰がこの線を引いたのかを追えなくなる」である。

この理由は、公開設定にしか掛かっていなかった。 名前と説明文は見た目の話で、アーカイブは戻せる。 プロジェクトを回している人が、終わったものを自分で畳めず、 名前の誤りも直せない。 それでは、この役を置いた意味がない。

公開設定についても、理由のほうが弱い。 プロジェクト管理者はすでに非公開の顔ぶれを決められる。 組織のメンバーを一人ずつ足していけば、公開に切り替えたのとほぼ同じ状態になる。 そこを任せておいて切り替えだけを止めても、守りにはならない。 手間が増えるだけである。

組織管理者がその人をプロジェクト管理者にした時点で、この判断はもう委ねられている。

削除だけを残した理由

論理削除は、どのテーブルでも組織管理者に寄せてある。 スレッドも、組織そのものも同じである。 プロジェクトだけを例外にする理由が無い。

設定の画面はプロジェクト管理者にも開くが、削除の一枚だけは押しボタンを出さない。 出さないだけでは守りにならないので、判定は SQL の中にもある。

最後のプロジェクト管理者は、守らなくてよい

組織管理者のほうには下限がある。 全員降ろせてしまうと、その組織は中の誰にも触れなくなるからで、 行を掴んでから数える仕掛けを前のセッションで入れた。

プロジェクトには同じ仕掛けを置いていない。 組織管理者が行を持たなくても管理者として扱われるので、 行が一本も無くなっても、外側に受け皿がある。 同じ形の問題に見えて、成り立ちが違う。

フォームから届く id を信じない

プロジェクトを操作する画面は、どれも組織の slug とプロジェクトキーだけを送る。 プロジェクトの id はサーバ側で引き直す。

引き直しは、閲覧できるプロジェクトを絞る副問い合わせを通る。 つまり見えないプロジェクトは、id を知っていても掴めない。 フォームに id を置いて受け取ると、この一段が丸ごと抜ける。

スコープに書いてある役割は、やはり信用しない

isOrgAdmin は画面の出し分けにしか使わない。 書き込みの可否は、すべて SQL の側で確かめている。

偽のスコープ（権限のない人の id に isOrgAdmin: true を付けたもの）を 作成、名前の変更、公開設定、アーカイブ、削除、メンバーの追加と削除の すべてに渡すテストを置いた。どれも通らない。

テストが素通りした穴

権限の断片をひとつ増やした。 組織管理者か、あるいはそのプロジェクトの管理者か、を確かめるものである。

export function projectAdminExists(projectParam, orgParam, userParam) {
  return `(${orgMemberExists(orgParam, userParam)}
       AND (${orgAdminExists(orgParam, userParam)}
            OR EXISTS (
                 SELECT 1 FROM project_members pm
                  WHERE pm.project_id = ${projectParam}
                    AND pm.user_id = ${userParam}
                    AND pm.is_admin
                    AND pm.deleted_at IS NULL)))

いちばん外の orgMemberExists は、 組織から外れた人の project_members が残っているだけで 管理者に戻ってしまうのを防いでいる。 前のセッションで開いた穴と同じ形である。

書いたあと、この行を (true) に置き換えてテストを流した。 47件すべてが通った。

「組織から外れたら管理できない」という筋のテストは、書いてあった。 ただしそれはプロジェクトを引く経路を通っていて、 そこでは閲覧の判定が先に効く。 外れた人にはプロジェクト自体が見えないので、 その先の権限の判定まで到達していなかった。

足りなかったのは、メンバーを足す経路と外す経路である。 こちらはプロジェクトの行を直接引くので、閲覧の判定を通らない。 組織から外し、project_members の行はわざと残したうえで、 もう誰も足せず外せないことを固定した。 置き換えると、今度は落ちる。

通ることと、届いていることは違う

意図した条件を、テストが本当に踏んでいるかどうかは、 通過した件数からは読めない。 条件を壊して落ちることを確かめるまで、分からない。

作った画面

URL誰が開けるか中身
/o/{slug}組織のメンバー閲覧できるプロジェクトの一覧。作成の入口は組織管理者にだけ出す
/o/{slug}/p/{key}閲覧できる人プロジェクトの中身。スレッド一覧はこれから
…/p/{key}/members組織管理者、プロジェクト管理者非公開の顔ぶれ
…/p/{key}/settings組織管理者、プロジェクト管理者名前、公開設定、アーカイブ。削除は組織管理者にだけ出す

左帯には、閲覧できるプロジェクトが並ぶようになった。 畳んだものは出さない。左帯は行き先を選ぶ場所で、 終わったものが常に並んでいると、動いているものが埋もれる。

一覧のほうには畳んだものも既定で出す。 スレッド一覧との違いは、桁である。 数万件に混ぜると読めなくなるが、数個なら並んでいたほうが早い。

公開プロジェクトのメンバー一覧

公開プロジェクトでも、メンバーの一覧は開けるようにした。 公開のあいだ、そこに誰を入れても閲覧の範囲は変わらない。

閉じておくほうが筋は通る。効かない設定を触れるのは紛らわしい。 ただ、そうすると非公開に切り替えてから人を入れる順にしかならず、 誰も入っていない非公開プロジェクトができる時間が生まれる。

先に揃えられるようにして、公開のあいだは効いていないことを画面の上で断った。

型が通らなかったこと

Next.js の typedRoutes は、URL を文字列のまま検査してくれる。 ところが /o/{slug}/p/{key} のように動的な区間が二つ並ぶと、 推論が通らず Link に渡せない。

型を当て直すしかないが、当て直した箇所では綴りの誤りも検査されなくなる。 そこで組み立てを一枚のファイルに閉じ込め、画面の側では URL の文字列を書かない形にした。 当て直しは三箇所に収まっている。

次にやること

スレッドである。 /o/{slug}/p/{key} はいま空の枠を出しているだけで、そこに一覧が並ぶ。 課題と議論と質問、親子関係、進捗率、担当者、絞り込み。 この機能でいちばん量があるところになる。
