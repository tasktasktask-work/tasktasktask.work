添付ファイルを上げ下げできるようにした

done

設計だけが先に済んでいた機能である。 形式を検査しない理由も、配信の四つのヘッダも、 attachments の列も、置き場のマウントも用意してあった。 src/features/attachment/ にあったのは README 一枚だけだった。

読む側も書く側も無かった

タグのときとは形が違った。あちらは読み取りだけが先にできていた。 こちらは両方とも無い。あるのは決定と、その決定を書き留めた文書である。

だから今回の作業の大半は、決めてあったことを裏切らずに書くことだった。 一つだけ、書いてみて初めて食い違いが見つかった箇所がある。

ブラウザ側の圧縮が、決定と噛み合っていなかった

機能ページには「アップロード前に browser-image-compression で圧縮する方針は残す」とあった。 一方でこのセッションでは、サーバー側で長辺を縮めないと決めた。 貼られる画像の大半は画面の写しで、要件は文字が読めることだからである。

ライブラリの主な効き目は長辺の縮小である。 ブラウザ側で縮めて送れば、サーバーが受け取る時点で既に原寸ではない。 「サーバーは縮めない」と決めても、原寸は守られない。

触るのを品質だけに限り、PNG には手を付けないことにした。 そのうえで、常に圧縮するのではなく 10MB を超えたものだけを縮める。 常に縮めると 1MB の写真も劣化する。得るのは上りの数百ミリ秒である。

同じファイルが、ブラウザによって別の扱いになった

この決定には副産物がある。iPhone の HEIC はサーバー側のデコーダが読めない。 ところが Safari の canvas は読める。

圧縮が働く大きさなら、Safari から貼った写真は JPEG になって届き、画像として扱われる。 Chrome から同じ写真を貼ると、ダウンロードできるだけの添付になる。 受け入れた差である。揃えるには形式ごとの経路を増やすことになる。

取り消せない操作が二つ増えた

添付を消すと、行だけでなくファイルの実体も消える。 消す動機の大半は「見えてはいけないものが置いてある」で、 行だけ落として実体を残すと目的を果たさない。

もう一つは再エンコードである。 保存するのは作り直した出力だけで、原本は残さない。 機能ページが「Exif の位置情報も構造的に消える」と書いている以上、 原本を並べて残せばその文が嘘になる。

どちらも取り消せない。だから消す押しボタンは二度押しにした。 タグを消すときと同じ形である。取り消せない操作の見せ方を、機能ごとに変える理由がない。

畳んだ後は、貼った本人には消せない

ここは一貫性を取って、使い勝手を落とした。

アーカイブ済みのスレッドでは添付を消せない。 畳んだものへの書き込みを一律で止める線に揃えてある。 畳みを解けるのは管理者だけなので、貼った本人には手が無い場面が出る。

逆の選択もありえた。「アーカイブは書き足せないことであって、消せないことではない」 という理屈は立つ。流出しているファイルを残す理由にはならない、とも言える。 それでも揃えたのは、例外を一つ開けると、 次に「これも例外でいいのでは」と問われたときに引く線が無くなるからである。

模組が互いを呼びそうになった。前と同じ形で

コメントを投稿するとき、添付は同じ取引で入る。 つまり #features/comment/queries.ts が添付側を呼ぶ。 一方で添付側は、書き込みの可否を判定するために THREAD_WRITABLE を読む。

タグのときに決めた形をそのまま当てた。 行を入れて実体を書くだけの部分を store.ts へ分け、そこには判定を置かない。 寸法の定数も limits.ts へ分けた。 画面の側でも上限の数字が要るので、queries.ts を読ませると pg がブラウザ向けの束に入る。

もう一段の分割が要ることは、書いてから分かった。 再エンコードを取引の中でやると、10MB の画像を読み直すあいだ行を押さえたままになる。 作り直しを prepareAttachments として取引の外へ出し、 取引の中では作り終えた中身を入れるだけにした。

この分割には別の効き目もあった。 透明を持つ画像を PNG で書き出すと、元より大きくなることがある。 これを取引の中で見つけると、上限の制約に当たってコメントごと巻き戻る。 外に出したので、断る文面を返すだけで済む。

並び順が、偶然に頼っていた

テストが一度だけ落ちた。二つ付けた添付の並びが入れ替わっていた。

原因は created_at の既定値である。 now() は取引の開始時刻を返すので、一度の送信で入れた行は全部同じ時刻になる。 そうなると並びは第二の鍵であるランダムな id で決まり、選んだ順とは無関係になる。

挿入時に clock_timestamp() を明示して入れることにした。 こちらは呼ばれた瞬間の時刻を返すので、同じ取引の中でも行ごとに違う。

テストのほうも直した。並びを見るだけでは、 ランダムな id がたまたま揃っただけの回に通ってしまう。 四行の created_at が全部違うことを、別に確かめている。

自動では確かめていないところ

nosniff の一行を消しても、何も落ちない。 next.config.ts が全経路に同じヘッダを付けているためである。 実際に外して当ててみたが素通りした。 片方を消しても壊れないので、この欠落だけは捕まえられない。 配信の経路にも書いてあるのは、守っているものを一枚の中で読み切れるようにするためである。

ブラウザ側の圧縮も、自動では確かめていない。 DataTransfer で欄の中身を差し替える処理は、実物のブラウザでしか動かない。 サーバー側は「原本がそのまま届いた」場合を前提に書いてあり、そちらは確かめてある。

二度押しの分岐も、タグのときと同じ理由で確かめていない。 サーバーアクションは cookies() を読むので、テストから呼べない。

直したもの

  • 機能ページの「ブラウザ側で圧縮してから送る」を、上限を超えたときだけに書き換えた
  • スレッド詳細の見本から「添付の欄は出ない」という断りを消した
  • deploy/compose.yaml の CLIENT_MAX_BODY_SIZE を 12m から 34m へ上げた

次にやること

本番への反映が溜まっている。 20260907135543 以降の四つの移行がまだ当たっていない。 そのうちの一つに CREATE INDEX CONCURRENTLY が入るので、 docker compose run --rm migrate がトランザクションを張らないことを、 本物のデータベースで初めて確かめることになる。

あわせて deploy/ の二つのファイルを VPS へ写す必要がある。 CLIENT_MAX_BODY_SIZE を上げないと、大きい添付だけが本番で 413 になる。

機能としてはガントが残っている。 見本はあるが、札は外したままである。
