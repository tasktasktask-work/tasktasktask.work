通知をメールで送るようにした

done

SmtpMailSender.send は呼ぶと例外を投げていた。 止まっていたのは通知だけではない。本番ではマジックリンクも招待も届かない状態だった。

認証の入り口が塞がっていた

前回までに三つのきっかけはどれも行を積むようになっていた。 無いのは送る仕掛けだけ、という認識で始めた。

手元を見ると、そうではなかった。 MAIL_TRANSPORT=console の開発環境では標準出力に書かれるので気づかない。 本番の smtp では、マジックリンクを送ろうとした時点で例外が飛ぶ。 ログインそのものができない。

SMTP を実装した時点で、通知より先にそちらが直った。

置き場が無い、という壁

行を作ってから送るまでのあいだに、誰かがその行を拾わなければならない。 デプロイ構成に常駐プロセスも定期実行も無い。 期限が近い課題の通知を先送りにしたときと同じ壁である。

四つ並べて、二つ目を選んだ。

案採らなかった理由
リクエストの後で送る失敗したときに拾い直す人がいない。永久に未送信の行が残る
同じプロセスで巡回する採用。置き場が増えない
送信専用のサービスを足すデプロイ構成に要素が増える
外から定期的に叩く同上。加えて叩く口を外へ開けることになる

間隔は60秒である。これはまとめる幅でもある。 会議がひとつ荒れると一人に十数通が数分で届くので、宛先ごとに一通へ束ねる。 無料枠は月3,000通しかない。

コンテナが一つであることに寄りかかっている

掴むところでは FOR UPDATE SKIP LOCKED を使うが、 ロックは掴む取引の終わりで放される。送るのはそのあとである。 取引を開けたまま SMTP の応答を待つわけにいかないためだ。

したがって app を二つに増やすと、同じ束が二通届きうる。 いま動くのは一つだけなので通しているが、増やすときは掴んだ印を行に持たせるところから直す。 デプロイ構成にも書いた。

送らない行を、拾い続けないための列

送らないと決める場面がいくつもある。 アプリで先に読まれた、本人が通知メールを切っている、 非公開になって見えなくなった、飛ぶ先が消えた。

作りながら気づいたのは、送らないだけでは足りないということである。

拾う索引は WHERE emailed_at IS NULL の部分索引で、 拾う順は古い順である。決着を付けない行はそこに残り続ける。 残るだけなら費用の話で済むが、古い順に拾うので、 居座った行が毎回の枠を先に取る。後ろに並んだ人の通知が永久に順番待ちになる。

アプリで先に読まれる行は、通知が来てから60秒以内に画面を開いた人の数だけ生まれる。 珍しい出来事ではない。放っておけば、その分だけ索引の先頭が詰まっていく。

そこで email_gave_up_at を足し、索引の条件をそれで書いた。 「送った」と「送らないことにした」を別の列にしてある。

emailed_at を代わりに埋めなかった理由

列を一つで済ませられる。ただし送っていないものを送ったことにすると、 届かなかった件を数えられなくなる。

索引の条件に試行の回数を書く手もあったが、そちらは上限を変えるたびに移行が要る。

二つに分けた副産物として、畳んだ理由も読める。 email_attempts が 0 のまま畳まれた行は、一度も送ろうとしていない。

回数だけで諦めると、復旧のあいだの通知が消える

諦めるまでの回数を決める、という話にはもう一段ある。

60秒ごとに巡回して5回で諦めるなら、 Cloudflare 側が5分止まっただけで、その間の通知が全部捨てられる。 宛先が壊れているのと、相手が一時的に応じないのとを、回数は区別しない。

SMTP はこの二つを応答コードで分けている。 5xx なら回数を待たずその場で諦め、4xx と接続の失敗は数える。 上限は60回、つまり一時間ぶんに取った。 一時間で復旧しない SMTP は、諦めたことより先に気づくべき事態である。

接続の失敗を一時側に入れたのは、 相手が居ないのか経路が切れているだけなのかを、こちらから区別できないためである。

回数は、掴むときに増やす

送ってから増やす形も取れる。そちらだと、送信の途中でプロセスが落ちる束は 回数が永久に 0 のまま、起動のたびに同じ場所で落ち続ける。

先に増やしておけば、そういう束もいずれ上限に達して外れる。 送れた行には emailed_at が入るので、増えた回数は「何回目で届いたか」として残る。

切るスイッチを、同じ回で入れた

値は前から users.email_notifications_enabled にあった。切り替える画面が無かった。 アカウントの設定として先送りにしてあったものである。

ただし機能ドキュメントは、このスイッチを迷惑メール報告への保険と位置づけていた。 止められないまま送り始めると、報告が積み重なって送信ドメインの評価が下がり、 最後にはマジックリンクが届かなくなる。 送るのと同じ回に入れないと、順番が逆になる。

置いたのは /me である。組織の下ではない。

URL は、その設定がどこまで効くかを語る

この値は所属しているすべての組織に効く。 /o/{slug}/... の下に置くと、その組織だけの設定に見える。

三つの組織に居る人が三箇所を止めて回り、一つ見落として届き続ける、という形を作らない。

止め方はメールの末尾にも書いた。 煩わしいと感じた人はメールを開いたその場で判断するので、 そこに切り方が無ければ、迷惑メールの押しボタンのほうが近い。 List-Unsubscribe ヘッダは付けていない。 あれは押した瞬間に止まる約束で、認証を通さずに止める口を開けることになる。

マジックリンクだけは、その場で送る

通知と同じ列に積む手もあった。採らなかった。

ログイン用リンクが最大一分遅れて届く。 ログインは待っている人の目の前で起きるので、その遅れは直接見える。 失敗したときに「送りました」と嘘をつかないためでもある。

Atlas の指示が、黙って無視された

CREATE INDEX CONCURRENTLY はトランザクションの中で実行できない。 規約どおり別のファイルへ分け、先頭に -- atlas:txmode none を置いた。 それでも cannot run inside a transaction block で落ちた。

指示の直後にコメント行を続けていたのが原因である。 一行目に置き、次を空行にすると通った。 スキーマ移行に書き足した。

テストの並行実行と、絞れない巡回

巡回は組織を絞らない。仕組みとして絞れない。宛先は組織をまたぐからである。

テストは複数のファイルが並行して走るので、 一巡の上限を確かめるテストが、他のファイルの積んだ行と枠を取り合って落ちた。

数え方を変えた。自分の作った宛先が何人届いたかではなく、 一巡で送られた通の総数を見る。 こちらは他のファイルの行が混ざっても、上限を超えないことに変わりはない。
