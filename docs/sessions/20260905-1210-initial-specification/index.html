構造を決めた三つの判断

基本単位をスレッドにした

課題として書けるほど固まっていない相談を、どこに置くか。 これがこの製品の出発点になった。

多くのツールは「課題」を基本単位に置き、議論をその付属物として扱う。 ここでは順序を逆にし、スレッドを基本単位として、 課題をその種別のひとつにした。

この決定から、threads テーブルに 制約が集中する構造が導かれた。 種別によって使える列が変わるため、CHECK 制約でそれを表現している。

状態を進捗率ひとつにした

ステータスの一覧を持たず、0から100の数値だけで表す。 ガントのバーの塗り分けと直結する筋のよさがある一方、 「やらないと決めた」と「まだ手をつけていない」を区別できない。

終了理由の軸を別に持つ案を検討したが、採らなかった。 却下の表現に経緯を残した。

添付ファイルの検査をやめた

途中まで、マジックバイトによるホワイトリストを置く方針だった。 検討の結果、次の四つが同時に成り立つとわかった。

  • Office 文書は zip と区別できず、テキスト系は判定そのものができない
  • 判定できる形式も、ポリグロットで素通りする
  • zip を許す限り、実行ファイル対策として成立しない
  • Node.js はそもそも置かれたファイルを実行しない

拡張子のホワイトリストも同時に外した。 .log や .patch のような正当な業務ファイルを弾き、 利用者は拡張子を変えるか zip に入れて迂回する。 防御は機能せず、データの質だけが下がる。

代わりに配信の仕方で守る方針に切り替えた。 常にダウンロードとして返すこと、種別を推測させないこと、 そして画面に出す画像はサーバー側で読み直して書き出し直すこと。 維持すべきリストがどこにも存在しない形になった。

その後の変更

このとき、あわせて「本体とは別のドメインから配信する」と決めていた。 次のセッションで同一オリジンに変更している。 実際に守っているのはヘッダであり、分離が足すのは保険だけである一方、 別オリジンには認可の仕組みを別に作る費用がかかるためである。

途中で見つけて直したこと

見つけたことどうしたか
通知チャネルを「メールのみ」としながら既読管理を持つ、という矛盾 アプリ内通知も作ることにした。既読の置き場所ができた
10回失敗で永続ロックだと、第三者が任意のユーザーを締め出せる マジックリンクでのログイン成功で自動解除する。ロック時に本人へメールも送る
Cloudflare のメール送信が、以前は検証済み宛先にしか送れなかった 現在は送信ドメインをオンボードすれば任意の宛先へ送れる。SMTP も使える
プロジェクトを廃した設計だと、ガントの単位が失われる ルート課題で代用する案を出したが、プロジェクトを復活させる判断になった
pg の既定の型変換が、期間を date にした判断を無効にする。 date がローカルの午前0時の Date になり、日付が1日ずれうる 型パーサの差し替えをコーディング規約に明記した

レビューで確定したこと

ドキュメントを書き上げた時点で、判断を仰ぎたい点が4つ残っていた。すべて決着している。

確定した4点
  1. プロダクト名は TASK3、ドメインは tasktasktask.work。 仮称で書いていた全ページを差し替えた。 名前の 3 を三つの種別と読み合わせ、ロゴの意匠に使っている
  2. thread_tags と watches の物理削除を、例外として認める。 「すべてのレコードは論理削除」という方針は、この2つの中間テーブルには適用しない。 付け外しが日常的に起きるためで、記録が必要になれば監査ログで扱う
  3. docs/theme.css の追加を認める。 ドキュメント構成の指定にはないが、共通スタイルの複製を避けるために置く
  4. 一覧は平ら、ガントは階層のままとする。 同じデータを二つの画面で違う形に見せるが、探すための画面と計画を読むための画面という目的の違いによる

これらに加えて、日付と時刻の扱いを規約に追加した。 pg の既定の型変換が、期間を date にした判断を無効にしうるためである。

決定の記録
