TypeScript を 7 に上げ、検査の CI を用意し、イメージの作り方を直した。 途中で、開発機でだけ通っていた依存が二つ見つかった。 どちらも「手元にあるものが、たまたま足りていた」という形をしていた。

TypeScript 7 と Next.js 16

「ESLint を使っていないなら TypeScript 7 に上げられないか」という問いから始まった。 typescript-eslint は TypeScript の API に依存するので、 そこが外れているのは条件のひとつではある。

ただし十分ではなかった。実際の足枷は Next.js だった。

TypeScript 7.0.2 is not supported by this version of Next.js.
The TypeScript 7 native compiler does not provide the JavaScript compiler API
that Next.js requires. Install TypeScript 6 ... or upgrade to a Next.js
v16.2.11 or later to get support for TypeScript 7.

TypeScript 7 は Go で書き直された実装で、従来の JS コンパイラ API を持たない。 Next はその API を設定の読み込みとビルド時の型検査で使っていた。 この二つは片方だけ上げられない。

測ったもの5.9.37.0.2
tsc --noEmit（3回平均）1020 ms335 ms
next build の型検査—181 ms

速いだけで検出しないのでは意味がないので、わざと型を壊して確かめた。 TS2322 が出ることを見てから採用している。

調整は二つ。CSS の副作用 import に型宣言が要ること （types/assets.d.ts）と、 typescript.tsdk を指定しないこと （TypeScript 7 は lib/tsserver.js を持たない）。

検査の CI

Deploy とは別のワークフローにした。 片方の失敗が、もう片方の判断を邪魔しないためである。

テストは実データベースに対して行うので、postgres:18 を立てる。 作業用データベースは要らない。 scripts/atlas.mjs を直し、diff のときだけ ATLAS_DEV_URL を要求するようにした。

Atlas の版を固定した

キャッシュの鍵を作るには版が決まっている必要がある。 そこで -latest をやめようとして、別の理由に気づいた。

$ atlas version
atlas version v1.3.4-cdeb6c3-canary    ← -latest で入るもの
                                          安定版は v1.3.0

スキーマを移す道具が、日によって別のものになっていた。 .atlas-version に版をまとめ、 手元の手順と CI と Dockerfile が同じファイルを読むようにした。

開発機でだけ通っていたもの

ここからが、このセッションで拾えた本題である。

ホストの node_modules がイメージに入っていた

.dockerignore が無かった。 Dockerfile の build 段は、deps 段から node_modules を写したあとに COPY . . を行う。 文脈にホストの node_modules が入っていると、そこで上書きされる。

この開発環境は aarch64 である。 @node-rs/argon2 のような各アーキテクチャ向けのバイナリが、 作った機械のものに置き換わっていた。 CI は fresh clone なので偶然無事だったが、手元のビルドは壊れた組み合わせだった。

前後
ビルド文脈1.2 GB188 KB（55ファイル）
node_modules の上書き起きる起きない
.env文脈に入る入らない

イメージを作るのに本番の接続先が要った

.env を文脈から外した途端、ビルドが落ちた。

Error: 環境変数が正しくありません:
  ✖ Invalid input: expected string, received undefined → at APP_ORIGIN
  ✖ Invalid input: expected string, received undefined → at DATABASE_URL
    at module evaluation (src/lib/env.ts:18:9)

env.ts と db.ts と mail.ts が、 モジュールを読み込んだ時点で実行時の設定を要求していた。 next build はページの情報を集めるためにモジュールを読み込むので、 そこで落ちる。

なぜ長く気づけなかったか

開発機には .env がある。 それがビルド文脈へ写り込んでいるあいだは、ビルドが通ってしまう。 手元では成功し、CI では失敗するという形をしていた。

Deploy ワークフローは fresh clone で動くので、 走らせていれば同じところで止まっていたはずである。 .dockerignore を入れたことで、先に表へ出た。

#lib/lazy.ts を足し、最初に触られたときに作る形にした。 呼ぶ側の書き方は変わらない。

対象読み込み時最初に触ったとき
env何もしない環境変数を検証する
pool何もしない接続プールを作る
mailSender何もしない送信の実装を選ぶ

検証を捨てたわけではない。足りなければ触った時点で落ちる。 タイミングが仕様なので tests/lazy.test.ts で固定した。 規約にも書いた。

共通していたこと

二つとも、開発機にあるものが、たまたま足りていたという形をしていた。 ホストの node_modules と、手元の .env である。 どちらも本来そこに無いものが、あることを前提に動いていた。

見つけたきっかけは、ビルド文脈を絞ったことだった。 渡すものを減らすと、渡していたつもりのないものが見える。
