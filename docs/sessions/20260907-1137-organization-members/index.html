組織とメンバーを実装した

done

認証は済んでいるので、ログインはできる。 ところが入った先には何もない。 組織がなければプロジェクトも置けないので、次はここになる。

最初のひとりは、どこから来るのか

組織に人が増える経路は招待だけだと決めてある。 招待を送れるのは組織管理者だけである。 すると、最初の組織管理者を作る手段が画面のどこにもない。

自分で組織を作れる入口を付ける手はある。 ただし誰でも作れる状態は、料金の話が決まっていない今は早い。 課金とプランを決めてから作る入口にしたい。

そこで、最初のひとりだけは手元の実行で作る。

pnpm org:create --name "株式会社アクメ" --slug acme \
                --admin someone@example.com --admin-name "佐藤 明日香"

組織と、組織管理者としての所属と、ログイン用リンクを作って出力する。 パスワードはこの経路では設定しない。 受け取った人がリンクで入り、あとから決める。

パスワードを設定する画面がまだない

この経路で作られたアカウントは、当面マジックリンクでしか入れない。 表示名も変えられない。 アカウントの設定として先送りにした。

スコープが無ければ、何も引けない

組織はデータの境界である。 条件から organization_id が落ちれば、他社のデータが混ざる。

「書き忘れないようにする」では守れないので、書かなければ何も引けない形にした。 /o/{slug}/... のページは、まず URL の slug から 組織のスコープを組み立てる。

const found = await currentScope(slug);
if (!found.ok) {
  return found.anonymous ? <LoginScreen /> : notFound();
}

スコープが取れなければ、その先のクエリに渡す第一引数が無い。 データにさわる関数はすべて OrgScope を第一引数に取るので、 型の側から通れない。

存在しない slug と、所属していない組織を区別しない

どちらも 404 を返す。 「その組織はあるが、あなたは所属していない」と答えると、 slug を総当たりして他社の存在と名前を確かめられる。

未ログインのときは、そのURLのままログイン画面を出す。 /login へは送らない。 /o/acme/members を開いた人は、そのURLでログインしてそのまま着地する。

スコープに書いてある役割を、信用しない

OrgScope には isOrgAdmin が入っている。 非公開プロジェクトの閲覧判定に使うためである。

この値は所属から組み立てたものなので、正しい。 ただし正しさは、組み立てた経路を通ったときだけ保証される。 呼ぶ側は好きな値のスコープを作れる。

画面に出さないことは、防御ではない

役割を変える、メンバーを外す、招待を送る、組織名を変える。 どれも SQL の中で組織管理者かどうかを確かめる。 scope.isOrgAdmin は画面の出し分けにしか使わない。

メンバー一覧のメールアドレスも同じで、 CASE WHEN EXISTS (...組織管理者...) で出し分けている。 呼ぶ側が絞る形にすると、その一箇所を忘れたときに漏れる。

この「信用しない」を、偽ったスコープを渡すテストで固定した。 isOrgAdmin: true と書いたスコープをメンバーの id で渡しても、 役割は変わらず、メールアドレスも返らない。

判定の条件そのものは 前のセッションで一箇所にまとめたものを、 orgMemberExists() と orgAdminExists() という断片に切り出して使い回している。 同じ条件を書き写す場所を、これ以上増やさないためである。

最後の組織管理者を、降ろせなくする

組織管理者が一人もいなくなると、その組織は設定もメンバーも触れなくなる。 中の誰にも戻す手段がない。

行数の下限は CHECK で書けないので、アプリケーション側で守る。 素朴に数えて判定すると、二人の管理者が同時に互いを降ろしたときに抜ける。 どちらも「自分のほかにもう一人いる」と読むためである。

SELECT user_id
  FROM organization_members
 WHERE organization_id = $1 AND role = 'admin' AND deleted_at IS NULL
 ORDER BY user_id
   FOR UPDATE

先に管理者の行を掴んでから数える。 二つめの要求は、一つめが終わるまで待つ。 管理者が増える側は待たせない。 増えるぶんには下限を割らないためである。

掴んだ行の中に自分がいるかどうかで、操作の可否も同時に決まる。 役割の確認と、数の確認と、順番待ちが、この一本にまとまっている。

招待を受けるとき

招待リンクは、招待されたメールボックスにしか届かない。 開けたこと自体が、そのアドレスの持ち主である証拠になる。 マジックリンクと同じ性質なので、有効期間も48時間で揃えてある。

状況することと、しないこと
アカウントが無い表示名とパスワードを訊いて作る
アカウントがあるパスワードも表示名も訊かない。所属を足すだけ
ロックされているロックを解く。マジックリンクと同じ扱いにする
一度外れた人畳んだ行は起こさず、新しい行を足す

二行目が大事なところである。 すでにアカウントがある人にパスワードを訊いて上書きできると、 招待リンクを踏ませるだけで他人のパスワードを書き換えられる。 訊かない形にしてある。

四行目は、入って抜けてを繰り返した人のためである。 畳んである行をまとめて起こすと、生きた行が二本になって部分一意索引に当たる。 過去の所属は記録として残し、新しい所属は新しい行にする。

受諾の画面は、開いただけでは何も変えない。 リンクを先読みするメールソフトに、勝手に受諾させないためである。

あわせて直したこと

画面で使っていた .app-frame と .app-empty が、どこにも定義されていなかった。 ログイン画面の知らせに使っていた .note は docs/theme.css にしかなく、製品側では効いていない。

共有ブロックへ .app-note として入れ直し、 メンバー一覧のための .app-people と、小さなフォームのための .app-form を足した。 意匠の正本は docs/theme.css なので、そちらに書いて pnpm styles:sync で写している。

次にやること

プロジェクトである。 /o/{slug} はいま空の枠を出しているだけで、そこに一覧が並ぶ。 作成、公開と非公開の切り替え、非公開のメンバー管理、アーカイブ。 閲覧の判定はもう固めてあるので、それを使う側を作ることになる。
