初回デプロイで VPS の CPU が張り付いた

done

VPS へ最初に置いた直後、CPU が通常の20倍あたりまで上がって戻らなくなった。 他のサービスも同居しているので、影響はこのアプリだけに留まらない。 原因の見当は二度外し、三度目で形が見えた。

症状

通常 200 msec ほどで推移していた CPU が、4700 msec まで上がってそのまま高止まりした。 「動いていない」のではなく「何かが全力で回っている」形である。

実行した手順は次のとおりだった。

docker compose up -d
docker compose run --rm app migrate

順序が記録した手順と逆になっているが、 これは今回の原因ではない。 アプリは起動時にデータベースへ触らない作りなので、 テーブルが無くても立ち上がる。

外した見当

イメージのアーキテクチャ

最初に疑ったのはこれだった。 x86_64 の VPS に arm64 のイメージを置くと、binfmt があれば QEMU がエミュレーションで動かす。 Node のようなプロセスでは CPU を数倍から十数倍消費するので、 張り付き方の形とは合っていた。

確認したところ linux/amd64 だった。外れである。

container_name の衝突

app には container_name を指定してある。 run が同じ名前を取ろうとして衝突したのではないか、と考えた。

調べたところ、docker compose run は container_name を無視して 自前の名前を作る。これも外れである。

有力な説明

app には restart: unless-stopped が付いている。 落ちても起き上がってほしいからである。

この方針は終了コードに関わらず起動し直す。 成功して終わっても、また立ち上がる。

一時的な処理に、常駐向けの方針が引き継がれた

docker compose run --rm app migrate は app の設定から一時コンテナを作る。 そこに unless-stopped が付いていれば、 移行が終わるたびに走り直す。

migrate は Atlas（120MB の Go バイナリ）と Node を 毎回立ち上げてデータベースを叩く。 これが延々と回れば、CPU は張り付く。

確証は取れていない。 --rm を付けていたためコンテナが残っておらず、後から確かめようがない。 ただし機構としては筋が通り、症状とも合う。

直した形

どの説が正しいかに関わらず起こらない形にした。 migrate を別のサービスとして定義する。

  migrate:
    image: ${APP_IMAGE:?APP_IMAGE を .env に設定してください}
    profiles: ["tools"]
    restart: "no"
    command: migrate
    env_file: .env
    networks:
      - postgres-network
指定意図
restart: "no"終わったら終わる。常駐向けの方針を引き継がない
profiles: ["tools"]up -d では起動しない
networks を絞るデータベースに届けばよい。nginx-proxy も添付の置き場も要らない

docker exec で済ませない理由

今回は docker exec で流して完了させた。 それで動くが、手順として残すのは避けた。

exec はアプリが動いていることが前提である。 つまり up -d を先に済ませることになり、 新しいコードが古いスキーマの上で動く時間ができる。

段階的な変更の手順は 「先にスキーマ、あとからコード」で成り立っている。 初回は差がないが、列を消す段になると効いてくる。

あわせて直したこと

Dockerfile に ENV HOSTNAME=0.0.0.0 を明示した。

const hostname = process.env.HOSTNAME || '0.0.0.0'

一見 0.0.0.0 に落ちるように見えるが、 Docker はコンテナに HOSTNAME を必ず設定する。 右側には落ちず、そのホスト名に bind する。 今回の CPU とは別件だが、nginx-proxy から届かない構成になりうる。

残しておきたいこと

設定を使い回すと、意図の違うものまで一緒に付いてくる。 restart: unless-stopped は「落ちても起き上がってほしい」という意図で書いたもので、 「一度だけ流す」処理に付けるつもりはなかった。 同じ image を使うことと、同じ service を使うことは別である。

もうひとつ。見当を二度外した。 どちらも症状の形とは合っていて、確かめるまでは尤もらしかった。 アーキテクチャの確認は一行で済んだのに、 それを待たずに動いていたら、直したつもりで同じことを繰り返していた。
