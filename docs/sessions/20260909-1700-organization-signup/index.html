組織を作る入口を開ける

done

組織はデータの境界である。 その境界を作る操作だけが、これまでシステムの外にあった。 手元で pnpm org:create を叩ける人だけが、新しい会社をこのシステムに載せられた。

入口が無いのではなく、閉じてあった

組織に人が増える経路は招待だけで、招待を送れるのは 組織管理者だけである。 この二つを繋げると、最初のひとりを作る手段がどこにも無い。 そこだけを外から埋めていたのが pnpm org:create だった。

塞いだままにしていた理由は、技術ではなく料金にあった。 誰でも組織を作れる状態は、誰がその費用を持つのかという問いを連れてくる。 料金の形が決まる前に入口を開けると、作られた組織の扱いを後から決めることになる。

それを承知で開ける、というのが今回の判断である。 費用の持ち主は組織に紐づけられる形（組織単位の契約）を想定しており、 それなら入口を先に開けても、後から紐づける先が消えることはない。

認証の文書は、最初からこの形で書かれていた

認証の「アカウントの作成」には、 アカウントが生まれる経路は「新しい組織を作る」と「招待を受ける」の二つだと書いてある。 初期仕様の想定が先にあり、実装だけが片方を欠いていた。 今回の作業で、文書と実装が同じ形になる。

決めたこと

何をどう決めたかなぜ
作れる人 誰でも。ログインしていない人が自分で組織を作れる 招待を持たない人が入れる経路が、これ以外に無い
作った人の役割 その場で組織管理者になり、ログイン状態で /o/{slug} へ着く pnpm org:create と同じ結果にする。違うのは実行する人だけである
アドレスの確認 確認が先。リンクを踏んだ先で組織を作る 組織の行は確認の後にしか生まれない。「未確認の組織」という状態を持たずに済む
slug 人が決める。早い者勝ち、予約語は拒否、後から変えられない URL が組織の身元を示す。変更は既存のリンクを全部切るので、別の話として扱う
予約語の置き場所 アプリのコード。DB の CHECK 制約にはしない 語を足すたびに移行が積まれ、すでに使われている語を後から予約語にできなくなる
受け取る項目 組織名と slug だけ。言語と時間帯は既定のまま 変える手段が無い欄を入口に置かない。時間帯は設定画面と一緒に足す
入口の位置 ログイン画面すべてに「組織を新しく作る」を出す ログイン画面はどのURLにも現れる。出す場所を選ぶと、出ない画面の説明が要る
既存アカウント 表示名とパスワードを訊かない。組織名と slug だけ入れて作る 訊いて上書きできると、リンクを踏ませるだけで他人のパスワードを書き換えられる
ログイン済みの人 メールを挟まず、その場で作る そのアドレスはとうに確認済みである。もう一度踏ませる理由が無い
トークンの置き場所 新しいテーブル signup_tokens この時点では組織もアカウントも無い。既存のどのテーブルの意味も変えずに済む
連投 同じアドレスへの再送は3分に一度まで 任意のアドレスへ送らせられる初めての経路になる。受信箱を埋める道具にさせない
pnpm org:create 残す。slug の検証だけ画面と共有する 画面の経路はメールの到達に依存する。送信が止まった環境でも組織を作れる道を残す

経路は二本、作る処理は一つ

未ログイン
  /signup            メールアドレスを入れる
    │                signup_tokens に行ができ、リンクが飛ぶ
    ▼
  /signup?token=…    組織名 / slug（アカウントが無ければ表示名 / パスワードも）
    │
    ▼
  組織を作る ──→ organizations / organization_members(admin) / sessions
    │
    ▼
  /o/{slug}

ログイン済み
  /  または /signup   組織名 / slug だけ
    │
    ▼
  組織を作る ──→ organizations / organization_members(admin)
    │
    ▼
  /o/{slug}

入口は二つだが、組織を作る処理そのものは一つにまとめる。 createOrganization(userId, { name, slug }) が 組織の行と、作った人を組織管理者とする所属の行を、ひとつのトランザクションで作る。 未ログインの経路は、その手前にアカウントの用意を足しただけである。

pnpm org:create もここへ寄せる。 寄せない場合に何が起きるかははっきりしていて、slug の予約語が片方だけ増える。 そのときCLIから admin という slug が通る。

signup_tokens

CREATE TABLE signup_tokens (
  id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  email      text        NOT NULL,
  token_hash bytea       NOT NULL,
  expires_at timestamptz NOT NULL,
  used_at    timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT signup_tokens_email_lowercase
    CHECK (email = lower(email)),
  CONSTRAINT signup_tokens_email_shape
    CHECK (email ~ '^[^@[:space:]]+@[^@[:space:]]+\.[^@[:space:]]+$')
);

CREATE UNIQUE INDEX signup_tokens_hash_key ON signup_tokens (token_hash);

CREATE INDEX signup_tokens_by_email
  ON signup_tokens (email) WHERE used_at IS NULL;

invitations から organization_id と役割を落とした形である。 持てるのはメールアドレスだけで、どの組織へ入るかはこの時点では存在しない。 詳細はテーブルの文書に置いた。

データを失う変更は無い。テーブルがひとつ増えるだけで、既存の列も制約も動かさない。

連投を3分で受ける

この画面は、任意のメールアドレスへ送信させられる初めての経路になる。 招待は組織管理者しか送れず、マジックリンクは既存のアカウントにしか飛ばない。 どちらも、見ず知らずの人の受信箱を埋めるのには使えなかった。

そこで、同じアドレスへの送信は3分に一度までとする。 未使用で期限内のトークンが3分以内に作られていたら、新しくは送らない。 画面の返事は変えない。「送りました」とだけ返す。 返事を変えると、そのアドレスが登録の途中かどうかを外から測れてしまう。

新しく発行するときは、そのアドレスの未使用の行を消してから入れる。 有効なリンクを一本だけにしておくと、 「古いメールのリンクを踏んだのに使えない」という筋の問い合わせを、期限切れ以外に増やさずに済む。

今回やらないこと

やらないこと理由
ひとりが作れる組織の数の上限 運用の実感が無いまま置くと、正当な人を先に止める。作られすぎが起きてから決める
IP 単位の回数制限 保存先を決める話になる。プロセス内に持つと複数台で効かない
slug の変更 既存のリンクとブックマークを全部切る。移行の話であり、入口の話ではない
時間帯と言語の選択 変える手段（組織の設定）と一緒に足すもの。入口には混ぜない
最初のプロジェクトの自動作成 プロジェクトキーまで登録時に決めさせることになる。空の状態は一覧の文言で受ける

実装して分かったこと

予約語のうち o と me は、予約語として断られない。 3文字に満たないので、形の検査のほうが先に落とす。 一覧には記録として残し、試験は形で落ちることのほうを固定した。

失敗したときにトークンを消費しない、という決めごとは例外で実現した。 値を返してトランザクションを抜けると COMMIT される。 slug が埋まっていた場合、作りかけのアカウントがそこで残る。

二つ、規約に足した

クラスの引数でプロパティを宣言しない。 Node の型剥がしが受け付けず、pnpm test と pnpm org:create が読み込みの時点で落ちる。

新しく作る欄に settled を使わない。 種が空文字の欄では、一文字打った時点で偽になり二度と戻らない。 送信は通っているのに「送りました」が出ない状態になり、ブラウザ試験で見つかった。

既存アカウントのロックは、ここでも解ける

登録のリンクを踏めたことは、そのアドレスの持ち主である証拠になる。 招待の受諾がアカウントロックを解いているのと同じ条件がここにも揃う。 揃っているのに解かないと、ロックされた人の解除経路が経路ごとに違うことになる。 完了の処理で clearLoginFailures() を呼ぶ。
