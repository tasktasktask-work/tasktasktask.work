書く場所を、対象の隣へ

done

タイトルの誤字に気づいてから直すまでに、この画面では四つの区画を通り過ぎることになっていた。 添付、子スレッド、コメント、投稿欄。「タイトルと本文を書き換える」は、その先で畳まれている。

入口が遠いのか、対象が遠いのか

最初は畳んであることが悪いのだと考えた。 開いておけば見つかる、という理屈である。 ところが開いたままにすると、コメントの下に12行のテキストエリアが常駐することになる。 読みに来た人が毎回それを跨ぐ。

遠いのは入口ではなく、入口と対象の距離のほうだった。 タイトルは画面の上端にあり、それを直す欄は最下部にある。 途中に何を挟んでも、その二つは離れたままである。

だから欄を上へ動かすのではなく、 タイトルの位置でタイトルを直し、本文の位置で本文を直す形にした。 読みと書きが同じ場所を使い、押すと入れ替わる。

そうすると本文列に空きが出る。 そこへ子スレッドと添付の追加欄が居座っていたので、あわせて右へ移した。 今回の四点は、どれも「本文列に何を残すか」という一つの問いに繋がっていた。

決めたこと

何をどう決めたかなぜ
編集の動線 見出しの横と本文の直下に「編集」を置き、押すと読み表示が入力欄に入れ替わる 入口が対象から遠いことと、押した先がさらに遠いことの二重になっていた
フォームの分割 タイトルと本文を別々のフォームにする 入口が二箇所になるので、開く先も二つに分かれる
編集済みの印 タイトルだけの変更では押さない。表示も「本文編集済み」に変える 印は、本文を前提に書かれたコメントが宙に浮いたことを知らせるものである
子スレッド サイドへ移し、2行の簡略行にする。0件なら区画を出さない 本文列の面積を占めていた。辿る先であって、読むものではない
子を作る導線 子スレッド欄と一緒にサイドへ移す 親子を扱う場所を一箇所にまとめる
添付の追加欄 サイドへ移し、選択またはドロップだけで送信まで終える 面積のわりに、押す回数が一度多い
添付の一覧 本文列に残す 仕様書や画面の写しは本文の側の情報である。18remに畳むと中身を確かめられない
削除の欄 組織管理者かつアーカイブ済みのときだけ出す 「できない操作は消す。無効化して残さない」に戻す
サイドの幅 15rem から 18rem へ 中身が増えたぶんだけ足す。本文側の上限は今回は置かない
狭い画面 本文 → サイド → コメント の順に落とす そのまま落とすと、属性が長いコメント列の後ろへ回る

実物の見え方は修正イメージにある。 広い画面、タイトルの編集中、保存したあと、本文が空のとき、1カラムのとき、アーカイブ済みのとき。 広い画面の一枚は製品と同じ規則で描いてあるので、実際の画面と同じものが出る。

読みと書きは、同じ場所を使う

入れ替えには details をそのまま使う。 開いているあいだ読み表示を隠すのは CSS の仕事なので、JavaScript は要らない。

入口は読み表示より後ろに置く。 見出しの「編集」は h2 の右、本文の「編集」は本文の下である。 隣接セレクタは前へは効かないので、:has() で受ける。

/* 開いているあいだ、読み表示を隠す */
.app-head h2:has(~ .app-edit[open])  { display: none; }
.app-body-md:has(+ .app-edit[open])  { display: none; }

/* 開いたら入口も引っ込める。閉じる役は「やめる」が持つ */
.app-edit[open] > summary { display: none; }

:has() が効かない環境では、読み表示と入力欄が並んで出る。 値は同じものなので読めなくはならないが、どちらが今の値かは分かりにくい。 対応しているのは Chrome 105、Safari 15.4、Firefox 121 からで、 この製品が想定する範囲は超えている。

入口は summary である。 a でも Link でもない。 書き換える動線を、リンクにしないの規約は、 Next の Link が画面に現れた時点で行き先を先読みすることへの備えである。 ここは開閉するだけでサーバー側が動かないので、その危険には当たらない。 ただし見た目をリンクに寄せる以上、新しいタブでは開けない。 規約の側に、この形を認める一行を足す。

「やめる」を保存の隣に置く。 読み表示が消えている状態では、元へ戻る道が画面にないと手が止まる。 details を閉じるだけなので JavaScript が要るが、動かないときは summary の押し直しが受ける。

保存できたら閉じて読みへ戻す。 戻したうえで「保存しました」を読み表示の直上に出す。 失敗したときは開いたまま、フォームの中にエラーを出す。 直す対象が画面にないと直せない。

既存の仕組みを使う

入力欄の値を画面の側で持つ useField と、 保存の知らせを出す Told は 前回のセッションで入れたものをそのまま使う。 「見えている値と保存済みの値が揃っているあいだだけ知らせを出す」という判定も同じである。

印が指すものが、本文だけになる

いまの editThreadText は、タイトルだけを直したときも body_edited_at を押す。 誤字を一文字直しただけで「編集済み」が付き、 それを見た人は、いま並んでいるコメントが古い本文に向けられていないかを疑うことになる。

更新文を二つに分ける。

-- タイトル。印には触らない
UPDATE threads SET title = $4, updated_at = now() WHERE …

-- 本文。ここでだけ押す
UPDATE threads SET body = $4, body_edited_at = now(), updated_at = now() WHERE …

表示も「編集済み」から「本文編集済み」へ変える。 タイトルを直したのに印が出ないことを、印そのものが説明する。

すでにある行には、タイトルだけの変更で付いた印が混ざっている。 どちらの理由で付いたかは記録していないので、遡っては直せない。そのまま残る。

添付は、選んだ時点で終わる

ファイルを選び、それから「添付する」を押す。 この二段目は、押し忘れたときにだけ意味を持つ。 ところが押し忘れたことは画面から分からないので、意味を持つ場面が来ない。

選択とドロップの直後に requestSubmit() を呼ぶ。 縮める処理が終わってからなので、10MBを超えた写真は今までどおり品質だけ落として送られる。

ドロップを受けるのはサイドの添付欄の中だけにする。 本文列まで受け皿にすると、本文の文字を選んで動かしたときに紛れる。

押しボタンは noscript の中へ移す。 JavaScript が動かない環境では素のフォームとして残り、動く環境では画面に出ない。 添付は経路を一本に決めてあり、 ここだけ JavaScript 必須にするとその決定が崩れる。

断るときは、選んだものを欄から捨てる。 押しボタンが無い以上、直してもう一度押す機会がない。 10MBを超えたファイルが一つ混じっていたときも、全部を断る。 一部だけ送ると、何が上がって何が上がらなかったかを人が突き合わせることになる。

送信中は欄そのものが「送っています…」に変わる。 終わったら「添付しました」を短く出す。 結果が増えるのは本文列の一覧だが、広い画面では視線が右にある。

コメント側は変えない

AttachmentPicker はコメントの投稿欄でも使っている。 そちらは本文と一緒に送るものなので、選んだ時点では送れない。 即時送信は引数で切り替え、コメント側は今のままにする。

子スレッドの行に、印が出ていなかった

サイドへ移す前に、ひとつ直すものが見つかった。

スレッドには、はみ出し警告についてこう書いてある。

印は子の行に出る。 親の行にも出せるが、一覧で親に警告が付いていても、ぶら下がった十件のうちどれがはみ出しているのかは分からない。 詳細画面では親の側にも出す。こちらは子が数件ずつ並んでいるので、そこから探せる。

詳細画面は ThreadRows を showMeta={false} で呼んでいる。 落とされる meta の中に、はみ出しの印も入っている。 つまりこの画面は「子スレッドの期間が、このスレッドの期間の外に出ています。」と警告を出しておきながら、 どれがそうなのかを表示していない。探せる、と書いてあるものが探せない。

サイドの簡略行を新しく作るので、そこで印を出す。 記述のほうが正しいので、実装を寄せる。

行は2段にする。 上に種別の札とタイトル、下に番号と進捗と担当者のハンコ、そしてはみ出しとアーカイブ済みの印を置く。 一覧の行をそのまま18remへ詰めることはしない。 一覧は横に並べて比べるためのもので、こちらは一件ずつ辿るためのものである。

削除の欄は、方針に戻すだけである

UI設計方針には二箇所ある。

無効化して灰色で残すのではなく、消す。
できない操作は消す。無効化して残さない

いまの削除欄は、組織管理者に対しては常に出る。 アーカイブしていないスレッドでは、説明文と灰色の押しボタンが並ぶ。 これは方針から外れた実装である。

deleteThread の条件を確かめた。 組織管理者であること、アーカイブ済みであること、閲覧できるプロジェクトにあることの三つで、 プロジェクト側のアーカイブは見ていない。 畳んだプロジェクトの中でも、畳んだスレッドは消せる。 だから表示の条件を「組織管理者かつアーカイブ済み」にすると、操作の可否と表示が過不足なく一致する。

永続化するデータは変えない

カラムの追加も削除もない。移行も要らない。 body_edited_at は押す条件が変わるだけで、既存の行には触れない。

組んでみて分かったこと

三つあった。どれも画面を撮るまで見えなかった。

入口が次の行へ落ちた。 h2 は塊なので、その後ろに置いた「編集」が改行の下に来る。 見出しの側を display: inline にして、同じ行へ並べた。

本文とコメントのあいだに、縦150pxの空きが出た。 右の欄が二行にまたがっていて、そちらのほうが高い。 行の高さを auto auto のままにすると、余りが一行目にも配られる。 grid-template-rows: auto 1fr にして、余りは下の行が受けるようにした。

送っているあいだに欄を差し替えると、ファイルが消える。 「送っています…」で欄ごと入れ替える組み方にしていた。 ファイルの入力欄が DOM から外れるので、 requestSubmit() がフォームからファイルを拾えなくなる。 入れ替えるのは中の文字だけにして、欄そのものは置いたままにした。

試験

判定の網は既存の483件が持つ。 ブラウザの中でしか起きないものだけを E2E に置く、という線もそのままにする。 足したのは4件で、E2E は9件から13件になった。

  • 見出しの「編集」でタイトルが入力欄に入れ替わり、保存すると閉じて新しいタイトルが出る
  • 「やめる」で元のタイトルへ戻る
  • ファイルを選ぶだけで、押しボタンを押さずに添付が終わる
  • ドロップで添付が終わる

「やめる」は決めた段階では数えていなかった。 読み表示が消えている状態から戻る道なので、 入れ替えそのものと同じだけ壊れると困る。

単体の側は件数が増えていない。 タイトルの書き換えを確かめていた試験の中に、 「タイトルだけを直したときは印が付かない」と「本文を直すと付く」を足した。

アーカイブしていないスレッドに削除欄が出ないことは、置かない。 サーバー側の描画の話で、ブラウザ固有の挙動ではない。 引き換えに、表示の条件を見張るものは無くなる。

残すもの

本文の幅に上限は置かない。 1920pxの画面では、本文もコメントも1500px以上の一行になる。 サイドを18remへ広げたぶん、属性欄との距離はいくらか縮むが、 広い画面での間延びの主題はそこではない。

その課題に挙げた三つのうち、空の区画は一つだけ片付く。 子スレッドが0件のとき、区画ごと出さないことにしたためである。 コメントが0件のときの「まだありません。」は、そのまま点線の中央に浮いたままになる。
