課金を入れる

done

組織を画面から作れるようにした翌日に、料金の話になった。 課金は「利用者がついてから作るもの」として先送りしてあり、 課題のページにもそう書いてある。 その判断を今日ひっくり返した。

人数で数えると決めた理由

先送りにしたとき、ひとつだけ先に見ておいた項目がある。 何を課金の単位にしうるか、である。 後から数えられないものは単位にできないので、そこだけは実装より先に確かめてあった。

そのとき数えられると分かっていたのは、メンバー数、プロジェクト数、スレッド数、添付の総容量の四つ。 数えられないと分かっていたのが月間の活動量で、こちらは監査ログが先に要る。 今回選んだのはメンバー数で、四つのうちで唯一、画面にすでに出ている数でもある。

単価は 1 ドル。一人ぶん、ひと月ぶんである。 この額は日を置いて二度動いた。決めた経緯は末尾の「あとから変えたこと」にある。

決めたこと

何をどう決めたかなぜ
課金の単位組織ごと。その月に在籍した実人数×$1.00（税込）既存のスキーマで数えられる唯一の素直な単位
日割りしない。月途中の増加も減少もその月はフル説明が一文で終わる。按分は請求の根拠を説明できなくする
請求のタイミング後払い。6月分を7月1日に請求する在籍した実人数は、月が終わらないと確定しない
おためし期間登録日から翌月末まで月末で切ると、課金の開始月が月単位できれいに決まる
凍結書き込みを全面停止。読み取りは全部残すデータを人質にすると、払う判断をする人が中身を見られない
支払い失敗猶予なしで即凍結猶予を置くと、未収の期間だけ費用が積み上がる
凍結中の請求作らない。あとから遡って請求もしない使えなかった月の代金を、解除の瞬間に突きつけない
払わない組織無期限に放置。督促も削除もしない凍結が効いていれば費用は止まる。削除は取り返しがつかない
プラン単一。階層を作らない階層は「このプランで使えるか」の判定を全機能に散らす
決済Stripe。ただしサブスクリプションは使わない後述

Stripe のサブスクリプションが使えなかった

人数ぶんの月額を取るのだから、Stripe のサブスクリプションに座席数を持たせれば済むはずだった。 実際にはそうならない。

サブスクリプションの座席数は、請求のときの値で課金される。 月の途中で10人から8人に減らせば、その月の請求は8人分になる。 日割りを切っても変わらない。切れるのは変更時に差額を即時請求するかどうかだけで、最後に残った数が請求額を決める。 月の途中で去った二人ぶんを取る方法が無い。

「その月に在籍した実人数」と、Stripe が持っている「いまの座席数」は、別の数である。 そこで Stripe には顧客と支払い方法だけを預け、 請求は毎月こちらが人数を数えて請求書を作り、確定させることにした。

言葉が一つずれた

この決定で「サブスク登録が完了するまで操作不可」という当初の言い方が実体と合わなくなった。 利用者が行うのは支払い方法の登録であり、定期購読の契約ではない。 カードを預けた時点で凍結が解け、実際に金が動くのは翌月以降になる。

凍結は、この製品がすでに持っている形をなぞる

組織の書き込みを止めると決めたとき、判定を何箇所に入れることになるかを先に調べた。 結果として、入れる場所は二つで足りる。

ひとつは currentScope() である。 /o/{slug}/ 配下の12経路と、組織スコープを要する Server Action のすべてが、漏れなくここを通っている。 ミドルウェアも組織用の layout も持たない代わりに、この関数が唯一の入口になっている。

もうひとつが SQL の中である。 書き込みの権限を呼び出し側の値で判定しない、という規約がすでにあり、 スレッド、コメント、タグの付与、添付の書き込みは THREAD_WRITABLE という条件の断片を共有している。 アーカイブされた対象を弾いているのがこの断片で、 読み取り専用という状態は、はじめから製品の中にある。

画面と Server Action        currentScope() が凍結を返す
                                 │
                                 ▼  書き込みの入口を消す／早期に断る
SQL                         ORG_NOT_FROZEN を AND で足す
                                 │
                                 ▼  最後の砦。0 行更新で理由を引き直す

粒度は違う。 アーカイブはスレッドとプロジェクトに掛かり、凍結は組織に掛かる。 掛かる範囲も違って、アーカイブはその配下だけを止めるが、凍結は組織のすべての書き込みを止める。

止めるものと、残すもの

凍結中にできるのは読み取りと、支払いの設定だけである。 既読を付けることも、コメントのチェックボックスを動かすことも、ウォッチの切り替えもできない。 どれも読むための操作だが、実装としては書き込みなので止まる。

メンバーの削除も止まる。 凍結している間は請求そのものが止まっているので、人数を減らす意味がない。

添付のダウンロードは残す。 持ち出せる状態を保つことが、書き込みを止める側の言い分を成り立たせている。

請求日の一点だけで判定する

凍結は日単位で始まり、日単位で解ける。 請求は月まるごとか、ゼロかの二択である。 この二つは噛み合わないので、どこか一点を決めて切るしかない。

切る場所を請求日にした。 請求日に凍結していなければ、その月を満額で請求する。 月の前半が凍結していても、日数を差し引かない。

具体例

おためし期間が10月31日に終わり、11月1日に凍結。 管理者が11月15日にカードを登録して解除。

12月1日の請求日に凍結していないので、11月分を満額（11月に在籍した人数×$1.00）請求する。 11月前半の14日ぶんは差し引かない。

もし12月1日も凍結したままなら、11月分は作らない。 そして、あとから遡って請求することもない。

この規則には抜け穴がある。 毎月末にカードを外しておけば、請求日に凍結していることになり、永久に無料で使える。 外している間は書き込みが全部止まるので、単価 $1.00 のためにそれを毎月繰り返す相手は現れないと見た。

今回やらないこと

やらないこと理由
請求書払い（銀行振込）「登録は済んだが入金は未確認」という中間状態が生まれ、凍結の判定が二段になる
プランの階層機能ごとの可否判定が全機能に散る。人数課金1本なら判定は組織の状態ひとつ
未払いの督促放置された組織を追いかけない。凍結が効いていれば費用は積み上がらない
払わない組織のデータ削除無期限に置く。削除は取り返しがつかないので、運用が始まってから設計する
凍結中に新しい組織を作ることの制限組織をまたぐデータの移動手段が無いので、別組織を作っても逃げ道にならない
Stripe との疎通の自動試験テストキーで手で確かめる。自動化すると外部サービスの都合で CI が落ちる

実装して分かったこと

凍結の判定を足す場所は、調べたとおり二つで足りた。 ただし書き込みの入口を消して回る側は、二つでは済まなかった。 スレッド、コメント、タグ、プロジェクト、メンバー、ウォッチ。 画面の側は、書ける人にだけ出していた欄を、書ける状態のときにだけ出す形へ直して回ることになる。

タグの管理画面だけは、消すと読むものまで消えた。 行そのものが名前を書き換える欄でできていたためである。 凍結中は静かな行に置き換えて、名前と件数だけを残した。

THREAD_WRITABLE を定数から関数に変えた。 凍結の判定が BILLING_MODE を読むためである。 定数のままだと読み込みの時点で環境変数を要求することになり、 「イメージを作るのに本番の設定が要る」という依存が戻ってくる。

おためし期限の既定値は、狙いどおり移行の手当てを兼ねた。 バックフィルの UPDATE を書かずに済み、組織を作る側のコードも触っていない。

Stripe の SDK が、開発支援ツール向けの文字列を吐く

stripe の 22.6.1 は、環境変数 CLAUDECODE があるとき、 標準エラーへ <claude-code-hint ... value="stripe@claude-plugins-official" /> という一行を書く（node_modules/stripe/cjs/stripe.core.js:140）。

指示の形をしているが、依存パッケージが出しているものであって、こちらの意図ではない。 従っていない。動作にも影響しないが、サーバーのログに混ざるので書き留めておく。

調べて分かったこと

外部の API を叩くコードが、このプロジェクトには一行も無い。 fetch( の呼び出しがゼロで、Webhook を受ける口も無く、外向きの通信は SMTP だけである。 Stripe を入れると、送るほうも受けるほうも今回が最初になる。

定期実行の仕組みも無い。 cron も常駐プロセスも持たず、通知メールはアプリと同じプロセスの中で60秒ごとに回るループが送っている。 毎月1日の請求はこのループに相乗りさせるので、置き場は増えない。 代わりに「アプリを二つに増やせない」という制約が、通知メールに続いて二つ目を抱えることになる。

月を単位に足し引きする処理も無かった。 期限はすべて時間、日、分で書かれていて、招待は48時間、登録メールの再送間隔は3分である。 おためし期間を翌月末で切ると決めたので、月末を求める計算を新しく書く。

呼び名が一つ増えた

決めた呼び名は6語だったが、書いているうちに7語目が要ることが分かった。 課金対象月である。

「その月に在籍した人数」と「請求日に凍結していない月」は別の月を指しうるので、 どちらの月の話をしているかを名前で分けないと、請求の規則を一文で書けない。

「凍結」がすでに使われていた

プロジェクトをアーカイブしたときの説明に「プロジェクト単位で凍結する」という一文があった。 組織の課金状態に同じ語を当てると、二つの別の状態が同じ名前で呼ばれる。 アーカイブ側を「まとめて読み取り専用にする」に書き換え、「凍結」は組織の課金状態だけに使う。

あとから変えたこと

実装が通ったあとで、値付けと税の扱いを二度動かした。 どちらも同じ問いから出ている。適格請求書発行事業者の登録番号を持っていない。

消費税を別に取るのをやめた

登録していない事業者が「消費税額」を別記した請求書を出すのは、避けたほうがよい形である。 納めていない税を税として請求している見え方になる。

そこで税額の行を無くし、単価そのものを税込とした。 Stripe Tax も使わない。月0.5%の費用と、税の計算に要る住所の必須化が、まとめて消えた。 住所そのものは請求書の宛先として集め続けている。

買い手の側は、この請求書では仕入税額控除を全額は受けられない。 経過措置の割合は 2026年10月1日 に80%から50%へ下がり、2029年10月1日 に無くなる。 ただし10人の組織でも月 $10 の取引なので、控除しそこねる額は月あたり数十円である。 取引をためらう額ではないと見た。

登録しなかった理由

登録すると課税事業者になり、売上が年1,000万円以下でも消費税を納める側になる。 利用者がまだ付いていない段階で、納税義務と事務を先に背負う理由がない。

事業が育って課税事業者になる年に、登録へ切り替える。 そのとき値付けをどう読み替えるかで揉めないよう、画面にも規約にも「税込」と明記しておく。

決済代行に繋いで分かったこと

テストキーで実際に繋ぐまで見えなかったものが三つあった。

ぶつかったものどう直したか
Managed Payments アカウントで既定で有効になっていて、カードを預かる画面（mode: 'setup'）が作れない。リクエストごとに切った。アカウントの設定に頼ると、戻された日に支払いの入口だけが黙って壊れる
請求書の通貨 請求書そのものに通貨を渡していなかった。アカウントの既定（JPY）で作られ、あとから入れる USD の明細と食い違って弾かれた。明細側だけに書いてあっても足りない
一本の失敗が全部を止める 上の食い違いで巡回そのものが倒れ、後ろの組織の請求が一件も立たなくなっていた。一件ずつ守るようにし、詰まった数を数えるようにした

三つ目が一番危なかった。 5分ごとに同じところで倒れ続けるので、誰も見ていなければ気づくのは月末である。 請求が立たないことは、画面のどこにも出ない。

決済が通らなかった理由も、握りつぶしていたのをやめた。 凍結された組織を前にして「カードが悪いのか、こちらの作りが悪いのか」を切り分けられない。

通貨を USD にした

はじめは税別100円で決めていた。 グローバルに出すことを想定して、税込 1 ドルへ移した。

為替次第でおおむね ¥140〜160 になるので、これは実質4〜6割の値上げである。 意図した値付けであることを確かめたうえで動かした。

100 の意味が変わった

円は小数を持たない通貨で、Stripe に渡す 100 は100円だった。 USD は小数を二桁持つので、同じ 100 が $1.00 になる。

数字は変わらないのに単位だけが変わる。 この取り違えは、他の通貨の感覚で100倍したときに100倍の請求として現れる。 plan.ts と billing_invoices の説明に、セントであることを書いた。

切り替えの時点で請求の行は0件だったので、過去の記録と食い違ってはいない。

通貨の列は持たせなかった。すべて USD で受け取ると決めたためである。 増やすときは、過去の行がどの通貨だったかを言えるようにしてからになる。
