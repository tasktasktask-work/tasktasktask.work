仕様はほとんど書いてあった。書いてあったとおりに作ると成立しない箇所が、二つあった。 ひとつはチェックボックス、もうひとつは本文のメンションである。

チェックボックスが機能しない

機能のドキュメントは、 チェックボックスを入れる理由をこう書いていた。 「課題の中の小さな作業を表す手段が要る。これがないと、子課題を立てるほどでもない項目のために子課題が乱立する」。

ところがコメントは編集できない。 チェックを入れる操作は本文の書き換えなので、投稿したコメントの中の箱は、永遠に空のままになる。 作業を管理する道具として置いたものが、作業を管理できない。

押せるようにする、という答えだった。 そこから、状態をどこに置くかが決まる。

本文を書き換える別のテーブルに置く
コメントの不変性崩れる保たれる
同時に押されたときあとから押したほうが相手を消す衝突しない
誰が入れたか残らない残る
増えるものなしテーブルが一枚

後者を選んだ。comments の冒頭にはこう書いてある。 「投稿後に更新される経路が存在しないため、updated_at を持たない。 列がないこと自体が『編集できない』という仕様の表明である」。 チェックボックスを入れるためにこれを崩すのは、釣り合わない。

comment_checks を足した。 持っているのは、コメントの id と、本文の中で何番目の箱か、誰がいつ入れたか。 本文が動かないので、この番号は永久に同じ箱を指す。

本文のメンションが、スキーマ上ありえない

用語集は「コメントや本文の中で @ に続けて人を指名する」と書いていた。 しかし notifications の制約はこうである。

CONSTRAINT notifications_comment_required
  CHECK (kind = 'assigned' OR comment_id IS NOT NULL),

kind = 'mention' の行は、必ずコメントに紐づかなければならない。 本文のメンションは、通知の行を作れない。

メンションをコメントだけの機能にし、用語集を直した。 色だけ付けて通知を飛ばさない形も考えたが、 見た目が同じで挙動が違うものが並ぶことになる。 指名したつもりの人が、気づかれないまま残る。

どこまでが名前か

@佐藤 明日香 賛成です から名前の終わりを見つける手立てが要る。 表示名には空白が入るうえ、一意でもない。ハンドルの列も持っていない。

閲覧できる人の表示名を全部持ってきて、最も長く一致したものを採ることにした。 @ を打つと候補が出るので、選べば確実に入る。

同姓同名がいたら、その全員に通知が飛ぶ。 どちらなのかを機械が決める手立てがない。 候補はもともとそのプロジェクトを閲覧できる人に限られているので、 余分に届いても見せてはいけないものは見えない。

誰を指したかを、いつ決めるか

表示のたびに現在の名前と突き合わせる形も採れた。保存するものが増えない。

採らなかったのは、改名が起きるからである。 指名された人が改名すれば、過去のコメントの色が消える。 それより悪いのは逆で、別人が「佐藤 明日香」に改名した瞬間、 過去のコメントがその人を指しているように見える。 通知はもとの人に届いているので、画面と通知の指す先が食い違ったまま残る。

comment_mentions に、 本文の何文字目から何文字目が誰なのかを書き留める。 本文が動かないので、この位置も永久に正しい。

テーブルのドキュメントは、これと逆のことを書いていた

comments には 「本文中の @表示名 を構造化して別テーブルに持つことはしない」とあった。 二重管理を避けて、表示の食い違いを受け入れる、という判断である。

受け入れる先が想定より広かった。そちらを書き換えた。 二重管理にはならない。本文が動かないので、片方だけが古くなることが起きない。

Markdown をどう描くか

依存を入れずに済ませる案を出した。記法を絞り、HTML の文字列を一度も作らず React の要素へ直接組み立てる。そうすれば無害化の失敗という状態が起こらない。

答えは streamdown だった。

落として中を見た。分かったことが四つある。

分かったことどうしたか
無害化は効いているそのまま使う。生の HTML を通す方針に変えた
Tailwind が要るdata-streamdown 属性に自前の CSS を当てた
依存が118個増える受け入れた
位置情報が取れない本文を前処理して、独自のタグを埋め込む

最後の一点が、チェックボックスの作り方を決めた。 カスタムコンポーネントに渡ってくるのは type checked disabled と hast のノードだけで、位置は落とされている。 描画された側から「何番目の箱か」を知る手段がない。

そこで - [ ] やること を - <task i="0" state="off"></task> やること に書き換えてから渡す。 allowedTags と literalTagContent という、まさにこの用途の仕組みが streamdown にある。 指名も同じ経路で <mention> に包む。

埋め込むタグは、利用者にも書ける

<mention> を許した以上、利用者が自分で書いたものと区別が付かない。 他人を指名したように見せかける文章が書けてしまう。

下ごしらえの段階で、この二つのタグの開き括弧だけを潰している。 コードブロックとインラインコードの中は、書いたとおりに出す。

生の HTML を通すことにした

機能のドキュメントは「生のHTMLは受け付けない」と書き、 理由を「サニタイズの実装と検証にかかるコストが、得られる表現力に見合わない」としていた。

そのコストを streamdown が引き受けた。禁じる理由のほうが先に消えている。

安全の根拠が外部のライブラリに移ったことは、 課題のページに残した。 自前で書いていれば「HTML の文字列を一度も作らない」形にでき、 無害化の失敗という状態そのものを消せた。そちらは選んでいない。

本文のチェックだけでは「編集済み」にしない

スレッドの本文にもチェックボックスを出す。 こちらは編集できるので、押すと本文そのものが書き換わる。

それでも編集済みの印は付けない。 印は「課題の定義が書き換わって、それを前提に書かれたコメントが宙に浮いた」ことを知らせるものである。 項目はもとから並んでいて、終わったかどうかだけが動く。 ここで印が付けば、チェックリストを持つスレッドが例外なく「編集済み」になり、 印が何も伝えなくなる。

同時に押されたときに片方が消える問題は、実装で消した。 本文を丸ごと組み立て直すのではなく、 トランザクションの中で行を押さえて読み、その箱の三文字だけを差し替える。
