タグを付けられるようにした

done

読み取りの側は既にできていた。listThreads はタグを返し、 tagId での絞り込みも書いてある。 行を作る側と、返ってきたものを画面に出す側だけが空だった。

一覧はタグを受け取りながら描いていなかった

問い合わせは json_agg で名前と色を組み立てて返している。 ThreadRows はそれを受け取り、どこにも使っていなかった。

絞り込みの tagId も同じで、条件を組み立てる分岐はあるが、 それを渡す画面が無い。tags と thread_tags の行を作る経路も無い。 片側だけが先に用意されていた。

作れる場所を一つに絞った

付ける欄の中で作れる形にすると、手数は減る。やめたのは、 打ち間違いがそのまま新しいタグになるからである。 backend と bakcend が並んだ時点で、 組織で共通に使うという前提が壊れる。

ところが付ける欄は、名前を打つ形にした。 datalist は入力を補助するだけで制限しないので、 一覧に無い名前がそのまま届く。この二つは噛み合っていない。

届いた側で断ることにした。断る文面に 管理画面へのリンクを添える。 本当に新しいタグが要る人は、そこへ行ける。

消したものを起こす仕掛けを、作ってから捨てた

タグの一意索引は WHERE deleted_at IS NULL の部分索引である。 消した backend が残っていても、新しい backend はそのまま入る。

それでも一度は「同じ名前で作り直すときは、消えた行を起こす」と決めた。 死んだ行が溜まらないほうがよい、という理由である。 そこから三つの枝が出た。起こした行の色はどちらになるか。 同名の消えた行が複数あったらどれを起こすか。起こしたことを利用者に伝えるか。

三つとも答えを出したあとで、開発者から 「部分ユニークだと新規登録時も復活させる必要が無かったりしますか」と指摘があった。 そのとおりだった。

要らなかった理由

タグを消すときに thread_tags の行も消すと決めている。 起こした行に付いているスレッドは一件もない。 新しく入れた行と、中身が一件も違わない。

三つの枝は、どれも画面に出ない違いについての決定だった。 答えを三つ出したのに、決めた内容が一つも表に出ない。 それが、この枝が要らなかったことを示していた。

もし「消したのを取り消したい」が本当に欲しかったのであれば、 直すべきは起こす側ではなく、結びを消すという決定のほうだった。 結びを残せば、起こす操作がそのまま取り消しになる。 ただしその場合、半年前に消した backend を作り直した人の前に、 128件のスレッドが一斉にタグ付きで現れる。 消したのを取り消したい人と、同じ名前で始め直したい人が、同じ操作をすることになる。

決めたこと

論点決定理由
作れる場所管理画面だけ付ける欄で作れると、打ち間違いがタグになる
管理画面の位置/o/{slug}/tags組織の設定は管理者以外に404を返す。誰でも作れる決まりと合わない
付ける形名前を打つ欄＋畳んだチェック数十個のチェックを開いておくと、属性欄が縦に伸びて他の欄が画面外へ出る
立てるフォームチェックだけ「一つ足す」という操作が存在せず、送るのは常に全体
色八色の見本から制約は #rrggbb しか見ない。薄い色を選ばれると点が消えたのと同じになる
名前の変更できるできないと、打ち間違えたタグは消して作り直すしかない
消したとき結びも消す残すと、作り直した人の前に過去のスレッドが一斉に現れる
消す歯止め二度押し＋使用数確認の窓は押し慣れると読まれない。押しボタンの文言なら手が気づく
使用数の範囲組織の全スレッド見える範囲に絞ると、実際に外れる行数より少ない数を見せる
絞り込みの選択肢そのプロジェクトで使用中のものだけ常に0件になる選択肢を並べても探す助けにならない
付ける側の選択肢組織の全タグ使用中に限ると、新しいタグを最初に付ける道が無くなる
一覧の行三つまで、あとは +2全部並べると、タグの多い行だけ高さが変わる
通知飛ばさないnotifications_kind_valid は三種類しか許さない。足すと移行が要る
「タグなし」での絞り込み置かない探す動機は、運用が定まってから出てくる

模組が互いを呼びそうになった

スレッドを立てるときにもタグを付けるので、 #features/thread/queries.ts がタグ側を呼ぶ。 一方でタグ側は、書き込みの可否を判定するために THREAD_WRITABLE を読む。 そのままだと二つが互いを参照する。

行を入れるだけの部分を attach.ts へ分けた。 ここには判定を置かない。呼ぶ側が先に済ませている前提の関数である。 判定を書き写す形にはしなかった。 同じ条件を各所に書き写すと、片方だけ直したときに穴が開く。

色の定義も colors.ts へ分けた。 色見本は画面の側でも要るので、queries.ts を読ませると pg がブラウザ向けの束に入る。

消す押しボタンの二度押しは、サーバアクションの中の分岐にある。 アクションは cookies() を読むので、テストの中から呼べない。 分岐そのものは確かめていない。何件から外れるかを数える countTagUsage は確かめてある。

直したもの

機能ドキュメントとデータベースのドキュメントに 「リネームは初期リリースに含めていない」と書いてあった。 名前を変えられるようにしたので、そこを直した。 除外すべきだったのは統合と一括削除である。

スレッドのドキュメントにあった「タグでの絞り込みは……いまは欄が出ない」も外した。
