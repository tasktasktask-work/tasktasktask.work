Feature 01

認証

ログインの手段を二つ用意した。 メールで届くリンクを開く方法と、パスワードを入力する方法である。 ひとつのアカウントがどちらでも入れる。この重なりが、後で効いてくる。

二つの手段を併用する理由

手段が二つあると実装が増える。それでも併用にしたのは、片方がもう片方の弱点を埋めるからである。

パスワード方式には、忘れた人を復帰させる仕組みが要る。 普通は「パスワード再設定」という機能を別に作る。 ところがマジックリンクがあるなら、忘れた人はそちらで入って設定し直せばよい。 再設定の画面もトークンも要らなくなる。

同じ理屈がアカウントロックの解除にも使える。 詳しくは後述する。

パスワードに記号や数字を必須にしない。 文字種を強制すると、利用者は Password1! のような、規則を満たすだけの推測しやすい文字列に流れる。 長さだけを条件にするほうが結果として強い。

セッション

ログインすると30日間有効なセッションを作る。 アクセスによる延長はしないので、30日経てば必ず再ログインになる。 セッションIDは HttpOnly かつ Secure の Cookie に置き、値そのものはハッシュしてデータベースに保存する。

アカウントロック

同じメールアドレスに対してパスワードの入力が10回連続で失敗すると、そのアカウントのパスワードログインを止める。 時間経過では解除されない。

時間で解除しない設計が抱える穴

この仕様のままだと、第三者が任意のユーザーを締め出せる。 他人のメールアドレスにでたらめなパスワードを10回送るだけで、その人はログインできなくなる。 正規の利用者を守るはずの仕組みが、そのまま攻撃の道具になる。

そこで解除の経路を二つ置く。

  • マジックリンクでのログイン成功で自動的に解除する。メールを受け取れることが本人の証拠になっている
  • 組織管理者による手動解除。メールが届かない障害時の逃げ道として残す

あわせて、ロックがかかった時点で本人にメールを送る。 通知がなければ、締め出された人は理由も解除方法もわからないまま止まってしまう。

アカウントの作成

アカウントは二つの経路でしか生まれない。

  1. 新しい組織を作る。サインアップした人が組織を作り、その人が最初の組織管理者になる
  2. 招待を受ける。組織管理者が送ったリンクからパスワードを設定して登録する

招待リンクの有効期間はマジックリンクと揃えて48時間とする。 メールドメインによる自動参加や、URLを知っていれば誰でも入れる仕組みは持たない。

メールの送信

マジックリンク、招待、そして通知。 三つの機能がメール送信に依存している。

送信は Cloudflare Email Service の SMTP 経由で行う。 ただしアプリケーション側は MailSender という抽象を通してしか呼ばない。 開発中はコンソールへ出力する実装を差し込み、本番では SMTP（nodemailer）の実装に切り替える。 送信先を別のサービスへ移すときも、接続設定の差し替えで済む。

見込んでおくこと

Cloudflare Email Service の無料枠は月3,000通である。 100人規模で通知が動けば、ひとりあたり月30通で上限に達する。 実運用では有料枠への移行が前提になる。

未認証のときの見せ方

ログインしていない人を /login へ送らない。 いま開いているURLのまま、ログイン画面を出す。

未認証で /o/acme/p/WEB/t/128 を開く
        │
        ├── 送らない: /login?next=/o/acme/p/WEB/t/128
        │
        └── 出す:     /o/acme/p/WEB/t/128 のままログイン画面
                      認証が済んだら、そのURLに着地する

行き先を問い合わせに載せて持ち回る必要がなくなる。 ブラウザの履歴も汚れない。

戻り先はフォームの hidden 項目で運ぶ。 つまり利用者が書き換えられるので、自分のサイトの中を指していることを毎回確かめる。 素通しすると、細工したリンクを踏んだ人をログイン直後によそのサイトへ送り込める。

渡された戻り先実際の行き先
/o/acme/p/WEB?tag=bugそのまま
https://evil.example.com/
//evil.example.com/（プロトコル相対）
/\evil.example.com/（一部のブラウザが同じに扱う）
途中に改行を含むもの/（ヘッダを分割される）
/auth/magic?token=.../（戻っても意味がない）
マジックリンクは元のURLへ戻れない

リンクはメールの中にある。 どのURLで受け取ったかを覚えておくには、magic_link_tokens に列を足して持ち回る必要がある。 いまは / に着地する。

/login というURLは残してある。 ロックの通知メールがこのURLを指しているためで、 そこが特別な場所というわけではない。

SmtpMailSender.send が呼ぶと例外を投げる状態のまま置いてあった。 開発環境はコンソールへ書き出す実装なので、通しの確認では見つからない。

通知メールを作るために SMTP を実装したところ、 先にこちらが直った。通知の付属物として直る場所ではなかった。

ログインの経路は通しで確かめてある。 10回失敗させてロックがかかること、 そのときメールが飛ぶこと、 リンクを開くとロックが解けてパスワードでも入れるようになること。

失敗の理由を出し分けない

パスワードが違うのか、そのアドレスが登録されていないのか。 どちらも同じ文言を返す。

アカウントが見つからない場合も、見つかった場合と同じだけ時間をかける。 照合を省くと応答が明らかに速くなり、 誰が登録しているかを応答時間から測れてしまう。

マジックリンクの要求も同じで、登録の有無にかかわらず 「送りました」と返す。
