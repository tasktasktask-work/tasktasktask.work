Feature 08

通知とウォッチ

通知が飛ぶきっかけは三つある。そのうち二つは自動で、ひとつは自分で申し込む必要がある。 この「自分で申し込む」という設計が、運用のあり方を決めている。

三つのきっかけ

きっかけ誰に届くか自動か
メンションで指名された指名された人自動
担当者に設定された設定された人自動
新しいコメントが付いたそのスレッドをウォッチしている人申し込みが要る
アプリの中では動く。メールはまだ飛ばない

三つのきっかけはどれも行を積む。ウォッチの押しボタンも、通知の一覧も、既読もある。

まだ無いのはメールの送信である。 SmtpMailSender.send は呼ぶと例外を投げる。 SMTP クライアントの依存を決めておらず、未送信の行を拾って送る仕組みの置き場も無い。 emailed_at は誰も埋めていない。

メール通知のオンオフも、値としては users にあるが、切り替える画面がない。 アカウントの設定は別の課題に置いてある。

ウォッチは自動では付かない

スレッドを立てても、担当者になっても、コメントを書いても、ウォッチしたことにはならない。 自分でボタンを押して初めて付く。

この設計が前提とする運用

自分が立てたスレッドに返信が来ても、ウォッチしていなければ気づけない。 これを補うのはメンションだけである。 「返信するときは相手を @ で呼ぶ」という運用が、この設計の前提になっている。

自動付与を入れるかどうかの検討は通知の拡張に記録した。

二つのチャネル

アプリの中の通知一覧と、メール。 三つのきっかけはどれも両方に等しく届く。きっかけごとの出し分けはしない。

アプリ内通知には既読がある

メールは送りっぱなしで、読んだかどうかをシステムは知らない。 何を見落としたかを確かめる場所として、アプリ内の一覧が要る。 既読と未読を持つのはこちらである。

通知一覧NotificationItem
田中 亮 があなたをメンションしました
WEB-3 検索の要件をどうするか
9月4日 13:02
佐藤 明日香 があなたを担当者に設定しました
WEB-7 検索APIの実装
9月4日 13:41
ウォッチ中のスレッドに新しいコメントがあります
WEB-9 全角の正規化はどこでやっている？
9月2日 09:15
鈴木 一郎 があなたをメンションしました
WEB-5 旧検索ロジックの撤去
8月30日 16:40 コメントは削除済み

未読は全部並べる。既読は直近20件で打ち切る。 未読を上に固めず、既読と混ぜて時系列一本にする。 固めると、消化したあとに画面の上半分が空になる。

コメントが消されても、通知は残す。 呼びかけが消えても、呼ばれたことは起きた出来事である。 飛んだ先には削除の跡がある。 スレッドごと消えたものだけは、行き先が無いので一覧から外す。

既読の付き方

通知の行を押して飛ぶと、その行だけが既読になる。 それとは別に、まとめて畳む押しボタンを一つ置く。

通知の行はリンクではない

素直にリンクにすると、ブラウザとフレームワークがそれを先読みする。 マウスを乗せただけで既読になり、押していない通知が消える。 そこで行ごと押しボタンにして、既読にしてから行き先へ送る形にした。

引き換えに、新しいタブでは開けない。 見落としの取り返しがつかないほうを避けた。

飛ぶ先は、その通知が指しているコメントである。 スレッドの先頭に落とすと、コメントが50件あればそこから探すことになる。 担当者の通知はコメントを持たないので、スレッドの先頭へ送る。

行き先はフォームに書かせない。通知の行から引く。 書かせると、他人のスレッドを指した状態で自分の通知を既読にする、という形が作れる。

未読の数はどの画面にも出る

組織の中の画面には上帯があり、その右にベルが立つ。 未読があれば数が付き、押すと通知のタブが開く。

数えるのは枠そのものである。各画面が数えて渡す形にすると、 同じ三行が8つの画面に散り、足し忘れた画面ではベルだけが黙る。

メールは止められる

ユーザーごとに、メール通知をまとめてオフにできる。 きっかけごとの細かい設定は持たない。スイッチはひとつだけである。

この一つのスイッチが保険になっている

メールを止める手段がないと、煩わしく感じた人が迷惑メールとして報告する。 報告が積み重なると送信ドメインの評価が下がり、メールが届かなくなる。

このシステムは認証をメールに依存している。 マジックリンクが届かなくなれば、ログインそのものができない。 通知の煩わしさが、最終的にサービスへの入り口を塞ぐ。

非公開プロジェクトとの関係

通知の本文にはスレッドのタイトルが含まれる。 そのため非公開プロジェクトを閲覧できない人へ通知が飛ぶと、そこで情報が漏れる。

メンションの候補をプロジェクトを閲覧できる人に限っているのは、この経路を塞ぐためである。 ウォッチも、見えないスレッドには付けられない。

入り口を絞るだけでは足りない

ウォッチの行は、付けたあとに権限が動いても残る。 公開だったプロジェクトが非公開に変わる経路と、 メンバーから外される経路と、組織から抜ける経路の三つがある。 付けた時点で見えていたことは、今も見えることを意味しない。

そこで、行を作るときに宛先を絞り、一覧に出すときにもう一度絞る。 二重だが役割が違う。書く側は行を積ませないためで、読む側は最後の砦である。 メールは積まれた行から文面を作るので、書く側を抜かすと、 メールを付けた瞬間にそこが漏れ口になる。

判定は #lib/db.ts の visibleProjectIds 一つだけを使う。 宛先ごとに違う人で引くので、引数の位置を渡せる関数の形にしてある。

担当者に設定するだけなら、そのプロジェクトを見られない人にもできる。 組織のメンバーでありさえすればよいからである。 この場合、担当者にはなるが通知は飛ばない。

送信の仕組み

メールは Cloudflare Email Service の SMTP 経由で送る。 アプリケーション側は MailSender の抽象を通してのみ呼び、開発中はコンソールへ出力する実装を差し込む。

無料枠は月3,000通である。 100人規模でこの三つのきっかけが動けば、ひとりあたり月30通で上限に達する。 実運用では有料枠が前提になる。

送る仕掛けは、まだ決めていない。 行を作ってから送るまでのあいだに、誰かがその行を拾わなければならない。 拾い手には常駐プロセスか定期実行が要るが、デプロイ構成にその置き場が無い。 期限通知を先送りにしたときと同じ壁である。

初期リリースに含めないもの

  • 期限が近い課題の通知。日次バッチと常駐プロセスの設計が要るため
  • きっかけごとの通知設定。設定画面が複雑になる割に、使う人が少ないと見込んだため
  • ウォッチの自動付与。上に書いたとおり、運用で補う前提とした
  • 通知の消去と保持期間。既読を20件で打ち切って出すので、増え続けても画面は伸びない

いずれも通知の拡張に記録している。
