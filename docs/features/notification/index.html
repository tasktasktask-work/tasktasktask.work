Feature 08

通知とウォッチ

通知が飛ぶきっかけは三つある。そのうち二つは自動で、ひとつは自分で申し込む必要がある。 この「自分で申し込む」という設計が、運用のあり方を決めている。

三つのきっかけ

きっかけ誰に届くか自動か
メンションで指名された指名された人自動
担当者に設定された設定された人自動
新しいコメントが付いたそのスレッドをウォッチしている人申し込みが要る
いま動いているのは、行を作るところまで

コメントを投稿すると、指名された人とウォッチしている人の行が notifications に積まれる。ここは動いている。

その行を読む画面と、メールの送信は、まだ無い。 通知の一覧（/dashboard）を作っていないし、 SmtpMailSender.send は呼ぶと例外を投げる。 担当者に設定されたときの行も、まだ作っていない。

行を先に正しく積むことにしたのは、一覧を出した時点で過去の指名がそのまま並ぶからである。 逆にすると、一覧を作るときにコメントの投稿処理へ手を入れ直すことになる。

ウォッチは自動では付かない

スレッドを立てても、担当者になっても、コメントを書いても、ウォッチしたことにはならない。 自分でボタンを押して初めて付く。

この設計が前提とする運用

自分が立てたスレッドに返信が来ても、ウォッチしていなければ気づけない。 これを補うのはメンションだけである。 「返信するときは相手を @ で呼ぶ」という運用が、この設計の前提になっている。

自動付与を入れるかどうかの検討は通知の拡張に記録した。

二つのチャネル

アプリの中の通知一覧と、メール。 三つのきっかけはどれも両方に等しく届く。きっかけごとの出し分けはしない。

アプリ内通知には既読がある

メールは送りっぱなしで、読んだかどうかをシステムは知らない。 何を見落としたかを確かめる場所として、アプリ内の一覧が要る。 既読と未読を持つのはこちらである。

通知一覧NotificationItem
田中 亮 があなたをメンションしました
WEB-3 検索の要件をどうするか
9月4日 13:02
佐藤 明日香 があなたを担当者に設定しました

9月4日 13:41
ウォッチ中のスレッドに新しいコメントがあります
WEB-9 全角の正規化はどこでやっている？
9月2日 09:15

メールは止められる

ユーザーごとに、メール通知をまとめてオフにできる。 きっかけごとの細かい設定は持たない。スイッチはひとつだけである。

この一つのスイッチが保険になっている

メールを止める手段がないと、煩わしく感じた人が迷惑メールとして報告する。 報告が積み重なると送信ドメインの評価が下がり、メールが届かなくなる。

このシステムは認証をメールに依存している。 マジックリンクが届かなくなれば、ログインそのものができない。 通知の煩わしさが、最終的にサービスへの入り口を塞ぐ。

非公開プロジェクトとの関係

通知の本文にはスレッドのタイトルが含まれる。 そのため非公開プロジェクトを閲覧できない人へ通知が飛ぶと、そこで情報が漏れる。

メンションの候補をプロジェクトを閲覧できる人に限っているのは、この経路を塞ぐためである。 担当者の設定とウォッチについても、プロジェクトのメンバーでなければそもそも操作できない。

送信の仕組み

メールは Cloudflare Email Service の SMTP 経由で送る。 アプリケーション側は MailSender の抽象を通してのみ呼び、開発中はコンソールへ出力する実装を差し込む。

無料枠は月3,000通である。 100人規模でこの三つのきっかけが動けば、ひとりあたり月30通で上限に達する。 実運用では有料枠が前提になる。

初期リリースに含めないもの

  • 期限が近い課題の通知。日次バッチと常駐プロセスの設計が要るため
  • きっかけごとの通知設定。設定画面が複雑になる割に、使う人が少ないと見込んだため
  • ウォッチの自動付与。上に書いたとおり、運用で補う前提とした

いずれも通知の拡張に記録している。
