Feature 08

通知とウォッチ

通知が飛ぶきっかけは三つある。そのうち二つは自動で、ひとつは自分で申し込む必要がある。 この「自分で申し込む」という設計が、運用のあり方を決めている。

三つのきっかけ

きっかけ誰に届くか自動か
メンションで指名された指名された人自動
担当者に設定された設定された人自動
新しいコメントが付いたそのスレッドをウォッチしている人申し込みが要る
三つとも、アプリの中とメールの両方に届く

きっかけの数だけ行が積まれる。 その行はアプリ内の一覧に並び、同じ行から通知メールの文面が作られる。

メールを送るのは、投稿した人のリクエストの中ではない。 巡回が後から拾って送る。

ウォッチは自動では付かない

スレッドを立てても、担当者になっても、コメントを書いても、ウォッチしたことにはならない。 自分でボタンを押して初めて付く。

この設計が前提とする運用

自分が立てたスレッドに返信が来ても、ウォッチしていなければ気づけない。 これを補うのはメンションだけである。 「返信するときは相手を @ で呼ぶ」という運用が、この設計の前提になっている。

自動付与を入れるかどうかの検討は通知の拡張に記録した。

二つのチャネル

アプリの中の通知一覧と、メール。 三つのきっかけはどれも両方に等しく届く。きっかけごとの出し分けはしない。

アプリ内通知には既読がある

メールは送りっぱなしで、読んだかどうかをシステムは知らない。 何を見落としたかを確かめる場所として、アプリ内の一覧が要る。 既読と未読を持つのはこちらである。

通知一覧NotificationItem
田中 亮 があなたをメンションしました
WEB-3 検索の要件をどうするか
9月4日 13:02
佐藤 明日香 があなたを担当者に設定しました
WEB-7 検索APIの実装
9月4日 13:41
ウォッチ中のスレッドに新しいコメントがあります
WEB-9 全角の正規化はどこでやっている？
9月2日 09:15
鈴木 一郎 があなたをメンションしました
WEB-5 旧検索ロジックの撤去
8月30日 16:40 コメントは削除済み

未読は全部並べる。既読は直近20件で打ち切る。 未読を上に固めず、既読と混ぜて時系列一本にする。 固めると、消化したあとに画面の上半分が空になる。

コメントが消されても、通知は残す。 呼びかけが消えても、呼ばれたことは起きた出来事である。 飛んだ先には削除の跡がある。 スレッドごと消えたものだけは、行き先が無いので一覧から外す。

既読の付き方

通知の行を押して飛ぶと、その行だけが既読になる。 それとは別に、まとめて畳む押しボタンを一つ置く。

通知の行はリンクではない

素直にリンクにすると、ブラウザとフレームワークがそれを先読みする。 マウスを乗せただけで既読になり、押していない通知が消える。 そこで行ごと押しボタンにして、既読にしてから行き先へ送る形にした。

引き換えに、新しいタブでは開けない。 見落としの取り返しがつかないほうを避けた。

飛ぶ先は、その通知が指しているコメントである。 スレッドの先頭に落とすと、コメントが50件あればそこから探すことになる。 担当者の通知はコメントを持たないので、スレッドの先頭へ送る。

行き先はフォームに書かせない。通知の行から引く。 書かせると、他人のスレッドを指した状態で自分の通知を既読にする、という形が作れる。

未読の数はどの画面にも出る

組織の中の画面には上帯があり、その右にベルが立つ。 未読があれば数が付き、押すと通知のタブが開く。

数えるのは枠そのものである。各画面が数えて渡す形にすると、 同じ三行が8つの画面に散り、足し忘れた画面ではベルだけが黙る。

メールは止められる

ユーザーごとに、メール通知をまとめてオフにできる。 きっかけごとの細かい設定は持たない。スイッチはひとつだけである。

この一つのスイッチが保険になっている

メールを止める手段がないと、煩わしく感じた人が迷惑メールとして報告する。 報告が積み重なると送信ドメインの評価が下がり、メールが届かなくなる。

このシステムは認証をメールに依存している。 マジックリンクが届かなくなれば、ログインそのものができない。 通知の煩わしさが、最終的にサービスへの入り口を塞ぐ。

切り替えは /me に置く。組織の下ではない。 値は users にあり、所属しているすべての組織に効くためである。 /o/{slug}/... の下に置くと、その組織だけの設定に見える。 三つの組織に居る人が三箇所を止めて回り、一つ見落として届き続ける、という形を作らない。

止め方はメールの末尾にも書く。

切り方を知る場所が、アプリの中にしか無いと困る

煩わしいと感じた人は、メールを開いたその場で判断する。 そこに切り方が書いていなければ、迷惑メールの押しボタンのほうが近い。 上のスイッチは、見つけられて初めて保険になる。

List-Unsubscribe ヘッダは付けない。 あれは押した瞬間に止まる約束であり、認証を通さずに止める口を開けることになる。 末尾には /me への URL を置き、ログインしてから切ってもらう。

マジックリンクと招待は、この設定に関わらず届く。 こちらは通知ではなく、本人が待っている応答である。

非公開プロジェクトとの関係

通知の本文にはスレッドのタイトルが含まれる。 そのため非公開プロジェクトを閲覧できない人へ通知が飛ぶと、そこで情報が漏れる。

メンションの候補をプロジェクトを閲覧できる人に限っているのは、この経路を塞ぐためである。 ウォッチも、見えないスレッドには付けられない。

入り口を絞るだけでは足りない

ウォッチの行は、付けたあとに権限が動いても残る。 公開だったプロジェクトが非公開に変わる経路と、 メンバーから外される経路と、組織から抜ける経路の三つがある。 付けた時点で見えていたことは、今も見えることを意味しない。

そこで、行を作るときに宛先を絞り、一覧に出すときにもう一度絞る。 二重だが役割が違う。書く側は行を積ませないためで、読む側は最後の砦である。 メールは積まれた行から文面を作るので、書く側を抜かすと、 メールを付けた瞬間にそこが漏れ口になる。

判定は #lib/db.ts の visibleProjectIds 一つだけを使う。 宛先ごとに違う人で引くので、引数の位置を渡せる関数の形にしてある。

担当者に設定するだけなら、そのプロジェクトを見られない人にもできる。 組織のメンバーでありさえすればよいからである。 この場合、担当者にはなるが通知は飛ばない。

送信の仕組み

メールは Cloudflare Email Service の SMTP 経由で送る。 クライアントは nodemailer である。 アプリケーション側は MailSender の抽象を通してのみ呼び、開発中はコンソールへ出力する実装を差し込む。

無料枠は月3,000通である。 100人規模でこの三つのきっかけが動けば、ひとりあたり月30通で上限に達する。 実運用では有料枠が前提になる。

リクエストの中では送らない

コメントを書いた人のリクエストの中で SMTP の応答を待つわけにいかない。 相手が詰まれば、投稿の押しボタンも詰まる。 行だけを先に積み、巡回が後から拾う。

マジックリンクと招待は逆に、リクエストの中で送り切る。

ログインだけは、その場で送って結果を見る

通知と同じ列に積むと、ログイン用リンクが最大一分遅れて届く。 ログインは待っている人の目の前で起きるので、その遅れは直接見える。

失敗したときに「送りました」と嘘をつかないためでもある。 積んで返すと、送れたかどうかを知らないまま画面が先に進む。

巡回

間隔は60秒である。この60秒は、まとめる幅でもある。

一巡は次の三段で進む。

1. 送らないと決める   読まれた / 切っている / 見えなくなった / 消された
2. 掴む               古い順に50人ぶん。試行の回数をここで増やす
3. 送る               宛先ごとに一通。結果を書き戻す

一巡で相手にする宛先は50人までとし、あふれた分は次の巡回が拾う。 拾う順は古い順である。ここで打ち切ると、後ろに並んだ人の通知が永久に順番待ちになる。

送らない行にも、決着が要る

一段めを飛ばすと、送らない行が索引に残り続ける。 拾う順は古い順なので、居座った行が枠を先に取り、後ろの人へいつまでも届かない。 送らないと決めることと、送るのをやめることは、同じ操作でなければならない。

決着には email_gave_up_at を使う。 ここで畳んだ行は email_attempts が 0 のままなので、 送ろうとして駄目だった行とは、あとから数え分けられる。

試行の回数は、掴むときに増やす

送ってから増やす形も取れる。そちらだと、送信の途中でプロセスが落ちる束は 回数が永久に 0 のまま、起動のたびに同じ場所で落ち続ける。 先に増やしておけば、そういう束もいずれ上限に達して外れる。

送れた行には emailed_at が入るので、増えた回数は「何回目で届いたか」として残る。

掴む取引は、そこで閉じる。 SMTP の応答をロックを握ったまま待つと、相手が詰まっているあいだ、その行に触れる問い合わせが並ぶ。

送れなかったとき

宛先が壊れているのと、相手が一時的に応じないのとを、回数だけでは区別できない。

返ってきたもの扱い次の巡回
SMTP 5xx恒久。宛先が無いその場で諦める
SMTP 4xx一時。いまは受けられないもう一度試す
接続の失敗一時として扱うもう一度試す
60回試した諦める拾わない

接続の失敗を一時として扱うのは、相手が居ないのか経路が切れているだけなのかを、 こちらから区別できないためである。

上限を60回に取ってある

60秒ごとなので、一時間ぶんにあたる。

数回で諦めると、Cloudflare 側が5分止まっただけで、その間の通知が全部捨てられる。 一時間で復旧しない SMTP は、諦めたことより先に気づくべき事態である。

文面

宛先ごとに一通へまとめる。会議がひとつ荒れると、同じ人に十数通が数分で届く。

一件のときだけ、コメントの冒頭を4行まで引用する。 まとめたときは見出しの一覧にとどめる。

全部載せない

本文を丸ごと載せると、メールを読んだ時点で用が済む。 スレッドに返事が戻らなくなり、決まったことがメールの中だけに残る。

消されたコメントは引用しない。消えた文章を配り直さない。 ただし通知そのものは出す。呼びかけが消えても、呼ばれたことは起きた出来事である。

組織をまたいで届くことがある。またぐときだけ、どこの話かを添える。

置き場

巡回はアプリと同じプロセスで回す（src/instrumentation.ts）。 デプロイ構成に常駐プロセスも定期実行も無く、足すとイメージの配り方から見直すことになる。 期限が近い課題の通知を先送りにしたときと同じ壁である。

コンテナが一つであることに寄りかかっている

掴むところでは FOR UPDATE SKIP LOCKED を使うが、 ロックは掴む取引の終わりで放される。送るのはそのあとである。

したがって、コンテナを二つに増やすと同じ束が二度送られうる。 増やすときは、掴んだ印を行に持たせる必要がある。 いま動くのは一つだけである（deploy/compose.yaml）。

初期リリースに含めないもの

  • 期限が近い課題の通知。巡回の置き場はできたが、 日付をまたいで一度だけ送る仕掛けが別に要るため
  • きっかけごとの通知設定。設定画面が複雑になる割に、使う人が少ないと見込んだため
  • ウォッチの自動付与。上に書いたとおり、運用で補う前提とした
  • 通知の消去と保持期間。既読を20件で打ち切って出すので、増え続けても画面は伸びない

いずれも通知の拡張に記録している。
