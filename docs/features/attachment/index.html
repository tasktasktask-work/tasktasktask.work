Feature 06

添付ファイル

アップロードされたファイルの種別を、このシステムは検査しない。 拡張子も、先頭のバイト列も見ない。 その代わり、配信の仕方で守る。

検査をやめた理由

スレッドやコメントに付けるファイルを添付ファイルと呼ぶ。保存先はサーバー上のローカルボリュームで、実体はファイルシステム側にある。

設計の途中まで、許可する形式を並べたホワイトリストを置く方針だった。 マジックバイトで種別を判定し、リストにあるものだけを通す。 それをやめたのは、次の四つが同時に成り立つとわかったからである。

判定できない形式が半分近くある

形式先頭のバイト列判定
JPEG, PNG, GIF, WebP, PDFFFD8FF 89504E47 ほかできる
xlsx, docx, pptxPK\x03\x04zip と区別できない
zipPK\x03\x04Office と同一
txt, csv, md, json規則なしできない

Office 文書の実体は zip である。 区別するには中身を展開して構成ファイルまで読む必要があり、それはもうマジックバイト判定ではない。

判定できる形式も素通りする

GIF89a で始まり、その後ろに HTML と JavaScript を詰めたファイルは、判定を正しく通過する。 先頭数バイトの確認は、残りの中身について何も保証しない。

実行ファイル対策としては成立しない

zip を許可すれば、その中に何を入れても通る。 zip を禁じても、拡張子を変えれば通る。

そもそもサーバーがファイルを実行しない

置かれたファイルが実行される危険は、Webルート上のファイルを解釈実行する構成に固有のものである。 ローカルボリュームに保存して Node.js が配信するだけの構成では、.php を置かれても単なるバイト列にすぎない。

結論

検査は、実装と維持のコストを払う割に守れる範囲が狭い。 そして「検証済み」という誤った安心を与える。 守れないものを守っているように見せる仕組みは、判断を誤らせる分だけ有害である。

何が実際に効くのか

添付ファイルの本当の危険は、保存された XSS である。 攻撃者が HTML や SVG をアップロードし、同僚がそのURLを開くと、このサービスのオリジンで JavaScript が動き、セッションが盗まれる。

これに効くのは中身の検査ではなく、返し方である。

  1. 必ず Content-Disposition: attachment を付ける。ブラウザは表示せずダウンロードする
  2. X-Content-Type-Options: nosniff を付ける。中身を見て勝手に HTML と解釈する挙動を止める
  3. Content-Type は application/octet-stream 固定。インライン表示する画像だけを例外とする
  4. Content-Security-Policy: default-src 'none'; sandbox を付ける。万一実行されかけても止まる
  5. 画面に表示する画像は、サーバー側で読み直して書き出し直す。

5 が要になる。 検査して通すのではなく、作り直して安全なものだけを出力する。 読めなかったファイルは画像として扱わず、ダウンロードできるだけの添付になる。 維持すべきリストがどこにも存在せず、デコーダそのものが判定器になる。

副産物として、ポリグロットも Exif の位置情報も構造的に消える。 ただしそれは、保存するのが作り直した出力だけだからである。 原本を並べて残せば、位置情報は残る。 「消えたと思っている人の期待」を裏切らないために、原本は捨てる。

サムネイルは別に持たない。画面では原寸のまま並べ、大きさは CSS で抑える。 別の一枚を持つには保存先のキーがもう一つ要り、行の形が変わる。

画像だけは、少しのあいだ持たせる

Cache-Control は既定で private, max-age=0, no-store である。 ただし画像だけは private, max-age=600 にしてある。 そうしないと、スレッドを開くたびに貼られた画像を全部取り直すことになる。

引き換えに、消してから10分はブラウザの中に残りうる。 実体はコミットの直後に消えるので、残る窓はその10分だけである。

nosniff は二重に付けてある

next.config.ts が全経路に同じヘッダを付けているので、 配信の経路にある指定は重複している。 それでも書いてあるのは、この経路が守っているものを一枚のファイルの中で読み切れるようにするためである。

片方を消しても壊れないので、この一行の欠落だけはテストで捕まえられない。 実際に外して通し確認に当ててみたが、素通りした。

配信は本体と同じオリジンから行う

設計の途中まで、添付を別のドメインから配信する方針だった。 万一スクリプトが動いても、本体のオリジンとは別なのでセッションに触れられない、という理屈である。

採らなかった。実際に守っているのは上の四つのヘッダであって、オリジンの分離ではないからである。 分離が足すのは「この配信経路に手を入れた誰かが将来間違えたとき、被害を抑える」という保険だけで、 その保険には実費がある。

別オリジンにすると認可を作り直すことになる

別のドメインにはセッションの Cookie が送られない。 つまり非公開プロジェクトの添付を誰に見せるかを、 署名付きURLのような別の仕組みで決めることになる。 同一オリジンなら Cookie がそのまま使え、閲覧判定は他の画面と同じ経路で済む。

同一オリジンにしたぶん、経路の作り方に条件を付ける。

  • 添付を返す経路を1本に限る。その関数が常に四つのヘッダを付ける。 インライン表示を切り替えるパラメータを作らない
  • インライン表示するのは、サーバー側で再エンコードした出力だけ。 Content-Type は決め打ちの値から選び、利用者由来の値を反映しない
  • ヘッダが付いていることをテストで確かめる。 この経路の誤りは、同一オリジンではセッションの盗難に直結する

保存と制限

項目内容
保存先VPS 上のローカルボリューム。キーの組み立てを一箇所に閉じ、将来のオブジェクトストレージ移行に備える
ファイル名生成したIDで保存する。元のファイル名はメタデータとして持ち、表示時にエスケープする
サイズ上限1ファイル 10MB。一度の送信で合計 30MB
件数の上限なし
形式の制限なし
画像の前処理サーバー側で再エンコードする。ブラウザ側の圧縮は上限を超えたときだけ働く
組織あたりの総量上限なし。合計を設定画面に出す

ファイル名をそのままパスに使わない理由は二つある。 ../../ を含む名前によるパストラバーサルと、 右横書きの制御文字を混ぜて report‮gpj.exe を report.exe.jpg に見せかける手口である。

合計 30MB の枠は、1ファイルの上限とは別の理由で要る。 送信の本体はサーバー側で丸ごとメモリに載るので、 この数字がそのまま同時アップロード1件あたりの消費になる。 next.config.ts の bodySizeLimit と、 nginx 側の CLIENT_MAX_BODY_SIZE は、この枠に揃えて上げてある。 片方だけ上げると、本番でだけ 413 が返る。

中身の無いものは、選ばれなかったものとして扱う

添付を付けずにコメントを投稿しても、ファイルの欄は送られてくる。 そのとき届く形は一つではない。名前の無い File のこともあれば、 名前を失って Blob になっていることもある。 Blob を FormData に入れると、仕様どおり blob という名前が付く。

つまり「何も選んでいない」と「空のファイルを選んだ」は、 サーバーへ届いた時点では見分けられない。名前が残っていないためである。

断るほうを選ぶと、添付を付けないコメントが一つも投稿できなくなる。 そこで、大きさが 0 のものは選ばれなかったものとして落とす。

断る側に倒して壊れた

最初は「中身が空です」と断っていた。 空のファイル欄は名前も空で届くと考えて、名前の有無で見分けていた。

本番では名前が blob で届いた。 見分けが外れ、コメントを書くたびに 「blob は中身が空です」と出て、投稿できなくなった（2026-09-08）。

手元では起きなかった。フォームを直に組む試験では、 符号化の層を通らないためである。

何も付かなかったこと自体は、付ける側の画面が伝える。 スレッドへ添付する画面は「ファイルを選んでください」と返す。 コメントの画面は何も言わない。本文だけの投稿は、それでよいためである。

ただしスレッドの側でこの断りに行き着くのは、JavaScript が動かないときだけである。 動いていれば、選ばずに送る手段がない（次節）。

スレッドへ付けるときは、選んだ時点で送る

詳細画面の右の欄に、落とす受け皿がある。 そこへ落とすか、ファイルを選ぶと、そのまま送信まで終わる。押しボタンは無い。

以前は「選ぶ」と「添付する」の二段だった。 二段目は押し忘れたときにだけ意味を持つ押しボタンで、 ところが押し忘れたことは画面から分からないので、意味を持つ場面が来ない。 間違えて付けたものは、一覧の側から一押しで消せる。

受け皿はその欄の中だけである。 本文列まで広げると、本文の文字を選んで動かしたときに紛れる。

断るときは、選んだものを欄から捨てる。 押しボタンが無いので、直してもう一度押す機会がない。 上限を超えたファイルが一つ混じっていたときも、その回の全部を断る。 一部だけ送ると、何が上がって何が上がらなかったかを人が突き合わせることになる。

コメントの投稿欄は今までどおり二段である。 こちらは本文と添付を一つの送信で出すので、選んだ時点では送れない。

ブラウザ側の圧縮は、超えたときだけ働く

アップロード前に browser-image-compression で圧縮する。 ただし常に圧縮するのではなく、10MB を超えた画像だけを品質で縮める。 常に縮めると、1MB の写真も劣化する。 得るのは上りの数百ミリ秒で、失うのは元に戻せない画質である。

触るのは品質だけで、長辺は変えない。 サーバー側で縮めないと決めたのと同じ理由で、 ここで縮めると、その一枚は二度と原寸に戻らない。 PNG は触らない。画面の写しの文字が JPEG 変換で潰れると、添付の用をなさなくなる。

縮めても収まらなければ、送る前に止める。 10MB を超えるものを送ってから断られるのは、上りに数十秒かけたあとである。

同じファイルが、ブラウザによって別の扱いになる

iPhone の写真（HEIC）は、サーバー側のデコーダが読めない。 ライセンスの都合で libheif が入っていないためである。

ところが Safari の canvas はこれを読める。 圧縮が働く大きさなら、Safari から貼った写真は JPEG になってサーバーに届き、 画像として扱われる。Chrome から同じ写真を貼ると、ダウンロードできるだけの添付になる。

受け入れた差である。揃えるには HEIC を読めるデコーダを持ち込むことになり、 それは形式ごとの経路を増やす方向の判断になる。

JavaScript が動かなくても送れる

送るのは素のフォームである。 圧縮は、動くときにだけ挟まる余分な処理として置いてある。 動かなければ原本がそのまま上がり、大きすぎればサーバーが断る。

選んだ時点で送る形も、動くときにだけ挟まる処理である。 スレッドの欄の「添付する」は noscript の中に置いてある。 動かない環境では素のフォームとして押せて、動く環境では画面に出ない。 ここだけ JavaScript 必須にすると、送信の経路を一本に決めた判断が崩れる。

進捗は割合で出さない。 上りの進捗を取るには XMLHttpRequest が要り、 一本にすると決めた送信の経路がもう一本増える。 出るのは「縮めています」「送っています」、そして終わったことを知らせる「○件を添付しました」だけである。

残っている危険

形式を制限しないため、マルウェアの受け渡しには使える。 配信ヘッダは実行を防ぐが、利用者が自分でダウンロードして開くことは止められない。

これに効くのはウイルススキャンだけである。 拡張子でもマジックバイトでもない。 導入の検討はウイルススキャンに記録した。

もう一つ残っているのが、行の無いファイルである。 データベースとファイルシステムは同じ取引に入らない。 行を先に入れ、実体を書き、最後にコミットする順にしてあるが、 「書けたがコミットで落ちた」窓は残る。 そこに残るのは誰にも見えず容量だけ食うファイルで、 掃除の仕組みは持たない（行の無いファイル）。

あわせて、容量の監視とバックアップ対象への追加が運用上必要になる。 詳しくはデプロイ構成に書いた。

付ける場所と、消せる人

付けられるのはスレッドの本文と、 コメントの二箇所である。 仕様書や画面の写しは本文の側の情報で、コメントに混ぜると流れて探せなくなる。

スレッドを立てる画面には欄を置いていない。 立てる処理は親子と期間とタグを一つの取引で検査するので、 そこへ 30MB の書き込みを足すと、失敗したときにファイルの選び直しまで巻き込む。 立てた直後の詳細画面で付けられる。

本文に付けられるのは、本文を書き換えられる人と同じ範囲である。 本文そのものを書き換えられる相手に、添付だけ禁じても守るものが無い。

消せるのは上げた本人と組織管理者だけで、 ここだけは範囲が狭い。消すと実体も消えて取り消せないためである。 消す動機の大半は「見えてはいけないものが置いてある」で、 行だけ落として実体を残すと目的を果たさない。

行のほうは残す。deleted_by_user_id は他のどのテーブルにも無い列だが、 消せる人が二通りあるのはここだけである。 貼った画像が消えている理由を尋ねられたとき、 自分で消したのか管理者が消したのかが分からないと、一次調査ができない。

畳んだ後は、貼った本人には消せない

アーカイブ済みのスレッドでは添付を消せない。 畳んだものへの書き込みを一律で止める線に揃えてある。

畳みを解けるのは管理者だけなので、 貼った本人が「畳んだ後に消したくなった」ときは、自分だけでは手が無い。 一貫性を取ったぶんの代償である。
