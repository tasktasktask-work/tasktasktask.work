Feature 04

スレッド

課題管理ツールの多くは「課題」を基本単位に置く。 そして議論はその付属物として、コメント欄の中に押し込まれる。 ここでは順序を逆にした。基本単位はスレッドであり、課題はその種別のひとつでしかない。

なぜ課題を基本単位にしなかったか

開発の現場で交わされる話は、最初から課題の形をしていない。 「検索の要件、どうしますか」という相談には、まだ実装のゴールがない。 「全角の正規化はどこでやってますか」という疑問には、そもそも作業が伴わない。

これらを課題として登録すると、いつまでも閉じない課題が一覧に溜まる。 かといってチャットへ流すと、決まったことが記録に残らない。

そこで、置き場所そのものを用意した。 スレッドという共通の器があり、その種別として課題と議論と質問が並ぶ。 三つとも同じ形なので、同じ一覧に出て、同じように親子でつながる。

三つの種別

議論type = giron

種別意味進捗率期間ガント

種別は後から変更できない。 議論として立てたスレッドを課題に作り変えることはできず、課題のスレッドを別に立てることになる。 そのとき二つをつなぐ手段は親子関係だけである。 議論を親、課題を子にすれば、「この課題はどの議論から出てきたのか」を辿れる。

この経路しかない

議論と、そこから生まれた課題を結びつける方法は親子関係だけである。 親子をつけ忘れると、両者の関係は失われる。 議論をクローズするときに子の課題が一つもなければ注意を出す、といった補助は初期リリースに含めていない。

立てる

立てるのに要るのは種別とタイトルだけである。 本文も、担当者も、期間も、タグも、立てたあとに詳細画面で入れる。

入口は二つある。 スレッド一覧の見出しとタブのあいだにある一行のフォームと、 スレッド詳細の右の欄にある「このスレッドを親にして 課題 / 議論 / 質問 を作成する」である。 後者では、押した語がそのまま種別になり、親はその画面のスレッドに決まる。 番号を書き写す手間が無いので、親子をつけ忘れる道がひとつ減る。

立てても画面は移動しない。 一覧では、タイトル欄が空に戻り、選んだ種別はそのまま残る。 立てた番号は欄の下に一行だけ出て、押すと詳細が開く。 絞り込みの条件から外れた行は一覧に現れないので、この知らせが結果を伝える唯一の手段になることがある。

以前は専用の画面があり、種別、タイトル、本文、親、担当者、期間、タグの7つを一度に入れる形だった。 本文を書く場所が要る、という理由で分けてある画面だった。 この理由が支えるのは本文を書ける場所を用意することまでで、立てる前に書かせることまでは支えない。 課題なら、立てる時点でやることの形が言える。 議論と質問は逆で、何が決まっていないのかを言えないから相談として置く。 そこへ本文を先に要求すると、この製品が置き場所を用意した相談ほど、入口が重くなる。

空のスレッドが並ぶことは、この形では止められない。 代わりに、本文を書く距離を詰めてある。 立てた直後に開く画面では、本文の位置に編集の入口がある。

進捗率

状態を表す欄は進捗率ひとつしかない。 0が未着手、100が完了、その間が進行中である。 議論と質問では0と100しか取らず、画面ではオープンとクローズと呼ぶ。

進捗表示ProgressMeter / OpenCloseBadge
0% 課題 / 未着手
40% 課題 / 進行中
100% 課題 / 完了
オープン議論と質問 / 0
クローズ議論と質問 / 100

値は担当者が自分で入力する。1刻みで自由に入れられるが、入力欄には <datalist> で0、25、50、75、100の候補を出す。 自由入力を残しつつ、よく使う値を一手で選べるようにするためである。

進捗率だけで表せないもの

「やらないと決めた課題」と「まだ手をつけていない課題」は、どちらも0のまま並ぶ。 「レビュー中」のような工程も数値では表せない。 どう扱うかは各組織の運用に委ねる方針を取った。 アーカイブするか、100にするか、タグで示すか。 この判断が組織ごとにばらつくことは承知のうえで、経緯を却下の表現に記録している。

親子関係

スレッドの下にスレッドをぶら下げられる。深さの制限はない。

  • 種別はまたげる。議論の子に課題、課題の子に質問を置ける
  • プロジェクトはまたげない。親と子は必ず同じプロジェクトに属する
  • 集計はしない。親の進捗率も期間も、子とは独立して人が入力する

親は後から付け替えられる。 詳細画面の右の欄、子スレッドの真上に「親スレッド」の欄がある。 いまの親が子と同じ形の行で出ていて、その下の入力欄に WEB-3 か 3 と入れると付け替わる。 空にすると親から外れる。 選択肢の一覧にしていないのは、プロジェクトのスレッドが数百件になると選べなくなるためである。 親にしたいスレッドは、たいてい直前に見ている。

付け替えは輪を作りうる。 自分の子孫を親に選ぼうとしたときは、祖先を辿って断る。 辿るところと書くところは同じ取引の中にある。

親の期間を子から自動計算しない理由は、親が固有の締切を持てなくなるからである。 「この塊は7月末まで」という計画は、子の日付の最大値とは別の情報である。 子がそこからはみ出したときははみ出し警告を出すが、値の書き換えはしない。 どう直すかは人が決める。

印は子の行に出る。 親の行にも出せるが、一覧で親に警告が付いていても、ぶら下がった十件のうちどれがはみ出しているのかは分からない。 詳細画面では親の側にも出す。こちらは子が数件ずつ並んでいるので、そこから探せる。

判定は親と子の両方に期間があるときだけ行う。 親が期間未設定なら、外側の枠そのものが無い。

はみ出す日付を入力すること自体は止めない。 止めると、親の締切を延ばすまで子の日付を入れられなくなる。 順番を強いるほどの話ではない。

識別子

スレッド番号は組織の中で通し番号になっている。 表示はプロジェクトキーを前に付けて WEB-128 の形になる。

プロジェクトごとに1から振らないため、一つのプロジェクトだけを見ると番号が飛ぶ。 WEB-3 の次が WEB-7 になるのは正常な状態である。 番号が同じスレッドが別プロジェクトに存在しない、という性質を優先した。

担当者

ひとつのスレッドに担当者はひとりだけ置ける。未設定でもよい。 複数人を割り当てられるようにはしていない。全員が自分の仕事ではないと思う状態を避けるためである。

担当者に設定されると通知が飛ぶ。 また担当スレッド一覧では、この人の名前でプロジェクトをまたいでスレッドが集まる。

一覧の見え方

スレッド一覧は階層を作らず平らに並べる。 親と子へは、それぞれの行に置いたリンクから辿る。

スレッド行ThreadRow
議論 検索の要件をどうするか オープン 佐 WEB-3 設計 子 2件 → 更新 9/4
課題 検索APIの実装 40% 田 WEB-7 backend ← 親 WEB-3 9/8 – 9/19
質問 全角の正規化はどこでやっている？ クローズ 鈴 WEB-9 ← 親 WEB-7 更新 9/2

絞り込みの軸は種別、担当者、タグ、進捗率が100のものを除くかどうか、アーカイブ済みを出すかどうかである。 全文検索を持たないため、この絞り込みが探すための唯一の手段になる。 既定の並び順は更新の新しい順とする。

担当者では「未設定」だけを選べる。 誰も持っていない課題を集めるのは、割り振りを決める会議で毎回やることになる。

タグの選択肢には、そのプロジェクトで実際に使われているものだけが並ぶ。 一つも使われていなければ、欄そのものが出ない。 組織の全タグを並べると、別のプロジェクト専用のタグが混ざり、 選んでも常に0件になる選択肢が並ぶ。

選べるタグは一つだけである。二つ選んで「両方に付いているもの」を出す形は入れていない。 タグを重ねて絞りたくなるほど数が増えたときに考えることで、 いま入れると、使われないまま選択肢が複雑になる。

行に出るタグは三つまでで、四つ目からは +2 のように数だけになる。 全部並べると、タグの多いスレッドの行だけが折り返して高さが変わる。

アーカイブと削除

アーカイブしたスレッドは読み取り専用になる。 新しいコメントも、子スレッドの追加もできない。

親をアーカイブしても子は連鎖しない。 親が畳まれても、子にはまだ動いているものがありうるからである。 ただし、そのままだと活動中の子が親ごと視界から消える。 そこで、活動中の子を持つアーカイブ済みスレッドは一覧に読み取り専用として出す。 上の見本の4行目がその状態にあたる。

削除は論理削除で、組織管理者だけが行える。 アーカイブを経ていないスレッドは削除できない。レコードは残るので番号は欠番のまま保たれる。

詳細画面で削除の欄が出るのも、その二つが揃ったときだけである。 畳んでいないスレッドでは、欄そのものを出さない。 押せない押しボタンを見せて断るより、出さないほうがいい （UI設計方針）。 条件にプロジェクト側のアーカイブは入らない。畳んだプロジェクトの中でも、畳んだスレッドは消せる。

誰が何をできるか

スレッドについては、見えている人は書ける。 立てることも、本文を直すことも、進捗率や担当者や期間を変えることも、畳むことも、 そのプロジェクトを閲覧できる人なら誰でも行える。

作成者や担当者だけに絞る案もあった。 絞らなかったのは、履歴を残さない設計と噛み合わないからである。 担当者が休んでいるあいだに締切だけ動かしたい、という場面で手が止まる。 そして荒れることへの備えは、権限ではなく編集済みの印と通知の側に置いた。

質問という種別を用意しておきながら、 質問を立てられない人が組織にいる、という状態も避けたかった。

削除だけ線が違う。 論理削除はどのテーブルでも組織管理者に寄せてあり、 辿れるものが消える操作を、この機能でだけ広げる理由がない。

閲覧の判定を書けるかの判定に使っている

「見えている人は書ける」は実装の手抜きではなく、そう決めた線である。 ただし判定そのものは画面に置いていない。 書き込みの SQL は毎回、閲覧できるプロジェクトかどうかを条件に含めている。 畳んだスレッドと、畳んだプロジェクトの中身も同じ条件で止める。

本文の編集

タイトルと本文は編集できる。履歴は残さず、印と最終更新日時だけを出す。

これはコメントとは逆の扱いである。 コメントは「その時点の発言」なので不変にした。 本文は「現在の課題の定義」なので、調査が進めば書き換わってよい。

ただし本文が黙って書き換わると、それを前提に書かれたコメントが宙に浮く。 編集済みの印は、その食い違いに気づくための最低限の手がかりとして置いている。

印が付くのは本文だけである

タイトルを直しても付かない。画面の表示も「本文編集済み」である。

誤字を一文字直しただけで印が付くと、それを見た人は、 並んでいるコメントが古い本文に向けられていないかを毎回疑うことになる。 印は食い違いを知らせるためのものなので、食い違わない変更で押すと、印そのものが働かなくなる。 本文のチェックボックスで押さないのも、同じ理由による。

2026-09-09 より前に付いた印には、タイトルだけの変更で付いたものが混ざっている。 どちらの理由で付いたかは記録していないので、遡っては直せない。

書き換える欄は、対象の隣にある

タイトルは見出しの隣、本文は本文の直下に「編集」がある。 押すと、その位置の読み表示が入力欄に入れ替わる。

以前は詳細画面の下端に「タイトルと本文を書き換える」という欄が一つあった。 畳んであること自体は正しい。この画面の主役は読むことで、書き換えは時々である。 遠かったのは入口ではなく、入口と対象の距離のほうだった。 タイトルは画面の上端にあり、それを直す欄は最下部にある。 途中に何を挟んでも、その二つは離れたままになる。

入れ替えは details と CSS で行う。 JavaScript が動かなくても入口は働く。

本文は Markdown で書ける。 見出し、箇条書き、表、コードブロック、リンク、引用。 解釈と無害化はコメントと同じ仕組みを通る。

本文にメンションは書けない

@佐藤 明日香 と書いても、ただの文字として出る。 メンションが使えるのはコメントの中だけである。

通知はコメントに紐づく形でしか作れない （notifications の制約がそうなっている）。 加えて本文は編集できるので、仮に飛ばすとすると、 保存のたびに飛ぶのか、書き換えて消したら取り消すのかまで決めることになる。 色だけ付けて通知を飛ばさない形にすると、指名したつもりの人が気づかれないまま残る。

チェックボックスは押せる

- [ ] やること と書くと、押せる箱が出る。 押せるのは、そのプロジェクトを閲覧できる人なら誰でもである。

押すと本文そのものが書き換わる（[ ] が [x] になる）。 本文は編集できるものなので、状態を本文に書いても筋は通る。 コメント側は事情が違い、そちらは別のテーブルに置いてある。

チェックだけでは「編集済み」にならない

文字としては本文が書き換わるが、印は付けない。

印は「課題の定義が変わって、それを前提に書かれたコメントが宙に浮いた」ことを知らせるものである。 項目はもとから並んでいて、終わったかどうかだけが動く。 ここで印が付けば、チェックリストを持つスレッドが例外なく「編集済み」になり、 印が何も伝えなくなる。

二人が同時に別々の箱を押しても、片方が消えることはない。 本文を丸ごと組み立て直すのではなく、行を押さえてから、その箱の三文字だけを差し替えている。
