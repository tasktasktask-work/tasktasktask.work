Feature 04

スレッド

課題管理ツールの多くは「課題」を基本単位に置く。 そして議論はその付属物として、コメント欄の中に押し込まれる。 ここでは順序を逆にした。基本単位はスレッドであり、課題はその種別のひとつでしかない。

なぜ課題を基本単位にしなかったか

開発の現場で交わされる話は、最初から課題の形をしていない。 「検索の要件、どうしますか」という相談には、まだ実装のゴールがない。 「全角の正規化はどこでやってますか」という疑問には、そもそも作業が伴わない。

これらを課題として登録すると、いつまでも閉じない課題が一覧に溜まる。 かといってチャットへ流すと、決まったことが記録に残らない。

そこで、置き場所そのものを用意した。 スレッドという共通の器があり、その種別として課題と議論と質問が並ぶ。 三つとも同じ形なので、同じ一覧に出て、同じように親子でつながる。

三つの種別

種別バッジThreadTypeBadge
課題type = kadai
議論type = giron
質問type = shitsumon
種別意味進捗率期間ガント
課題 やることが決まっていて、終わりの形が言える 0から100持つ載る
議論 関係者で決めなければ終わらない相談 0か100持たない載らない
質問 知っている人がいれば終わる疑問 0か100持たない載らない

種別は後から変更できない。 議論として立てたスレッドを課題に作り変えることはできず、課題のスレッドを別に立てることになる。 そのとき二つをつなぐ手段は親子関係だけである。 議論を親、課題を子にすれば、「この課題はどの議論から出てきたのか」を辿れる。

この経路しかない

議論と、そこから生まれた課題を結びつける方法は親子関係だけである。 親子をつけ忘れると、両者の関係は失われる。 議論をクローズするときに子の課題が一つもなければ注意を出す、といった補助は初期リリースに含めていない。

進捗率

状態を表す欄は進捗率ひとつしかない。 0が未着手、100が完了、その間が進行中である。 議論と質問では0と100しか取らず、画面ではオープンとクローズと呼ぶ。

進捗表示ProgressMeter / OpenCloseBadge
0% 課題 / 未着手
40% 課題 / 進行中
100% 課題 / 完了
オープン議論と質問 / 0
クローズ議論と質問 / 100

値は担当者が自分で入力する。1刻みで自由に入れられるが、入力欄には <datalist> で0、25、50、75、100の候補を出す。 自由入力を残しつつ、よく使う値を一手で選べるようにするためである。

進捗率だけで表せないもの

「やらないと決めた課題」と「まだ手をつけていない課題」は、どちらも0のまま並ぶ。 「レビュー中」のような工程も数値では表せない。 どう扱うかは各組織の運用に委ねる方針を取った。 アーカイブするか、100にするか、タグで示すか。 この判断が組織ごとにばらつくことは承知のうえで、経緯を却下の表現に記録している。

親子関係

スレッドの下にスレッドをぶら下げられる。深さの制限はない。

  • 種別はまたげる。議論の子に課題、課題の子に質問を置ける
  • プロジェクトはまたげない。親と子は必ず同じプロジェクトに属する
  • 集計はしない。親の進捗率も期間も、子とは独立して人が入力する

親の期間を子から自動計算しない理由は、親が固有の締切を持てなくなるからである。 「この塊は7月末まで」という計画は、子の日付の最大値とは別の情報である。 子がそこからはみ出したときははみ出し警告を出すが、値の書き換えはしない。 どう直すかは人が決める。

識別子

スレッド番号は組織の中で通し番号になっている。 表示はプロジェクトキーを前に付けて WEB-128 の形になる。

プロジェクトごとに1から振らないため、一つのプロジェクトだけを見ると番号が飛ぶ。 WEB-3 の次が WEB-7 になるのは正常な状態である。 番号が同じスレッドが別プロジェクトに存在しない、という性質を優先した。

担当者

ひとつのスレッドに担当者はひとりだけ置ける。未設定でもよい。 複数人を割り当てられるようにはしていない。全員が自分の仕事ではないと思う状態を避けるためである。

担当者に設定されると通知が飛ぶ。 また担当スレッド一覧では、この人の名前でプロジェクトをまたいでスレッドが集まる。

一覧の見え方

スレッド一覧は階層を作らず平らに並べる。 親と子へは、それぞれの行に置いたリンクから辿る。

スレッド行ThreadRow

絞り込みの軸は種別、担当者、タグ、進捗率が100のものを除くかどうか、アーカイブ済みを出すかどうかである。 全文検索を持たないため、この絞り込みが探すための唯一の手段になる。 既定の並び順は更新の新しい順とする。

アーカイブと削除

アーカイブしたスレッドは読み取り専用になる。 新しいコメントも、子スレッドの追加もできない。

親をアーカイブしても子は連鎖しない。 親が畳まれても、子にはまだ動いているものがありうるからである。 ただし、そのままだと活動中の子が親ごと視界から消える。 そこで、活動中の子を持つアーカイブ済みスレッドは一覧に読み取り専用として出す。 上の見本の4行目がその状態にあたる。

削除は論理削除で、組織管理者だけが行える。 アーカイブを経ていないスレッドは削除できない。レコードは残るので番号は欠番のまま保たれる。

本文の編集

タイトルと本文は編集できる。履歴は残さず、「編集済み」の印と最終更新日時だけを出す。

これはコメントとは逆の扱いである。 コメントは「その時点の発言」なので不変にした。 本文は「現在の課題の定義」なので、調査が進めば書き換わってよい。

ただし本文が黙って書き換わると、それを前提に書かれたコメントが宙に浮く。 編集済みの印は、その食い違いに気づくための最低限の手がかりとして置いている。
