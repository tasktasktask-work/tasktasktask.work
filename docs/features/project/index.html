Feature 03

プロジェクト

プロジェクトはスレッドを入れる箱である。 ただの箱ではない。ガントが一枚に描く範囲、メンションの候補に出る人の範囲、閲覧できる人の範囲。 このシステムのいくつもの境界が、同じ一本の線で引かれている。

境界としてのプロジェクト

プロジェクトが引く線を並べると、それが単なる分類でないことがわかる。

何の境界か意味
閲覧範囲非公開に設定すると、メンバーと組織管理者しか見られない
ガントの範囲ガントチャートはプロジェクト一つぶんを一枚に描く
メンションの候補そのプロジェクトを閲覧できる人だけが候補に出る
親子関係の範囲親と子は必ず同じプロジェクトに属する

作れるのは組織管理者だけ

プロジェクトを作れるのは組織管理者である。 作った人は、そのままプロジェクト管理者として登録される。

公開で作った場合でも登録する。 非公開へ切り替えた瞬間に、誰も入っていないプロジェクトができるのを避けるためである。

公開と非公開

公開プロジェクトは組織のメンバー全員が見られる。 非公開プロジェクトは、メンバーに加えられた人と組織管理者だけが見られる。 設定は後から切り替えられる。

非公開から公開への切り替えには確認をはさむ。 戻すことはできても、見られた事実は戻せないからである。

プロジェクト管理者

ひとつのプロジェクトの面倒を見る人をプロジェクト管理者と呼ぶ。 非公開プロジェクトのメンバーを追加したり外したりでき、名前と説明文、公開設定、アーカイブも変えられる。 スレッドの操作について一般メンバーとの差はない。

プロジェクトを作った組織管理者が自動的に管理者になる。 加えて、すべての組織管理者が全プロジェクトの管理者として扱われる。 メンバーが退職者しかいないプロジェクトを引き継げなくなる事態を避けるためである。

できないのは削除だけである。 論理削除はどのテーブルでも組織管理者に寄せてあり、 プロジェクトだけを例外にしていない。

公開設定まで任せてあるのは、この人がすでに非公開の顔ぶれを決められるからである。 組織のメンバーを一人ずつ足していけば、公開に切り替えたのとほぼ同じ状態を作れる。 切り替えだけを止めても守りにはならず、手間が増えるだけになる。

プロジェクトを回している人が、終わったものを自分で畳めず、 名前の誤りも直せないのでは、この役を置いた意味がない。

最後のプロジェクト管理者を守る仕掛けは要らない。 行が一本も無くなっても、組織管理者が管理者として扱われるので、 そのプロジェクトが誰にも触れなくなることはない。 組織管理者のほうに下限があるのは、 そちらには外側からの受け皿が無いからである。

公開プロジェクトでも、顔ぶれは揃えられる

メンバーの一覧は、公開プロジェクトでも開けて、足したり外したりできる。 公開のあいだ、この一覧は閲覧の範囲を変えない。 非公開に切り替えたときに効きはじめる。

切り替えてから慌てて人を入れる順にすると、 誰も入っていない非公開プロジェクトができる時間が生まれる。 先に揃えられるようにしてある。

組織から外れたら、何も見えない

閲覧の判定はまず組織の所属を見る。 所属が切れていれば、プロジェクトのメンバー行が残っていても 非公開プロジェクトは見えない。

組織からメンバーを外すとき、プロジェクト側の行まで消し忘れることはありうる。 そこに頼らずに済ませている。 判定の詳細を参照。

プロジェクトキー

半角の英大文字と数字で2文字から10文字。組織の中で重複しない。 スレッド識別子の前半になる。

後から変更できない。 WEB-128 として議事録やコミットメッセージに書かれたものが、ある日から FRONT-128 になると、過去の記録との照合ができなくなる。

キーが変わっても壊れない部分

スレッド番号は組織の中で通し番号になっている。 つまり 128 という数字だけでスレッドは一意に定まり、キーは表示のための飾りにすぎない。 そのため技術的には変更しても壊れないが、人の記憶と記録が壊れるので許可しない。

プロジェクトが持つもの

項目内容
名前画面に出る名称。変更できる
キー2から10文字。作成後は変更できない
説明文何のためのプロジェクトかを書く。変更できる
公開設定公開か非公開。切り替えられる
アーカイブ状態畳んだかどうか

期間は持たない。 プロジェクトの期間を知りたければ、中の課題の日付を見ればわかる。 同じ情報を二か所に持つと、必ず食い違う。

アーカイブと削除

プロジェクトをアーカイブすると、配下のスレッドがまとめて読み取り専用になる。 個々のスレッドのアーカイブ状態は書き換えず、プロジェクト単位でまとめて読み取り専用にする。 解除すれば元どおり編集できる。

削除は論理削除で、組織管理者だけが行える。 アーカイブを経ていないプロジェクトは削除できない。

権限は、SQL の中で確かめる

スコープの isOrgAdmin は画面の出し分けにしか使わない。 呼ぶ側は好きな値のスコープを組み立てられるからである。 組織のスコープと同じ扱いになっている。

操作誰がどこで確かめるか
作る組織管理者INSERT … SELECT … WHERE に条件を入れる
名前と説明文を変える組織管理者かプロジェクト管理者UPDATE の WHERE に条件を入れる
公開設定を切り替える組織管理者かプロジェクト管理者同上
アーカイブ組織管理者かプロジェクト管理者同上
メンバーを足す、外す組織管理者かプロジェクト管理者同上
削除組織管理者同上。畳んであることも同時に見る
一覧に並べる、中を開く閲覧できる人VISIBLE_PROJECT_IDS を通す

フォームから届くのは組織の slug とプロジェクトキーだけである。 プロジェクトの id はサーバ側で引き直す。 フォームに書かれた id を信じると、他のプロジェクトの id を差し込むだけで 閲覧の判定を飛び越えられる。

存在しないキーと、見えないプロジェクトを区別しない

どちらも 404 を返す。 分けて答えると、キーを総当たりして非公開プロジェクトの存在を確かめられる。 slug で同じことをしないのと同じ理由による。

移動できないことの帰結

スレッドを別のプロジェクトへ移すことはできない。 置き場所を間違えたら、正しいプロジェクトで立て直し、元のスレッドをアーカイブすることになる。

この制約があるため、プロジェクトをどう切るかは最初に慎重に決める必要がある。 移動を認めるかどうかはスレッドの可変性に記録した。
