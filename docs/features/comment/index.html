Feature 05

コメント

スレッドの下に、投稿順で一本に連なる。枝分かれはしない。 そして一度書いたら、直すことも消すこともできない。 この不便さは、意図して残したものである。

編集も削除もできない

コメントは「その時点で誰が何と言ったか」の記録である。 後から書き換えられると、それを前提に進んだ議論の意味が失われる。

誤字を直したいという要求は当然出る。 それでも不変にしたのは、記録としての価値のほうが上回ると判断したからである。 訂正は、続けてコメントを書いて行う。

PMコメントの誤字を直したいんですが。

開発者直せません。訂正のコメントを続けて書いてもらう形になります。

PM不便ですけど、言った言わないが起きないのは助かりますね。

スレッドの本文は逆に編集できる。 本文は「現在の課題の定義」であり、調査が進めば書き換わってよいものだからである。 性質が違うので、扱いを分けた。

書き方

GitHub Flavored Markdown を使う。 見出し、強調、リスト、リンク、コードブロック、引用、表、 チェックボックスまで通る。 解釈と無害化は streamdown が行う。

生の HTML も通す。<b>太字</b> は太字として出る。 かつては受け付けない方針だった。禁じた理由は 「サニタイズの実装と検証にかかるコストが、得られる表現力に見合わない」ことである。 そのコストを streamdown が引き受けたので、禁じる理由のほうが先に消えた。

危ないものが落ちることは、実際に投げて確かめている

<script> は消える。onerror の付いた画像は差し止められる。 javascript: のリンクは無効になる。 描画の経路には rehype-sanitize と rehype-harden が入っている。

ただし、ここから先の安全は外部のライブラリが握っている。 自前で書いていれば「HTML の文字列を一度も作らない」という形にでき、 無害化の失敗という状態そのものを消せた。そちらは選ばなかった。

二つだけ、書いても効かない書き方がある。<task> と <mention> である。 この二つは、描画の直前にこちらが本文へ埋め込むタグで、 利用者が書いたものと見分けが付かない。 他人を指名したように見せかける文章を作れてしまうので、開き括弧を潰してから渡す。 コードブロックとインラインコードの中は、書いたとおりに出る。

チェックボックスだけは押せる

- [ ] やること と書くと、押せる箱が出る。 コメントは直せないのに、ここだけ動く。

本文には触れていないからである。 押された箱の番号を、別のテーブルが持っている。 コメントの本文は投稿されたときのまま一字も変わらず、 「何番目の箱に、誰が、いつチェックを入れたか」がその隣に並ぶ。

コメントスレッドの本文
状態の置き場所comment_checks の行本文の [x] という文字
本文は変わるか変わらない変わる
誰が入れたか残る残らない
編集済みの印そもそも無い付かない

置き場所が違うのは、直せるかどうかが違うからである。 本文は編集できるので、状態を本文に書いても約束を破らない。 コメントに同じことをすると、updated_at を持たないという comments の作りごと崩れる。

本文のほうで「編集済み」の印を付けないのは、別の理由による。 印は課題の定義が書き換わったことを知らせるものである。 項目はもとから並んでいて、終わったかどうかだけが動く。 ここで印が付けば、チェックリストを持つスレッドが例外なく「編集済み」になり、 印が何も伝えなくなる。

番号で指すことの弱み

本文の中で何番目か、という数え方をしている。 コメントの本文は変わらないので、この番号は永久に同じ箱を指す。

スレッドの本文は編集できるので、そうはいかない。 箱を押している最中に本文から項目が消えると、その操作は断られる。 こちらは本文そのものを書き換える形なので、番号がずれたまま別の箱に入ることはない。

メンション

@ に続けて人を指名すると、その人に通知が飛ぶ。

候補に出るのはプロジェクトを見られる人だけ

非公開プロジェクトのメンバーでない人を指名できると、 閲覧権限のないスレッドの本文を含む通知メールがその人に届く。 非公開という設定が、そこで無効になる。 加えて、開いても中身を見られない通知を受け取るのは体験としても壊れている。

ウォッチが自動で付かない仕様のため、メンションは相手に気づいてもらう主要な手段になる。 誰かに宛てて書くときは指名する、という運用がこの設計の前提である。

どこまでが名前か

@佐藤 明日香 賛成です という文字列から、名前の終わりを見つける手立てが要る。 表示名には空白が入るうえ、一意でもない。ハンドルの列も持っていない。

閲覧できる人の表示名を全部持ってきて、最も長く一致したものを採る。 書き手は何も覚えなくてよい。@ を打つと候補が出るので、そこから選べば確実に入る。

同じ表示名の人が複数いたら、その全員に通知が飛ぶ。 書き手はそのうちの一人を思って書いているが、どちらなのかを機械が決める手立てがない。 候補はもともとそのプロジェクトを閲覧できる人に限られているので、 余分に届いても、見せてはいけないものは見えない。 指名されなかったほうが気づけないより、害が小さいと判断した。

コードの中は拾わない。`@example` は指名ではない。 メールアドレスの途中も拾わない。sato@… の @ は直前が英数字である。

誰を指したかは、投稿した時点で決まる

本文の何文字目から何文字目が誰なのかを、投稿と同じトランザクションで書き留める。 表示のたびに現在の表示名と突き合わせる形は採らない。

表示名は変更できる。突き合わせ方式だと、指名された人が改名した瞬間に過去のコメントの色が消える。 それより悪いのは逆のほうで、別人が「佐藤 明日香」に改名すると、 過去のコメントがその人を指しているように見える。 通知はもとの人に届いているのに、画面上の指名先だけが入れ替わる。

コメントの本文は書き換わらないので、記録した位置は永久に正しい。

誰が何をできるか

スレッドと同じ線を引いた。見えている人は書ける。

操作閲覧できる人組織管理者
読む●●
投稿する●●
チェックボックスを押す●●
直す誰にもできない
消す●

チェックボックスを書いた本人に限らないのは、担当が変わるからである。 書いた人が離れた作業に、永遠にチェックが入らなくなる。

消せるのを組織管理者だけにしたのは、消す場面が限られているためである。 機密情報を貼ってしまった、というような場面で使う。 押す動線はまだ画面に出していない。 そのとき何を確かめさせるかを決めてから出す。

通知

コメントを投稿すると、二種類の通知が立つ。

誰に種類
指名された人mention
そのスレッドをウォッチしている人comment

両方に当たる人には、指名のほうだけを作る。同じコメントで二度知らせても、二度目に新しい情報がない。 自分の投稿で自分に通知は来ない。

宛先は、そのコメントを読めるはずの人に限る。 ウォッチの行は、あとでプロジェクトが見えなくなっても残るからである。 絞り込みは notification 側が持っていて、 投稿の処理はそこを呼ぶだけである。

積んだ行は担当スレッド一覧の隣のタブに並ぶ。 メールの送信だけが、まだ動いていない。

添付

コメントには添付ファイルを付けられる。 画像はコメント本文の中に表示され、それ以外はダウンロードのリンクとして並ぶ。

まだ作っていない

投稿欄に「ファイルを添付」の押しボタンは出していない。 押しても何も起きない札を先に置くと、動かないのか壊れたのかが区別できない。

アーカイブされたスレッドでは書けない

アーカイブされたスレッド、およびアーカイブされたプロジェクトの配下では、新しいコメントを投稿できない。 既存のコメントは読める。チェックボックスも押せなくなる。
