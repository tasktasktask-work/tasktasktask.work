Feature 05

コメント

スレッドの下に、投稿順で一本に連なる。枝分かれはしない。 そして一度書いたら、直すことも消すこともできない。 この不便さは、意図して残したものである。

編集も削除もできない

コメントは「その時点で誰が何と言ったか」の記録である。 後から書き換えられると、それを前提に進んだ議論の意味が失われる。

誤字を直したいという要求は当然出る。 それでも不変にしたのは、記録としての価値のほうが上回ると判断したからである。 訂正は、続けてコメントを書いて行う。

PMコメントの誤字を直したいんですが。

開発者直せません。訂正のコメントを続けて書いてもらう形になります。

PM不便ですけど、言った言わないが起きないのは助かりますね。

スレッドの本文は逆に編集できる。 本文は「現在の課題の定義」であり、調査が進めば書き換わってよいものだからである。 性質が違うので、扱いを分けた。

書き方

GitHub Flavored Markdown 相当の記法を使う。 見出し、強調、リスト、リンク、コードブロック、引用、表、チェックボックスまで。 生のHTMLは受け付けない。

チェックボックスを入れたのは、課題の中の小さな作業を表す手段が要るからである。 これがないと、子課題を立てるほどでもない項目のために子課題が乱立する。

生HTMLを禁じたのは、サニタイズの実装と検証にかかるコストが、得られる表現力に見合わないためである。

メンション

@ に続けて人を指名すると、その人に通知が飛ぶ。

候補に出るのはプロジェクトを見られる人だけ

非公開プロジェクトのメンバーでない人を指名できると、 閲覧権限のないスレッドの本文を含む通知メールがその人に届く。 非公開という設定が、そこで無効になる。 加えて、開いても中身を見られない通知を受け取るのは体験としても壊れている。

ウォッチが自動で付かない仕様のため、メンションは相手に気づいてもらう主要な手段になる。 誰かに宛てて書くときは指名する、という運用がこの設計の前提である。

添付

コメントには添付ファイルを付けられる。 画像はコメント本文の中に表示され、それ以外はダウンロードのリンクとして並ぶ。

アーカイブされたスレッドでは書けない

アーカイブされたスレッド、およびアーカイブされたプロジェクトの配下では、新しいコメントを投稿できない。 既存のコメントは読める。
