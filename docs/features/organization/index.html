Feature 02

組織とメンバー

複数の会社が同じシステムを使う。 ひとりが二つの会社に関わることもある。 そのどちらも当たり前に起きるという前提から、この機能の形は決まった。

組織はデータの境界である

組織は分類のラベルではない。 ユーザーもプロジェクトもスレッドもタグも、すべてがいずれかの組織に属し、組織をまたいで参照されることがない。 クエリの条件から組織を落とすと、他社のデータが混ざる。 そのため、あらゆるテーブルに organization_id を置く。

ひとりが複数の組織に所属する

業務委託で二社に関わる人や、事業部をまたぐ人は実際にいる。 そのためユーザーと組織の関係は多対多にする。

この決定は画面のURLに影響する。 どの組織を見ているかがURLからわからないと、二つのタブを開いている人が必ず取り違える。 そこで組織ごとに slug を持たせ、/o/{slug}/... の形で常にURLへ含める。

役割は二段だけ

役割できること
組織管理者 組織設定の変更、メンバーの招待と削除、プロジェクトの作成と削除、非公開プロジェクトの閲覧、論理削除と復元、アカウントロックの手動解除、支払い方法の登録と変更
組織メンバー 公開プロジェクトの閲覧と編集、参加している非公開プロジェクトの閲覧と編集、スレッドとコメントの作成

組織管理者は複数人置ける。 ひとりに限ると、その人が退職したりアカウントを失った時点で、組織そのものが操作不能になる。

「ゲスト」のような第三の役割は用意しない。 外部の人に一部だけ見せたい場合は、非公開プロジェクトで代替する。

支払いのための役割も作らなかった。 請求担当を別に置くと role の意味が増え、招待とメンバー管理の画面すべてに影響する。 凍結された組織で支払いに進めるのは組織管理者だけで、 それ以外のメンバーには管理者へ連絡を促す案内が出る。 詳しくは課金にある。

参加は招待だけ

組織管理者がメールアドレスを指定して招待を送る。 受け取った人はリンクからパスワードを設定して登録する。 リンクは48時間で切れる。

メールドメインによる自動参加は用意しない。 @example.com のアドレスを持つ人が全員そのまま入れる仕組みは、 退職者のアカウントが生きている間ずっと入り続けられることを意味する。

既存の組織に入る手段はこれだけである。 自分で組織を作る経路は、入る先を新しく作るものであって、 すでにある組織へ入る手段ではない。

組織が持つ設定

項目内容初期リリース
名前画面に出る組織名あり
slugURLに含まれる識別子。組織をまたいで一意あり
言語画面表示の言語日本語のみ
タイムゾーン日時の表示に使うJSTのみ

言語とタイムゾーンは、値としては最初から持つ。 選べる値が一つしかなくても、列とインタフェースを後から足すほうが高くつくからである。 実際に複数の値を扱えるようにする作業は多言語対応に送った。

組織を作る

組織は/signup から作る。 作った人がその組織の最初の組織管理者になり、そのままログイン状態で /o/{slug} へ着く。

ログインしていない人は、先にメールアドレスの確認を通る。 アドレスを入れると確認のリンクが飛び、そのリンクの先で組織名と slug を決める。 organizations の行が生まれるのはこの瞬間である。 確認より前に組織を作らないので、「まだ確認されていない組織」を掃除する仕組みが要らない。

すでにログインしている人には、確認を求めない。 そのアドレスはログインできている時点で確認済みであり、もう一度踏ませても確かめられることが増えない。 組織名と slug だけで、その場で作る。

slug は早い者勝ちで、あとから変えられない

slug は人が決める。 小文字の英数字とハイフン、3文字から40文字。 すでに使われている名前と、admin や login のような予約語は断る。

予約語はアプリケーション側で持ち、データベースの制約にはしない。 制約に入れると、語をひとつ足すたびに移行が積まれる。 そのうえ、すでに使われている語を後から予約語にできなくなる。 既存の行が制約に違反するためである。

作成後の変更は用意しない。 変えると、その組織のURLを指すリンクとブックマークが全部切れる。 必要になったときは、移行の手順を含めて別に決める。

手元から作る道も残す

pnpm org:create --name "株式会社アクメ" --slug acme \
                --admin someone@example.com --admin-name "佐藤 明日香"

組織と、組織管理者としての所属と、ログイン用リンクを作って出力する。 画面の経路がメールの到達に依存するのに対し、こちらは依存しない。 送信が止まっている環境でも組織を作れる道として残してある。

slug の検証は画面と共有する。 分けて持つと、片方にだけ予約語が増えた日から、CLI からは admin が通る。

組織のスコープ

組織はデータの境界なので、条件から organization_id が落ちれば他社のデータが混ざる。 「書き忘れないようにする」では守れないため、書かなければ何も引けない形にしてある。

/o/{slug}/... のページは、まず URL の slug から 組織のスコープを組み立てる。 データにさわる関数はすべてこれを第一引数に取るので、 スコープが取れなければその先へ進めない。

存在しない slug と、所属していない組織を区別しない

どちらも 404 を返す。 「その組織はあるが、あなたは所属していない」と答えると、 slug を総当たりして他社の存在と名前を確かめられる。

未ログインのときは、そのURLのままログイン画面を出す。 /login へは送らない。

権限は、SQL の中で確かめる

スコープには isOrgAdmin が入っているが、 これは画面の出し分けにしか使わない。 呼ぶ側は好きな値のスコープを組み立てられるからである。

操作どこで確かめるか
招待を送る、取り消すSQL の中で組織管理者かどうかを見る
役割を変える、メンバーを外す掴んだ管理者の行に自分がいるかで見る
組織名を変えるUPDATE の WHERE に条件を入れる
メンバーのメールアドレスCASE WHEN で出し分ける

メールアドレスを組織管理者にしか返さないのは、 招待の重複や、誰を外すのかを確かめるのに要るのが管理する側だけだからである。 他のメンバーには表示名と役割があれば足りる。

最後の組織管理者は降ろせない

組織管理者がいなくなると、その組織は設定もメンバーも触れなくなる。 中の誰にも戻す手段がない。

行数の下限は CHECK で書けないので、アプリケーション側で守る。 素朴に数えると、二人の管理者が同時に互いを降ろしたときに抜ける。 どちらも「自分のほかにもう一人いる」と読むためである。

SELECT user_id
  FROM organization_members
 WHERE organization_id = $1 AND role = 'admin' AND deleted_at IS NULL
 ORDER BY user_id
   FOR UPDATE

先に管理者の行を掴んでから数える。 二つめの要求は、一つめが終わるまで待つ。 管理者が増える側は待たせない。増えるぶんには下限を割らないためである。

招待を受けるとき

招待リンクは、招待されたメールボックスにしか届かない。 開けたこと自体が、そのアドレスの持ち主である証拠になる。 マジックリンクと同じ性質なので、有効期間も48時間で揃えてある。

状況することと、しないこと
アカウントが無い表示名とパスワードを訊いて作る
アカウントがあるパスワードも表示名も訊かない。所属を足すだけ
ロックされているロックを解く。マジックリンクと同じ扱いにする
一度外れた人畳んだ行は起こさず、新しい行を足す
すでにアカウントがある人には、パスワードを訊かない

訊いて上書きできると、招待リンクを踏ませるだけで他人のパスワードを書き換えられる。 受諾したときに変わるのは、所属と、ロックの状態と、ログイン中のアカウントだけである。

受諾の画面は、開いただけでは何も変えない。 リンクを先読みするメールソフトに、勝手に受諾させないためである。

受諾すると、別のアカウントでログインしていても招待された側へ切り替わる。 一度外れた人を呼び戻したときは、畳んである行を起こさずに新しい行を足す。 入って抜けてを繰り返した人には畳んだ行が何本も並んでいて、 まとめて起こすと生きた行が二本になるためである。

メンバーを外すと何が起きるか

所属を切れば、その組織の何も見えなくなる。 閲覧できるプロジェクトの判定が、 所属をいちばん外側で確かめているためである。

それでも project_members の行を一緒に畳んでいる。 意味を失った行を残さないためで、権限のためではない。 権限が行の後片付けに依存する形は、 一度そこで漏れを作っている。
