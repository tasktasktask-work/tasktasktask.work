Feature 02

組織とメンバー

複数の会社が同じシステムを使う。 ひとりが二つの会社に関わることもある。 そのどちらも当たり前に起きるという前提から、この機能の形は決まった。

組織はデータの境界である

組織は分類のラベルではない。 ユーザーもプロジェクトもスレッドもタグも、すべてがいずれかの組織に属し、組織をまたいで参照されることがない。 クエリの条件から組織を落とすと、他社のデータが混ざる。 そのため、あらゆるテーブルに organization_id を置く。

ひとりが複数の組織に所属する

業務委託で二社に関わる人や、事業部をまたぐ人は実際にいる。 そのためユーザーと組織の関係は多対多にする。

この決定は画面のURLに影響する。 どの組織を見ているかがURLからわからないと、二つのタブを開いている人が必ず取り違える。 そこで組織ごとに slug を持たせ、/o/{slug}/... の形で常にURLへ含める。

役割は二段だけ

役割できること
組織管理者 組織設定の変更、メンバーの招待と削除、プロジェクトの作成と削除、非公開プロジェクトの閲覧、論理削除と復元、アカウントロックの手動解除
組織メンバー 公開プロジェクトの閲覧と編集、参加している非公開プロジェクトの閲覧と編集、スレッドとコメントの作成

組織管理者は複数人置ける。 ひとりに限ると、その人が退職したりアカウントを失った時点で、組織そのものが操作不能になる。

「ゲスト」のような第三の役割は用意しない。 外部の人に一部だけ見せたい場合は、非公開プロジェクトで代替する。

参加は招待だけ

組織管理者がメールアドレスを指定して招待を送る。 受け取った人はリンクからパスワードを設定して登録する。 リンクは48時間で切れる。

メールドメインによる自動参加は用意しない。 @example.com のアドレスを持つ人が全員そのまま入れる仕組みは、 退職者のアカウントが生きている間ずっと入り続けられることを意味する。

組織が持つ設定

項目内容初期リリース
名前画面に出る組織名あり
slugURLに含まれる識別子。組織をまたいで一意あり
言語画面表示の言語日本語のみ
タイムゾーン日時の表示に使うJSTのみ

言語とタイムゾーンは、値としては最初から持つ。 選べる値が一つしかなくても、列とインタフェースを後から足すほうが高くつくからである。 実際に複数の値を扱えるようにする作業は多言語対応に送った。
