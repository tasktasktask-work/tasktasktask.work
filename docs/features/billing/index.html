Feature 11

課金

組織ごとに、人数ぶんの月額を後払いで、USD で受け取る。 払わない組織は書き込みだけが止まり、中身は見え続ける。 この二つの決定から、あとの形はほとんど決まった。

組織の状態は四つ

課金から見ると、組織は四つの状態のどれかにいる。 どの状態にいるかは列に書き込まず、リクエストのたびに計算する。 日付が変わった瞬間に凍結してほしいので、日次で状態を更新する形は採らなかった。

課金免除 ── CLI でのみ出入りする。請求も凍結も行わない

課金免除は他の三つと同じ平面には無い。 他の状態を上書きする印で、社内で使う組織、デモ用の組織、支払いの取り決めが特殊な相手に必ず要る。 画面からは操作できず、pnpm org:exempt と pnpm org:unexempt でだけ切り替える。

おためし期間は翌月末で切る

おためし期間は、組織を作った日から翌月末までである。 9月9日に作った組織なら10月31日まで、9月30日に作った組織も10月31日まで。 登録日によって長さが21日から61日まで変わるが、そこは受け入れた。

長さを揃えるより、終わりを月末に揃えるほうが後段が楽になる。 終わりが月末なら、最初の課金対象月が月単位できれいに決まるからである。 10月31日に終わるなら、最初の課金対象月は11月、最初の請求は12月1日。 月の途中で終わると、その月を請求するかどうかという判断が毎回発生する。

おためし期間中でも支払い方法は登録できる。 早く登録しても課金の開始は早まらない。

課金人数は、その月に在籍した実人数

請求の根拠になる数を課金人数と呼ぶ。 対象月のあいだに一度でも在籍した人を、ひとり1と数える。

月の途中で増えた人も、去った人も、その月はまるごと課金する。 日割りをしない代わりに、増減のどちらも同じ扱いにした。 按分を入れると、請求額の内訳を説明するために在籍日数の一覧が必要になる。

招待を送っただけの人は数えない。 受諾して organization_members に行ができたときに、はじめて一人になる。

SELECT count(DISTINCT m.user_id)
  FROM organization_members m
 WHERE m.organization_id = $1
   AND m.created_at < $3                                -- 翌月1日 0:00
   AND (m.deleted_at IS NULL OR m.deleted_at >= $2)     -- 対象月1日 0:00

境界の日時は組織のタイムゾーンで作る。 DISTINCT が要るのは、抜けてから戻った人が行を二つ持つためである。 招待の受諾は畳んだ行を起こさず、新しい行を足す作りになっている。

数え直さない

この式は過去を数えられるが、請求のたびに走らせることはしない。 走らせると、確定した請求の正しさが「過去の行が二度と動かないこと」に依存する。 数えた結果は請求明細（billing_invoices）に焼き、 誰を数えたかは対象者の行に残す。 人が抜けたあとも、当時の表示名のまま明細に並ぶ。

凍結は組織まるごとの読み取り専用

凍結された組織では、読み取りがすべて生き、書き込みがすべて止まる。 例外は支払いの設定だけである。

既読もチェックボックスもウォッチも、読むための操作でありながら実装は書き込みである。 例外に加えると、次にメンバーの削除を加えたくなり、線を引く場所が無くなる。 そのため止める側に置いた。凍結中の組織では、通知が未読のまま溜まる。

メンバーの削除を止めても人質にはならない。 凍結している間は請求そのものが止まっているので、人数を減らして請求を抑える必要がないからである。

添付のダウンロードを残したのは、持ち出せる状態を保つためである。 中身を見られないまま支払いを迫る形にはしない。

判定を入れる場所は二つ

ひとつめは currentScope() である。 /o/{slug}/ 配下のすべてのページと、組織スコープを要する Server Action が、例外なくここを通る。 ここで組織の課金状態を解決し、OrgScope に frozen として載せる。 画面はこの値で書き込みの入口を消し、Server Action は早い段階で断る。

ふたつめが SQL の中である。 OrgScope は呼び出し側で組み立てられるので、書き込みの側はその値を信用しない。 この方針はコーディング規約にすでにある。

-- src/lib/db.ts に置く断片
export const ORG_NOT_FROZEN = `NOT EXISTS (
  SELECT 1 FROM organizations fo
   WHERE fo.id = $1
     AND fo.billing_exempt = false
     AND fo.trial_ends_on < (now() AT TIME ZONE fo.timezone)::date
     AND (fo.payment_method_set_at IS NULL
          OR EXISTS (SELECT 1 FROM billing_invoices bi
                      WHERE bi.organization_id = fo.id
                        AND bi.status = 'unpaid')))`;

スレッド、コメント、タグの付与、添付は THREAD_WRITABLE という条件を共有しているので、 そこへ AND で足せば四つの機能に一度に効く。 プロジェクト、タグの定義、メンバー、組織設定、通知、ウォッチは別の SQL なので、それぞれに足す。

アーカイブとは別のもの

アーカイブも読み取り専用にする仕組みだが、掛かる粒度が違う。 アーカイブはスレッドとプロジェクトに掛かり、凍結は組織に掛かる。 理由も違う。アーカイブは終わったものを畳む操作で、凍結は支払いが済んでいない状態の表示である。 同じ「読み取り専用」でも、別の語で呼び分ける。

請求は毎月1日に、こちらが作る

Stripe には顧客と支払い方法だけを預ける。 サブスクリプションは使わない。

使えない理由は座席数の扱いにある。 サブスクリプションの座席数は請求時点の値で課金されるので、 月の途中で10人から8人に減った組織は8人分になる。 日割りを切っても、最後に残った数が請求額を決めるという点は変わらない。 月の途中で去った二人ぶんを取る方法が無い。

そこで月が変わったら、前月分の請求書をこちらで作って確定させる。 日付の境目は日本標準時に固定する。 請求は事業者側の暦で切るものなので、組織のタイムゾーンによって締め日がずれる形にはしない。

巡回は日で区切らない。 「1日に走らせる」形にすると、その日にアプリが落ちていた月だけ請求が飛ぶ。 対象月はいつ走らせても前月なので、月が変わってから最初の一巡が請求を立て、 二巡目以降は選ぶ組織が 0 件になる。

5分ごとの巡回（対象月は常に前月。JST）
  │
  ├─ 対象の組織を選ぶ
  │    課金免除でない
  │    trial_ends_on が対象月の1日より前   ← おためし終了月の翌月以降
  │    いま凍結していない                  ← 請求日の一点で判定する
  │    その月の請求明細がまだ無い          ← 二度目以降は 0 件になる
  │
  ├─ 課金人数を数え、billing_invoices に行を作る（status = pending）
  │    UNIQUE (organization_id, billing_month) が二重作成を防ぐ
  │
  ├─ 対象者を billing_invoice_members へ焼く（user_id と当時の表示名）
  │
  └─ Stripe の請求書を作って確定する（冪等キー billing:{org}:{YYYY-MM}）
       status = open。税額を別に足さないので、金額はここで確定する

詰まった請求を作り直す

決済代行に載せられなかった請求は pending のまま残り、次の巡回がもう一度試す。 相手が一時的に落ちていただけなら、それで通る。

通らないのは、渡した内容そのものが間違っている場合である。 そのときは行を作り直すしかない。 冪等キーを請求の行の id から作っているためで、 同じ行で作り直しても、決済代行は前回と同じ請求書を返してくる（キーは24時間覚えられている）。 内容を直して送っても、返ってくるものは変わらない。

-- 詰まった行と、その内訳を消す。次の巡回が新しい id で作り直す
DELETE FROM billing_invoice_members
 WHERE billing_invoice_id IN (SELECT id FROM billing_invoices WHERE status = 'pending');
DELETE FROM billing_invoices WHERE status = 'pending';

消してよいのは pending だけである。 この状態の行は決済代行に載っていないので、消しても請求の記録は失われない。 決済代行の側に残った下書きは、そのまま置いても課金されない。

一本が詰まっても、巡回そのものは止まらない。 一件ずつ守ってあるので、後ろに並んでいる組織の請求は立つ。 詰まった数は巡回の記録に「詰まり」として出る。

手で一度だけ回すこともできる（pnpm billing:run）。 普段は要らないが、決済代行と繋いだ直後の疎通を確かめるときと、 アプリが長く落ちていたあとに待たずに追いつかせたいときに使う。 何度打っても、同じ月の請求は一本しか立たない。

途中で落ちても壊れないようにしてある。 行だけできて Stripe の請求書ができていない状態は status = 'pending' として残り、 次の実行がその行を拾って続きから進める。 同じ月を二度処理しても、請求は一本しか立たない。

請求日の一点だけで判定する

凍結は日単位で始まって日単位で解けるのに、請求は月まるごとかゼロかである。 この二つを噛み合わせるために、判定する時点を請求日の一点に決めた。

請求日に凍結していなければ、その月を満額で請求する

おためし期間が10月31日に終わり、11月1日に凍結。11月15日にカードを登録して解除。

12月1日の請求日に凍結していないので、11月分を満額（11月の課金人数×$1.00）請求する。 前半14日ぶんは差し引かない。

12月1日も凍結したままなら、11月分は作らない。あとから遡って請求することもない。

毎月末にカードを外せば請求日に凍結していることになり、実質ずっと無料で使える。 外しているあいだ書き込みが全部止まるので、単価 $1.00 のためにこれを毎月繰り返す動機は薄いと判断した。

金額

項目値
単価税込 $1.00 / 人 / 月
請求額課金人数 × $1.00
消費税別に取らない。単価そのものが税込である
通貨USD。どの国の組織からも同じ通貨で受け取る
保存の単位セントの整数。100 が $1.00

税額を別に取らないのは、適格請求書発行事業者の登録をしていないためである。 納めていない税を税として請求する形にはしない。 そのため Stripe Tax は使わず、請求書にも消費税額の行が出ない。

買い手の側は、この請求書では仕入税額控除を全額は受けられない。 経過措置で 2029年9月30日 までは一部が控除でき、その割合は下がっていく。 ただし 10人の組織でも月 $10 の取引なので、控除しそこねる額は月あたり数十円である。

金額はセントの整数で持つ。USD は小数を二桁持つ通貨で、 Stripe に渡す金額もセント単位である。 円のような小数を持たない通貨とは、同じ 100 でも意味が違う。

請求先の住所は、税の計算に要らなくなった今も集めている。 請求書の宛先になり、カード会社の不正検知にも効くためである。

支払い方法と、失敗したときの道

カード番号がこちらのフォームを通る設計は採らない。 登録も変更も Stripe の画面へ送る。

操作行き先戻り
はじめて登録するStripe Checkout（住所の入力を含む）/o/{slug}/billing?checkout=done
カードや住所を変えるStripe Customer Portal/o/{slug}/billing

Checkout は mode: 'setup' で開く。ここでは課金せず、カードを預かるだけである。 アカウントで Managed Payments が有効だとこの mode が弾かれるので、 リクエストごとに切ってある。

登録の完了は Checkout からの戻りでその場で確かめ、payment_method_set_at を立てる。 このとき SetupIntent でカードが実際に使えることも確認する。 おためし期間が翌月末まである以上、登録から最初の請求まで1ヶ月以上空くことがあり、 そのあいだ使えないカードを預かったまま気づかない状態を避けるためである。

Stripe に自動で追いかけさせない。 1回目の失敗で凍結すると決めたので、数日後に勝手に再試行が成功すると、凍結だけが取り残される。 請求書を auto_advance: false で作り、決済をこちらから一度だけ呼ぶことで、 その経路に入らないようにしてある。ダッシュボード側の設定に依らない。

請求に失敗した組織は即座に凍結する。 失敗した請求は unpaid のまま残り、これが凍結の理由であり続ける。 管理者が新しいカードを登録すると、まずその未払いを決済する。 成功すれば凍結が解け、失敗すれば凍結のままである。

凍結の解け方が二つある形になる。 支払い方法が無いことによる凍結は登録で解け、未払いによる凍結は決済の成功で解ける。 督促はしない。

Webhook

外部から通信を受ける口は、このプロジェクトでは初めてになる。

POST /api/stripe/webhook

  署名を検証する（STRIPE_WEBHOOK_SECRET）
  invoice.paid           → billing_invoices を paid にする
  invoice.payment_failed → unpaid にし、凍結を知らせるメールを送る

受けるのはこの二つだけで、他は無視する。 支払い方法の登録完了は Checkout からの戻りで確かめられるので、Webhook には頼らない。

同じイベントが二度届いても結果は変わらない。 状態がすでに unpaid なら、メールを送り直さない。

知らせるメール

いつ宛先きっかけ
おためし終了の7日前組織管理者全員5分ごとの巡回
おためし終了の前日組織管理者全員5分ごとの巡回
おためし切れで凍結した日組織管理者全員5分ごとの巡回
請求に失敗して凍結したとき組織管理者全員Webhook

上の三つは billing_notice_stage という一つの列で重複を防ぐ。 0から3へ単調に増えるだけなので、送信済みの記録に別のテーブルを立てずに済む。

四つめは Webhook から直接送る。 一つの請求が失敗するのは一度きりなので、状態が unpaid へ移った瞬間だけ送れば重複しない。

巡回は通知メールとは別のループで回す。 始める場所は同じ（src/instrumentation.ts）で、置き場は増えない。 間隔だけが違う。通知は60秒、課金は5分である。

これらは notifications テーブルには載せない。 あのテーブルはスレッドの出来事を伝えるためのもので、宛先も組織のメンバー全員ではない。
