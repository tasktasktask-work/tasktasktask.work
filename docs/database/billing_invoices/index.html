Table

billing_invoices

ひと組織のひと月ぶんの請求を、一行で表す。 課金人数を数え直さずに済ませるための、確定した請求明細である。

なぜこのテーブルが必要か

課金人数は organization_members から後追いで計算できる。 行に created_at と deleted_at があり、物理削除をしない方針が守られているためである。

それでも計算し直さない。 計算し直す作りにすると、確定した請求の正しさが「過去の行が二度と動かないこと」に依存してしまう。 移行の手違いひとつで、請求済みの金額と画面の表示が食い違う。 数えた時点の結果をここに固定し、以後は読むだけにする。

もうひとつの役割が冪等性である。 請求の処理は60秒ごとに回るループから起動されるので、同じ月に何度も走りうる。 (organization_id, billing_month) の一意索引が、二重の請求を database の側で止める。

DDL

CREATE TABLE billing_invoices (
  id                 uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id    uuid        NOT NULL REFERENCES organizations (id),
  billing_month      date        NOT NULL,
  member_count       integer     NOT NULL,
  unit_price         integer     NOT NULL,
  subtotal           integer     NOT NULL,
  tax_amount         integer,
  total_amount       integer,
  status             text        NOT NULL DEFAULT 'pending',
  stripe_invoice_id  text,
  invoice_pdf_url    text,
  paid_at            timestamptz,
  failed_at          timestamptz,
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now(),

  -- 対象月は必ず月初の日付で持つ。月そのものを表す型が無いため。
  CONSTRAINT billing_invoices_first_of_month
    CHECK (extract(day from billing_month) = 1),

  -- 課金人数が 0 の請求は作らない。最後の組織管理者は外せないので 1 以上になる。
  CONSTRAINT billing_invoices_member_count_positive
    CHECK (member_count >= 1),

  CONSTRAINT billing_invoices_unit_price_positive
    CHECK (unit_price >= 1),

  -- 単価を変えても、過去の明細が自分で辻褄を持つ。
  CONSTRAINT billing_invoices_subtotal_matches
    CHECK (subtotal = member_count * unit_price),

  CONSTRAINT billing_invoices_status_valid
    CHECK (status IN ('pending', 'open', 'paid', 'unpaid')),

  -- Stripe に載っていない請求は pending だけ。確定したら必ず ID を持つ。
  CONSTRAINT billing_invoices_open_has_stripe
    CHECK (status = 'pending' OR stripe_invoice_id IS NOT NULL),

  CONSTRAINT billing_invoices_paid_has_time
    CHECK ((status = 'paid') = (paid_at IS NOT NULL))
);

-- 同じ月を二度請求しない。請求処理の冪等性はここが担保する。
CREATE UNIQUE INDEX billing_invoices_month_key
  ON billing_invoices (organization_id, billing_month);

-- 凍結の判定が毎リクエスト走るので、未払いの有無だけを引く索引を置く。
CREATE INDEX billing_invoices_unpaid
  ON billing_invoices (organization_id) WHERE status = 'unpaid';

CREATE UNIQUE INDEX billing_invoices_stripe_key
  ON billing_invoices (stripe_invoice_id) WHERE stripe_invoice_id IS NOT NULL;

四つの status

値意味組織への影響
pending行はできたが、Stripe の請求書がまだ無い無し
open確定して決済を待っている無し
paid入金済み無し
unpaid決済に失敗した組織が凍結される

pending があるのは、途中で落ちた場合のためである。 行を作ってから Stripe の請求書を確定するまでのあいだにプロセスが落ちると、この状態で残る。 次の実行がこの行を拾って続きから進めるので、請求が消えることも二重になることもない。

unpaid だけが組織の状態に効く。 この行がひとつでも残っているあいだ、その組織は凍結されている。

通貨の列を持たない

金額はすべて USD のセントである。どの国の組織からも同じ通貨で受け取ると決めたので、 行ごとに通貨を持たせていない。

この判断は、通貨を増やすまで有効である。 増やすときは、過去の行がどの通貨だったかを言えるようにしてから増やすことになる。

削除の列を持たない

他のテーブルには deleted_at があるが、ここには置かない。 請求を消す操作が存在しないためである。 間違えた請求は Stripe 側で無効にし、こちらの行は記録として残す。

関係

organizations ──< billing_invoices ──< billing_invoice_members >── users

請求は組織にぶら下がり、その内訳として対象者がぶら下がる。 対象者の側が users を指しているが、表示名は別に焼いてあるので、 そのユーザーが名前を変えても明細の見え方は変わらない。
