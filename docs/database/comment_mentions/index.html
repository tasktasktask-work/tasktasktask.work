Table

comment_mentions

コメントの本文の、何文字目から何文字目が誰なのか。 投稿した時点で決めて、あとから読み直さない。

なぜこのテーブルが必要か

メンションは @佐藤 明日香 と書く。 表示名には空白が入るので、どこまでが名前かは、閲覧できる人の一覧と突き合わせて決めている。

その突き合わせを表示のたびに行うと、名前が変わったときに答えも変わる。 指名された人が改名すれば、過去のコメントの色が消える。 それより悪いのは逆で、別人が「佐藤 明日香」に改名した瞬間、 過去のコメントがその人を指しているように見える。 通知はもとの人に届いているのに、画面上の指名先だけが入れ替わる。

誰に通知を飛ばしたかは notifications にも残る。 ただしあちらは、自分を指名したときの行を持たない （notifications_not_self が拒む）。 画面に色を付ける根拠としては使えない。

DDL

CREATE TABLE comment_mentions (
  comment_id   uuid NOT NULL REFERENCES comments(id),
  start_offset int  NOT NULL,
  end_offset   int  NOT NULL,
  user_id      uuid NOT NULL REFERENCES users(id),

  PRIMARY KEY (comment_id, start_offset, user_id),

  CONSTRAINT comment_mentions_span
    CHECK (start_offset >= 0 AND end_offset > start_offset)
);

各カラム

カラム意味
comment_idどのコメントの中か
start_offset@ の位置
end_offset名前の直後。半開区間 [start, end) である
user_id指した相手

主キーに user_id が入っている理由

同じ表示名の人が組織に複数いることがある。 display_name に一意の制約は無い。

その場合、一つの @佐藤 明日香 が二人を指す。 どちらなのかを機械が決める手立てが無いので、両方に通知を飛ばす。 同じ位置に複数の行が立つ。

表示のときは位置だけを見るので、DISTINCT start_offset, end_offset で畳んでから使う。

位置が動かない理由

文字数で指しているので、本文が書き換わると全部ずれる。

コメントの本文は書き換わらない。 comments が updated_at を持たず、更新する関数も存在しない。 このテーブルは、その約束の上に乗っている。

スレッドの本文にメンションが無いのは、これと逆の事情による。 あちらは編集できるので、位置を記録しても保たない。 加えて notifications の制約が、指名の通知をコメントに紐づくものに限っている。
