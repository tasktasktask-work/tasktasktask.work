Table

watches

このテーブルに行が作られるのは、ユーザーが自分でボタンを押したときだけである。 スレッドを立てても、担当者になっても、コメントを書いても、行は増えない。

なぜこのテーブルが必要か

通知の三つのきっかけのうち、 「新しいコメントが付いた」だけは宛先が自明でない。 メンションと担当者設定は相手が決まっているが、コメントの投稿には特定の宛先がない。

誰に届けるかを表すのがウォッチである。

DDL

CREATE TABLE watches (
  thread_id  uuid        NOT NULL REFERENCES threads(id),
  user_id    uuid        NOT NULL REFERENCES users(id),
  created_at timestamptz NOT NULL DEFAULT now(),

  PRIMARY KEY (thread_id, user_id)
);

CREATE INDEX watches_by_user ON watches (user_id);

列が三つしかない。 thread_tags と同じく、付け外しが日常的に起きる中間テーブルなので物理削除とした。 「すべてのレコードは論理削除」という方針からの逸脱にあたるが、 中間テーブルに限った例外として承認されている（2026-09-05 のレビュー）。

自動で行を作らない

作成者、担当者、コメントした人を自動的にウォッチ扱いにする設計もありえた。 そうしなかったので、次のことが起きる。

この設計が前提とする運用

自分が立てたスレッドに返信が来ても、ウォッチしていなければ気づけない。

これを補うのはメンションだけである。 「返信するときは相手を @ で呼ぶ」という運用が、この設計の前提になっている。

自動付与を入れるかどうかの検討は通知の拡張に記録した。

通知を作るときの問い合わせ

-- コメント投稿時、ウォッチしている人に通知を作る
INSERT INTO notifications
        (organization_id, user_id, kind, thread_id, comment_id, actor_user_id)
      SELECT $1, w.user_id, 'comment', $2, $3, $4
        FROM watches w
       WHERE w.thread_id = $2
         AND w.user_id <> $4                    -- 書いた本人には送らない
         AND w.user_id <> ALL($5::uuid[])       -- 指名で届く人は除く
         AND $6::uuid IN (…visibleProjectIds…)  -- 見えなくなった人も除く

投稿した本人を除く条件が要る。 自分のコメントで自分に通知が来る状態は、通知一覧をすぐに無意味にする。

権限が変わったウォッチャーの扱い

非公開プロジェクトから外された人のウォッチ行は残る。 外れる経路は三つある。プロジェクトのメンバーから外される、 公開だったプロジェクトが非公開に変わる、組織から抜ける。

通知を作るときにプロジェクトの閲覧権限を確認し、失っている場合は作らない。 行を消す方式も取れるが、再び参加したときに以前のウォッチが失われる。 通知の生成時に判定するほうを選んだ。

読むときにも同じ判定をかける。 書く側を抜けた行が過去に積まれていても、一覧には出ない。

付け外しの動線

スレッド詳細の属性欄に押しボタンを一つ置く。 アーカイブされたスレッドでも押せる。 自分あての設定であって、そのスレッドへの書き込みではないからである。 畳んだ先に新しいコメントは付かないので通知は飛ばないが、 外す手立てまで消えると、開け直したときに困る。

誰がウォッチしているかは、他の人には見せない。人数も出さない。 少人数の組織では、人数だけでも誰が見張っているかが割れる。
