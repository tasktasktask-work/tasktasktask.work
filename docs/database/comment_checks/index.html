Table

comment_checks

コメントの中のチェックボックスが入っているかどうか。 この一枚があるおかげで、コメントの本文は投稿されたときのまま動かない。

なぜこのテーブルが必要か

コメントは投稿したら直せない。 comments が updated_at を持たないのは、その表明である。

ところがチェックボックスは押せる必要がある。 子スレッドを立てるほどでもない作業を並べる手段として置いたものなので、 終わったかどうかを表せなければ、置いた意味がない。

本文の [ ] を [x] に書き換えれば済む、というのが素直な作りである。 そうすると comments に更新の経路ができ、 「一度書いたら直せない」という約束が、そこから崩れる。 加えて、本文まるごとの更新になるので、二人が別々の箱をほぼ同時に押すと、 あとから書いたほうが相手の変更を消す。

状態を本文の外に出すと、その二つが同時に消える。 そして「誰がいつ終わらせたか」という、本文には書かれない事実も残る。

DDL

CREATE TABLE comment_checks (
  comment_id         uuid        NOT NULL REFERENCES comments(id),
  position           smallint    NOT NULL,
  checked_by_user_id uuid        NOT NULL REFERENCES users(id),
  checked_at         timestamptz NOT NULL DEFAULT now(),

  PRIMARY KEY (comment_id, position),

  CONSTRAINT comment_checks_position_range
    CHECK (position >= 0)
);

各カラム

カラム意味
comment_idどのコメントの箱か
position本文の中で何番目のチェックボックスか。0 始まり
checked_by_user_id入れた人。本文には残らない事実なので、ここが唯一の記録になる
checked_at入れた時刻

organization_id を持たない。 thread_tags や watches と同じく、親を辿れば必ず組織に行き着くためである。 読み書きはすべて comments と threads を経由する。

番号で指してよい理由

本文の何番目か、という数え方は、本文が動くなら壊れる。 項目が一つ挿入されただけで、以降の番号がすべてずれる。

コメントの本文は動かない。 だから position は、書かれた瞬間から永久に同じ箱を指す。 このテーブルが成立しているのは、コメントが不変であることの帰結である。

数える側は src/lib/markdown.ts にある。 コードブロックとインラインコードの中は数えない。 ここが本文の描画と食い違うと、別の箱にチェックが入る。

行が無ければ入っていない

外すときは行を消す。deleted_at は置かない。

例外として承認済み

「基本的にすべてのレコードは論理削除」という方針からの逸脱である。 thread_tags と watches に続く三枚目にあたる。

理由も同じで、付け外しが日常的に起きる。 deleted_at を置くと、押すたびに同じ箱の行が積み上がり、 主キーを条件付きの一意インデックスに置き換えることになる。 そして「いつチェックを外したか」を読む場面が想定しにくい。
