Table

comments

投稿されたら変わらない。 そのため updated_at を持たない。 列がないこと自体が、この設計の宣言になっている。

なぜこのテーブルが必要か

コメントはスレッドに時系列で連なる発言である。 枝分かれしないので、返信先を指す列は持たない。

DDL

CREATE TABLE comments (
  id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid        NOT NULL REFERENCES organizations(id),
  thread_id       uuid        NOT NULL REFERENCES threads(id),
  author_user_id  uuid        NOT NULL REFERENCES users(id),
  body            text        NOT NULL,
  deleted_at      timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT comments_body_not_blank
    CHECK (btrim(body) <> '')
);

CREATE INDEX comments_by_thread
  ON comments (thread_id, created_at) WHERE deleted_at IS NULL;

カラム

カラム型説明
author_user_iduuid書いた人。変わらない
bodytextMarkdown。空のコメントは作れない
deleted_attimestamptz組織管理者による論理削除のみ

updated_at がない

他のテーブルにはある updated_at を、このテーブルだけ持たない。 投稿後に更新される経路が存在しないためである。

列を用意しておけば将来編集機能を足せる、という考え方は取らない。 使われない列があると、実装者は「編集できるのかもしれない」と読む。 列がないことで、編集できないという仕様がスキーマから読み取れる。

deleted_at は持つ

本人による削除はできないが、組織管理者による論理削除は残す。 誤って機密情報を書き込んだ場合など、消さざるを得ない場面があるためである。

メンションをどう保持するか

本文中の @表示名 を構造化して別テーブルに持つことはしない。 body をそのまま保存し、投稿時に解析して notifications を作る。

この方式の帰結

ユーザーが表示名を変えても、過去のコメントの @ 表記は古いままになる。 通知は投稿時点で作られているので機能には影響しないが、表示は食い違う。

構造化して保持すれば解決するが、Markdown の本文と構造化データの二重管理になる。 表示の食い違いを受け入れるほうを選んだ。

アーカイブとの関係

スレッドまたはプロジェクトがアーカイブされていると、新しいコメントを作れない。 この判定は threads と projects の archived_at を見て行う。 comments 自身はアーカイブの状態を持たない。
