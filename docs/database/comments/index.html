Table

comments

投稿されたら変わらない。 そのため updated_at を持たない。 列がないこと自体が、この設計の宣言になっている。

なぜこのテーブルが必要か

コメントはスレッドに時系列で連なる発言である。 枝分かれしないので、返信先を指す列は持たない。

DDL

CREATE TABLE comments (
  id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid        NOT NULL REFERENCES organizations(id),
  thread_id       uuid        NOT NULL REFERENCES threads(id),
  author_user_id  uuid        NOT NULL REFERENCES users(id),
  body            text        NOT NULL,
  deleted_at      timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT comments_body_not_blank
    CHECK (btrim(body) <> '')
);

CREATE INDEX comments_by_thread
  ON comments (thread_id, created_at) WHERE deleted_at IS NULL;

カラム

カラム型説明
author_user_iduuid書いた人。変わらない
bodytextMarkdown。空のコメントは作れない
deleted_attimestamptz組織管理者による論理削除のみ

updated_at がない

他のテーブルにはある updated_at を、このテーブルだけ持たない。 投稿後に更新される経路が存在しないためである。

列を用意しておけば将来編集機能を足せる、という考え方は取らない。 使われない列があると、実装者は「編集できるのかもしれない」と読む。 列がないことで、編集できないという仕様がスキーマから読み取れる。

deleted_at は持つ

本人による削除はできないが、組織管理者による論理削除は残す。 誤って機密情報を書き込んだ場合など、消さざるを得ない場面があるためである。

本文の外に出した二つのもの

コメントの本文は、投稿されたときのまま動かない。 その代わりに、本文の中の位置を指す表が二枚ぶら下がっている。

テーブル持っているもの
comment_checks入っているチェックボックスの番号と、入れた人
comment_mentions指名の位置と、指した相手

どちらも body が動かないことに乗っている。 番号も文字数も、本文が一文字ずれれば別のものを指す。

2026-09-07 に方針を変えた

ここには以前、「本文中の @表示名 を構造化して別テーブルに持つことはしない」と書いてあった。 Markdown の本文と構造化データの二重管理を避け、表示の食い違いを受け入れる、という判断だった。

受け入れる先が想定より広かった。display_name は変更でき、しかも一意ではない。 表示のたびに現在の名前と突き合わせると、 別人が同じ表示名に改名した瞬間、過去のコメントがその人を指しているように見える。 通知はもとの人に届いているので、画面と通知の指す先が食い違ったまま残る。

二重管理にはならなかった。本文が動かないので、片方だけが古くなることが起きない。

アーカイブとの関係

スレッドまたはプロジェクトがアーカイブされていると、新しいコメントを作れない。 この判定は threads と projects の archived_at を見て行う。 comments 自身はアーカイブの状態を持たない。 チェックボックスの付け外しも、同じ判定で止まる。
