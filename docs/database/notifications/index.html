Table

notifications

三つのきっかけで作られる。 アプリ内の一覧とメールの両方に同じ内容が届き、既読を持つのはアプリ内の側だけである。

なぜこのテーブルが必要か

メールは送りっぱなしで、読んだかどうかをシステムは知らない。 何を見落としたかを確かめる場所として、アプリ内の一覧が要る。 その一覧の実体がこのテーブルである。

DDL

CREATE TABLE notifications (
  id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid        NOT NULL REFERENCES organizations(id),
  user_id         uuid        NOT NULL REFERENCES users(id),
  kind            text        NOT NULL,
  thread_id       uuid        NOT NULL REFERENCES threads(id),
  comment_id      uuid        REFERENCES comments(id),
  actor_user_id   uuid        REFERENCES users(id),
  read_at         timestamptz,

  -- メールの決着。三つで一組になっている
  emailed_at       timestamptz,
  email_attempts   integer     NOT NULL DEFAULT 0,
  email_gave_up_at timestamptz,

  created_at      timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT notifications_kind_valid
    CHECK (kind IN ('mention', 'assigned', 'comment')),

  -- mention と comment は必ずコメントに紐づく
  CONSTRAINT notifications_comment_required
    CHECK (kind = 'assigned' OR comment_id IS NOT NULL),

  CONSTRAINT notifications_not_self
    CHECK (actor_user_id IS DISTINCT FROM user_id),

  -- 送ったのに諦めた、という行は作れない
  CONSTRAINT notifications_email_settled_once
    CHECK (emailed_at IS NULL OR email_gave_up_at IS NULL)
);

CREATE INDEX notifications_inbox
  ON notifications (user_id, created_at DESC);

CREATE INDEX notifications_unread
  ON notifications (user_id) WHERE read_at IS NULL;

CREATE INDEX notifications_pending_email
  ON notifications (created_at)
  WHERE emailed_at IS NULL AND email_gave_up_at IS NULL;

notifications_not_self

自分の操作で自分に通知が来る状態を、データベース側で拒否する。 自分のコメントで自分に通知が届く一覧は、すぐに読まれなくなる。

メールの決着が三つの列に分かれている理由

メール送信は失敗しうるし、外部サービスへの呼び出しなので同期的に待ちたくない。 行を先に作り、未送信のものを後から巡回が拾って送る。 notifications_pending_email の部分インデックスは、この拾い出しのためにある。

拾われた行は、いずれ三つのどれかに落ち着く。

状態列の形
まだ送っていないemailed_at も email_gave_up_at も NULL
送れたemailed_at が入る。回数は「何回目で届いたか」として残る
送らなかったemail_gave_up_at が入る

三つめには、性質の違う二つが混ざる。 送ろうとして駄目だったものと、送る必要が無くなったものである。 email_attempts がそれを分ける。 0 のまま畳まれた行は、一度も送ろうとしていない。

諦めた行を索引から外す必要がある

emailed_at を代わりに埋める手もあった。 送っていないものを送ったことにすると、届かなかった件を数えられなくなる。

索引の条件に回数を書く手もあった。 そちらは上限を変えるたびに移行が要る。列を分けておけば索引は定数を持たない。

どの手を取るにせよ、外すこと自体は避けられない。 拾う順は古い順なので、居座った行が枠を先に取り、後ろに並んだ人へいつまでも届かなくなる。

作られるとき

kind作られるきっかけ受け取る人
mentionコメントで @ 指名された指名された人
assigned担当者に設定された設定された人
commentコメントが投稿されたウォッチしている人

宛先は、そのとき見える人だけ

作成時に、受け取る人がそのプロジェクトを閲覧できるかを確認する。 通知の本文にはスレッドのタイトルが含まれるため、 閲覧権限のない人へ届くと、そこで非公開プロジェクトの情報が漏れる。

判定は #lib/db.ts の visibleProjectIds を使う。 宛先ごとに違う人で引くことになるので、引数の位置を渡せる関数の形にしてある。 行を作る三つの経路は、どれも src/features/notification/queries.ts の 二つの関数を通る。この判定を書き写した場所は他に無い。

同じコメントで二重に作らない

ウォッチしている人がメンションもされた場合、通知が二つできる。 投稿時に mention を先に作り、指名した相手の一覧を comment の生成へ渡して除く。

INSERT INTO notifications
        (organization_id, user_id, kind, thread_id, comment_id, actor_user_id)
      SELECT $1, w.user_id, 'comment', $2, $3, $4
        FROM watches w
       WHERE w.thread_id = $2
         AND w.user_id <> $4                    -- 書いた本人には送らない
         AND w.user_id <> ALL($5::uuid[])       -- 指名で届く人は除く
         AND $6::uuid IN (…visibleProjectIds…)  -- 見えなくなった人も除く

作られた通知の read_at を埋めるのは、一覧で行を押したときと、 「すべて既読にする」を押したときの二つである。 詳しくは既読を参照。

メール通知を止めている人

users.email_notifications_enabled が偽の人には、 行は作るがメールは送らない。 アプリ内の一覧には出る。

送らないと決めた行には email_gave_up_at が入る。 送らないだけでは足りない。切っている人の行が積み上がり、 巡回が毎分それを読み直すことになる。

この一つのスイッチが認証を守っている

メールを止める手段がないと、煩わしく感じた人が迷惑メールとして報告する。 報告が積み重なると送信ドメインの評価が下がる。

このシステムは認証をメールに依存している。 マジックリンクが届かなくなれば、ログインそのものができない。
