Table

notifications

三つのきっかけで作られる。 アプリ内の一覧とメールの両方に同じ内容が届き、既読を持つのはアプリ内の側だけである。

なぜこのテーブルが必要か

メールは送りっぱなしで、読んだかどうかをシステムは知らない。 何を見落としたかを確かめる場所として、アプリ内の一覧が要る。 その一覧の実体がこのテーブルである。

DDL

CREATE TABLE notifications (
  id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid        NOT NULL REFERENCES organizations(id),
  user_id         uuid        NOT NULL REFERENCES users(id),
  kind            text        NOT NULL,
  thread_id       uuid        NOT NULL REFERENCES threads(id),
  comment_id      uuid        REFERENCES comments(id),
  actor_user_id   uuid        REFERENCES users(id),
  read_at         timestamptz,
  emailed_at      timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT notifications_kind_valid
    CHECK (kind IN ('mention', 'assigned', 'comment')),

  -- mention と comment は必ずコメントに紐づく
  CONSTRAINT notifications_comment_required
    CHECK (kind = 'assigned' OR comment_id IS NOT NULL),

  CONSTRAINT notifications_not_self
    CHECK (actor_user_id IS DISTINCT FROM user_id)
);

CREATE INDEX notifications_inbox
  ON notifications (user_id, created_at DESC);

CREATE INDEX notifications_unread
  ON notifications (user_id) WHERE read_at IS NULL;

CREATE INDEX notifications_pending_email
  ON notifications (created_at) WHERE emailed_at IS NULL;

カラム

カラム型説明
user_iduuid受け取る人
kindtextmention / assigned / comment
comment_iduuidきっかけになったコメント。assigned のときだけ NULL
actor_user_iduuidきっかけを作った人。受け取る人と同じにはならない
read_attimestamptzアプリ内で既読になった時刻
emailed_attimestamptzメールを送った時刻。NULL なら未送信

notifications_not_self

自分の操作で自分に通知が来る状態を、データベース側で拒否する。 自分のコメントで自分に通知が届く一覧は、すぐに読まれなくなる。

emailed_at を持つ理由

メール送信は失敗しうるし、外部サービスへの呼び出しなので同期的に待ちたくない。 行を先に作り、未送信のものを後から拾って送る形にする。

notifications_pending_email の部分インデックスは、この拾い出しのためにある。

作られるとき

kind作られるきっかけ受け取る人
mentionコメントか本文で @ 指名された指名された人
assigned担当者に設定された設定された人
commentコメントが投稿されたウォッチしている人

作成時に、受け取る人がそのプロジェクトを閲覧できるかを確認する。 通知の本文にはスレッドのタイトルが含まれるため、 閲覧権限のない人へ届くと、そこで非公開プロジェクトの情報が漏れる。

同じコメントで二重に作らない

ウォッチしている人がメンションもされた場合、通知が二つできる。 投稿時に mention を先に作り、comment の生成では既に通知を受けた人を除く。

INSERT INTO notifications (organization_id, user_id, kind, thread_id, comment_id, actor_user_id)
SELECT $1, w.user_id, 'comment', $2, $3, $4
  FROM watches w
 WHERE w.thread_id = $2
   AND w.user_id <> $4
   AND NOT EXISTS (
     SELECT 1 FROM notifications n
      WHERE n.comment_id = $3 AND n.user_id = w.user_id
   );

メール通知を止めている人

users.email_notifications_enabled が偽の人には、 行は作るがメールは送らない。 アプリ内の一覧には出る。

この一つのスイッチが認証を守っている

メールを止める手段がないと、煩わしく感じた人が迷惑メールとして報告する。 報告が積み重なると送信ドメインの評価が下がる。

このシステムは認証をメールに依存している。 マジックリンクが届かなくなれば、ログインそのものができない。
