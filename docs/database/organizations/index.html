Table

organizations

テナントの境界。すべてのデータがこの下に入る。 加えて、スレッド番号の採番元であり、 おためし期間の期限を持つ場所でもある。

なぜこのテーブルが必要か

マルチテナントの構成では、どのデータがどの顧客のものかを示す起点が要る。 組織がそれにあたる。

もう一つの役割が採番である。スレッド番号を組織の中で通し番号にすると決めたため、 「次に使う番号」をどこかに置く必要がある。組織ごとにシーケンスを作るのは扱いにくいので、この行に持たせた。

DDL

CREATE TABLE organizations (
  id                  uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  name                text        NOT NULL,
  slug                text        NOT NULL,
  language            text        NOT NULL DEFAULT 'ja',
  timezone            text        NOT NULL DEFAULT 'Asia/Tokyo',
  next_thread_number  integer     NOT NULL DEFAULT 1,

  -- 課金 --------------------------------------------------------------
  -- 既定値が「翌月末」を返すので、新しい組織にも既存の行にも同じ規則が当たる。
  trial_ends_on       date        NOT NULL DEFAULT
    ((date_trunc('month', now() AT TIME ZONE 'Asia/Tokyo')
      + interval '2 month' - interval '1 day')::date),
  billing_exempt        boolean     NOT NULL DEFAULT false,
  stripe_customer_id    text,
  payment_method_set_at timestamptz,
  billing_notice_stage  smallint    NOT NULL DEFAULT 0,

  deleted_at          timestamptz,
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT organizations_name_not_blank
    CHECK (btrim(name) <> ''),
  CONSTRAINT organizations_slug_format
    CHECK (slug ~ '^[a-z0-9][a-z0-9-]{1,38}[a-z0-9]$'),
  CONSTRAINT organizations_language_supported
    CHECK (language IN ('ja')),
  CONSTRAINT organizations_next_number_positive
    CHECK (next_thread_number >= 1),

  -- 0=未送信 1=7日前 2=前日 3=凍結。単調に増えるだけなので一列で足りる。
  CONSTRAINT organizations_notice_stage_range
    CHECK (billing_notice_stage BETWEEN 0 AND 3)
);

CREATE UNIQUE INDEX organizations_slug_key
  ON organizations (slug) WHERE deleted_at IS NULL;

-- ひとつの Stripe 顧客が二つの組織に結びつかないようにする。
CREATE UNIQUE INDEX organizations_stripe_customer_key
  ON organizations (stripe_customer_id) WHERE stripe_customer_id IS NOT NULL;

拡張を使わない

大文字小文字を区別しない識別子なので citext が候補になる。 採らなかった理由は二つある。

ひとつは、CHECK 制約の正規表現が小文字と数字しか許さないこと。 小文字しか格納できないなら、比較を大文字小文字非依存にする意味がない。

もうひとつは、Atlas が無料の範囲では CREATE EXTENSION を扱えないことである。 メールアドレス（users、invitations）も 同じ理由で text にし、小文字に揃えて保存する。 このプロジェクトは拡張をひとつも使わない。

language に CHECK を置いた理由

選べる値がひとつしかないのに列を持つのは、後から列を足すほうが高くつくからである。 ただし列だけあって値の検証がないと、実装が対応していない値が入りうる。 対応言語を増やすときに CHECK も一緒に更新する、という手順を強制するために制約を置いた。

おためし期限の既定値が、移行の手当てを兼ねる

trial_ends_on の既定値は「今日の属する月の翌月末」を返す。 9月に評価すれば10月31日、9月30日でも10月31日である。

この式を既定値に置いたことで、列を足す移行がそのまま既存組織への付与になる。 すでに動いている組織は、移行を当てた日から翌月末まで書き込みを続けられる。 created_at を起点にすると、移行の瞬間にすべての組織が凍結する。

タイムゾーンは組織ごとの timezone ではなく日本標準時に固定した。 自分の行の他の列を既定値の式から参照できないという事情もあるが、 請求を事業者側の暦で切ると決めたこととも揃っている。

関係

organizations ──┬─< organization_members >── users
                ├─< projects
                ├─< tags
                ├─< invitations
                ├─< threads        （project 経由でも辿れるが直接も持つ）
                ├─< comments
                ├─< attachments
                ├─< notifications
                └─< billing_invoices

スレッドやコメントは projects を辿れば組織にたどり着ける。 それでも organization_id を直接持たせているのは、権限判定を結合なしの等値条件で書けるようにするためである。
