Table

tags

組織の単位で定義する。プロジェクトごとではない。 bug や 要相談 のような分類は、プロジェクトが変わっても同じ意味で使われるためである。

なぜこのテーブルが必要か

親子関係は階層という一本の軸しか表せない。 frontend のように階層と直交する分類は、親子では代わりにならない。 タグはその軸を足す。

DDL

CREATE TABLE tags (
  id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid        NOT NULL REFERENCES organizations(id),
  name            text        NOT NULL,
  color           text        NOT NULL DEFAULT '#7d8792',
  deleted_at      timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT tags_name_not_blank
    CHECK (btrim(name) <> '' AND length(name) <= 40),
  CONSTRAINT tags_color_format
    CHECK (color ~ '^#[0-9a-f]{6}$')
);

CREATE UNIQUE INDEX tags_name_uniq
  ON tags (organization_id, lower(name)) WHERE deleted_at IS NULL;

カラム

カラム型説明
nametext40文字まで。組織の中で重複しない。大文字小文字を区別せず比較する
colortext小文字の16進6桁。画面では小さな円の色として使う

色は文字色に使わない

タグの色は円形の点にだけ使い、文字色は変えない。 色数が増えても可読性が落ちないようにするためである。

また、色だけで意味を伝えないので、色覚の違いによる読み取りの差も生じない。 文字が常に主で、色は補助である。

誰でも作れる

作成を管理者に限らない。 必要なタグが作れないと、結局使われなくなるためである。

増え続けることへの手当てがない

組織単位かつ誰でも作成可という組み合わせは、タグが増え続けることを意味する。 選択肢に数十個が並ぶ状態は起こりうる。

統合、リネーム、未使用タグの一括削除といった整理の仕組みは初期リリースに含めていない。 運用してみて実際に問題になるかを見てから判断する。
