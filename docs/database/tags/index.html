Table

tags

組織の単位で定義する。プロジェクトごとではない。 bug や 要相談 のような分類は、プロジェクトが変わっても同じ意味で使われるためである。

なぜこのテーブルが必要か

親子関係は階層という一本の軸しか表せない。 frontend のように階層と直交する分類は、親子では代わりにならない。 タグはその軸を足す。

DDL

CREATE TABLE tags (
  id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid        NOT NULL REFERENCES organizations(id),
  name            text        NOT NULL,
  color           text        NOT NULL DEFAULT '#7d8792',
  deleted_at      timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT tags_name_not_blank
    CHECK (btrim(name) <> '' AND length(name) <= 40),
  CONSTRAINT tags_color_format
    CHECK (color ~ '^#[0-9a-f]{6}$')
);

CREATE UNIQUE INDEX tags_name_uniq
  ON tags (organization_id, lower(name)) WHERE deleted_at IS NULL;

カラム

カラム型説明
nametext40文字まで。組織の中で重複しない。大文字小文字を区別せず比較する
colortext小文字の16進6桁。画面では小さな円の色として使う

色は文字色に使わない

タグの色は円形の点にだけ使い、文字色は変えない。 色数が増えても可読性が落ちないようにするためである。

また、色だけで意味を伝えないので、色覚の違いによる読み取りの差も生じない。 文字が常に主で、色は補助である。

誰でも作れる

作成を管理者に限らない。 必要なタグが作れないと、結局使われなくなるためである。

増え続けることへの手当てがない

組織単位かつ誰でも作成可という組み合わせは、タグが増え続けることを意味する。 選択肢に数十個が並ぶ状態は起こりうる。

名前と色の変更は管理画面から行える。 統合と、未使用タグの一括削除は入れていない。 運用してみて実際に問題になるかを見てから判断する。

消すときに結びも消す

タグの削除は deleted_at を入れる論理削除である。 同じ取引の中で、thread_tags の行を物理削除する。

結びを残しておけば、deleted_at を戻すだけで消す前に戻せる。 それでも消しているのは、同じ名前で作り直した人の前に、半年前のスレッドが一斉にタグ付きで現れるからである。 消したのを取り消したい人と、同じ名前で始め直したい人が、同じ操作をすることになる。

一意の索引が生きている行しか見ない

tags_name_uniq は WHERE deleted_at IS NULL の部分索引である。 消した backend が残っていても、新しい backend はそのまま挿入できる。

消えた行を起こす形も考えたが、採らなかった。 結びは消すときに一緒に消しているので、起こした行に付いているスレッドは一件もない。 新しく入れた行と中身が一致するため、区別する意味がない。

そのため、同じ名前の消えた行が複数溜まりうる。 リネームでも起こしにはいかないので、 foo を消したあと別のタグを foo にして、それも消す、という順で二行になる。 どれも表には出ない。
