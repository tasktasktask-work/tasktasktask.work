Table

billing_invoice_members

請求のときに数えた人を、ひとりずつ残す。 「この金額は誰の分ですか」という問い合わせに答えるためだけの行である。

なぜこのテーブルが必要か

請求書には人数と金額しか載らない。 ところが実際に届く問い合わせは、金額そのものより「先月抜けた人が入っていませんか」という形をとる。

そのときに organization_members を数え直して答えるわけにはいかない。 数え直した結果は、請求した時点の数と一致する保証がない。 請求と同じ瞬間に対象者を書き出しておけば、答えは読むだけで済む。

表示名まで焼くのは、人が名前を変えるからである。 user_id だけを残すと、あとで明細を開いたときに当時と違う名前が並ぶ。 請求の根拠は、そのときの姿のまま置いておく。

DDL

CREATE TABLE billing_invoice_members (
  id                 uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  billing_invoice_id uuid        NOT NULL REFERENCES billing_invoices (id),
  user_id            uuid        NOT NULL REFERENCES users (id),
  display_name       text        NOT NULL,
  created_at         timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT billing_invoice_members_name_not_blank
    CHECK (btrim(display_name) <> '')
);

-- 同じ人を二度数えない。抜けてから戻った人は所属の行を二つ持つ。
CREATE UNIQUE INDEX billing_invoice_members_uniq
  ON billing_invoice_members (billing_invoice_id, user_id);

カラム

カラム型説明
iduuid主キー
billing_invoice_iduuidどの月の請求か
user_iduuid数えた人。すでに組織を抜けていることもある
display_nametext請求した時点の表示名。以後は変わらない
updated_at を持たない

他のテーブルには updated_at があり、トリガが値を埋めている。 ここには置かない。書いたあと二度と変えない行だからである。 更新の時刻を持たせると、更新しうるように読めてしまう。

一意索引が二重計上を止める

組織を抜けてから招待し直された人は、organization_members に行を二つ持つ。 招待の受諾が畳んだ行を起こさず、新しい行を足す作りだからである。

数えるクエリの側でも count(DISTINCT user_id) にしているが、 書き出す側にも一意索引を置いて二重に止める。 片方が壊れても、請求の人数と内訳の行数がずれない。

関係

billing_invoices ──< billing_invoice_members >── users

users への外部キーは持つが、表示のために辿ることはない。 名前は display_name に焼いてあるので、明細を描くのに結合は要らない。 外部キーは、実在しない人を数えていないことを database に確かめさせるためだけに置いている。
