Table

signup_tokens

組織登録の途中で、メールアドレスの持ち主であることを確かめるための一時的な行。 この時点では、組織もアカウントもまだ存在しない。

なぜこのテーブルが必要か

登録を始めた人について分かっているのは、入力されたメールアドレスひとつだけである。 そのアドレスが本人のものかは、リンクを踏んでもらうまで分からない。 確かめる前に users の行を作ると、認証のいちばん基礎のテーブルに 「まだ確認されていないアカウント」という状態が生まれる。 ログインできるのか、誰が掃除するのか、招待の宛先として扱ってよいのか。 問いが一つずつぶら下がる。

そこで、確認が済むまでの情報だけを別の場所に置く。 invitations から organization_id と役割を落とすと、ちょうどこの形になる。

DDL

CREATE TABLE signup_tokens (
  id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  email      text        NOT NULL,
  token_hash bytea       NOT NULL,
  expires_at timestamptz NOT NULL,
  used_at    timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT signup_tokens_email_lowercase
    CHECK (email = lower(email)),
  CONSTRAINT signup_tokens_email_shape
    CHECK (email ~ '^[^@[:space:]]+@[^@[:space:]]+\.[^@[:space:]]+$')
);

CREATE UNIQUE INDEX signup_tokens_hash_key ON signup_tokens (token_hash);

-- 再送の間隔を測るときに引く。使い終わった行は対象から外れる。
CREATE INDEX signup_tokens_by_email
  ON signup_tokens (email) WHERE used_at IS NULL;

カラム

カラム型説明
emailtext登録しようとしているアドレス。小文字で正規化して保存する。users にあるとは限らない
token_hashbytea登録URLに含めた値の SHA-256。値そのものは保存しない
expires_attimestamptz発行から48時間後。マジックリンクと招待に揃えてある
used_attimestamptz組織を作り終えた時刻。一度きり
created_attimestamptz発行の時刻。同じアドレスへの再送の間隔をここで測る

organization_id を持たない。 組織はこのトークンが使われた瞬間に生まれるので、発行の時点では指す先が無い。 組織名も slug も持たないのは同じ理由である。 どちらもリンクを踏んだ先の画面で入力する。

使われたときに起きること

  1. そのメールアドレスの users が無ければ作る。表示名とパスワードはこの画面で設定する
  2. organizations に行を作る。slug が埋まっていたらここで止まる
  3. organization_members に admin で行を作る
  4. used_at を埋める
  5. sessions を作ってログイン状態にする

すべて同じトランザクションの中で行う。 2 で止まったときは used_at も埋まらないので、同じリンクで slug を入れ直せる。 作れなかったリンクを消費しないのは、 ここで消費すると、埋まっていた slug をひとつ選んだだけの人が最初からやり直すことになるためである。

すでにアカウントがある人には、表示名もパスワードも訊かない

訊いて上書きできると、登録リンクを踏ませるだけで他人のパスワードを書き換えられる。 招待の受諾がパスワードを訊かないのと同じ判断である。

この経路で既存のアカウントに起きるのは、組織がひとつ増えることと、 ロックが解けることだけである。

同じアドレスへの再送

未使用で期限内の行が3分以内に作られていれば、新しくは送らない。 画面の返事は送ったときと同じにする。 返事を変えると、そのアドレスが登録の途中かどうかを外から測れてしまう。

3分を過ぎていれば、そのアドレスの未使用の行を消してから新しく入れる。 有効なリンクは常に一本だけになる。 古い行を used_at で畳まずに消すのは、 使われていないトークンに残す価値が無いからである。 誰がいつ登録を試みたかの記録は、監査ログの仕事になる。

期限切れの行も、定期的に物理削除してよい。 magic_link_tokens と同じ扱いである。

関係

      │

      ▼
users ──< organization_members >── organizations

外部キーを一本も持たない。 invitations が organization_id と invited_by_user_id を持つのと対照的だが、これは招待が 「すでにある組織の、ある人が送るもの」であるのに対し、 登録は「まだ何も無いところから始まるもの」だからである。
