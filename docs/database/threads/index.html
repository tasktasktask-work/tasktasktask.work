Table

threads

課題も議論も質問も、この一つのテーブルに入る。 自己参照で無制限の階層を作り、種別ごとに使える列が変わる。 そのぶん制約が集中していて、このスキーマでいちばん読むべき場所になっている。

なぜ一つのテーブルにまとめたか

種別ごとにテーブルを分けることもできた。 分けなかったのは、三つが同じ一覧に並び、同じように親子関係でつながるからである。

種別をまたぐ親子を許した以上、parent_thread_id が三つのテーブルのどれを指すかわからない状態になる。 それを解くために型を判別する列を足すくらいなら、最初から一つのテーブルに置くほうが素直である。

代償として、使わない列が種別によって生じる。 議論と質問は starts_on も ends_on も持たない。 この空きは CHECK 制約で「必ず NULL であること」を強制し、意図しない値が入らないようにする。

DDL

CREATE TABLE threads (
  id                 uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id    uuid        NOT NULL,
  project_id         uuid        NOT NULL,
  number             integer     NOT NULL,
  type               text        NOT NULL,
  title              text        NOT NULL,
  body               text        NOT NULL DEFAULT '',
  body_edited_at     timestamptz,
  progress           smallint    NOT NULL DEFAULT 0,
  starts_on          date,
  ends_on            date,
  assignee_user_id   uuid        REFERENCES users(id),
  parent_thread_id   uuid,
  created_by_user_id uuid        NOT NULL REFERENCES users(id),
  archived_at        timestamptz,
  deleted_at         timestamptz,
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now(),

  -- プロジェクトと組織の整合をデータベース側で保証する
  CONSTRAINT threads_project_fk
    FOREIGN KEY (project_id, organization_id)
    REFERENCES projects (id, organization_id),

  -- 親子は同じプロジェクトに閉じる
  CONSTRAINT threads_parent_fk
    FOREIGN KEY (parent_thread_id, project_id)
    REFERENCES threads (id, project_id),

  CONSTRAINT threads_id_project_uniq UNIQUE (id, project_id),

  CONSTRAINT threads_type_valid
    CHECK (type IN ('kadai', 'giron', 'shitsumon')),

  CONSTRAINT threads_progress_range
    CHECK (progress BETWEEN 0 AND 100),

  -- 議論と質問は 0 か 100 しか取らない
  CONSTRAINT threads_progress_binary_for_non_kadai
    CHECK (type = 'kadai' OR progress IN (0, 100)),

  -- 議論と質問は期間を持たない
  CONSTRAINT threads_period_only_for_kadai
    CHECK (type = 'kadai' OR (starts_on IS NULL AND ends_on IS NULL)),

  -- 期間は両方入れるか両方空けるか
  CONSTRAINT threads_period_paired
    CHECK ((starts_on IS NULL) = (ends_on IS NULL)),

  CONSTRAINT threads_period_ordered
    CHECK (starts_on IS NULL OR starts_on <= ends_on),

  CONSTRAINT threads_not_own_parent
    CHECK (parent_thread_id IS DISTINCT FROM id),

  CONSTRAINT threads_delete_after_archive
    CHECK (deleted_at IS NULL OR archived_at IS NOT NULL)
);

CREATE UNIQUE INDEX threads_number_uniq
  ON threads (organization_id, number);

CREATE INDEX threads_by_project
  ON threads (project_id, updated_at DESC) WHERE deleted_at IS NULL;

CREATE INDEX threads_by_assignee
  ON threads (assignee_user_id, ends_on) WHERE deleted_at IS NULL;

CREATE INDEX threads_by_parent
  ON threads (parent_thread_id) WHERE deleted_at IS NULL;

CREATE INDEX threads_gantt
  ON threads (project_id, starts_on, ends_on)
  WHERE type = 'kadai' AND deleted_at IS NULL AND archived_at IS NULL;

制約が守っていること

親子が同じプロジェクトに閉じる

threads_parent_fk は少し変わった形をしている。 親を指すのに (parent_thread_id, project_id) という二列で参照している。

FOREIGN KEY (parent_thread_id, project_id)
REFERENCES threads (id, project_id)

この形にすると、親の project_id が自分の project_id と一致していなければ外部キーが成立しない。 つまり親子がプロジェクトをまたげないことを、アプリケーションではなくデータベースが保証する。

同じ手法を threads_project_fk にも使い、 スレッドの組織とプロジェクトの組織が食い違う状態を拒否している。

循環参照はデータベースでは防げない

A の親が B、B の親が C、C の親が A、という状態を CHECK 制約で表す方法はない。 階層の深さに制限がないため、なおさら難しい。

親を設定するときにアプリケーション側で祖先を辿り、自分自身が現れないことを確認する。 再帰CTEで祖先を取得し、その中に対象のIDが含まれていれば拒否する。

確かめてから書くまでには隙間がある。 その間に別の付け替えが通れば、二つとも単独では輪を作らないのに、 合わせると輪になる。そこで辿るところと書くところを同じトランザクションに入れ、 親の行を FOR UPDATE で掴んでから辿る。

種別ごとの列の使い分け

議論と質問が期間を持たないこと、進捗率が0か100しか取らないこと。 これらは画面の制御だけに任せず、CHECK 制約で書いている。

APIを直接叩かれた場合や、運用中の手作業でデータを触った場合に、 画面の制御は効かない。 オープンとクローズで表示するはずの質問に progress = 45 が入ると、画面は何を出せばいいかわからなくなる。

アーカイブを経ないと削除できない

projects と同じく、deleted_at は archived_at が埋まっていなければ設定できない。

畳んだプロジェクトの中身は、この列では止まらない

プロジェクトをアーカイブしても、 中のスレッドの archived_at は埋めない。 埋めると、プロジェクトを戻したときに、元から畳んであったスレッドまで開いてしまう。

そのため書き込みの条件は、この行の archived_at と、 projects.archived_at の両方を見なければならない。 片方だけを見ると、畳んだプロジェクトの中身が書き換えられる。

誰が書けるかはスレッドにまとめてある。 短く言えば、閲覧できる人は書ける。削除だけが組織管理者に残っている。

祖先と子孫を辿る

階層に制限がないため、親子の探索は再帰CTEで行う。

-- ある スレッド の祖先をすべて取得する（循環の検出にも使う）
WITH RECURSIVE ancestors AS (
  SELECT id, parent_thread_id, 1 AS depth
    FROM threads WHERE id = $1
  UNION ALL
  SELECT t.id, t.parent_thread_id, a.depth + 1
    FROM threads t
    JOIN ancestors a ON t.id = a.parent_thread_id
   WHERE a.depth < 50           -- 暴走を止める安全弁
)
SELECT id FROM ancestors WHERE id <> $1;

深さの上限を50で切っているのは、万一循環が入り込んだときに問い合わせが止まらなくなることを防ぐためである。 仕様としての階層の上限ではない。

ガントで使う問い合わせ

ガントチャートに出す行は、期間を持つ課題とその祖先である。 期間で絞ってから親を辿るので、再帰の起点は種になる課題だけになる。

WITH RECURSIVE seed AS (
  -- 時間軸に描く課題。ここだけ件数を切る
  SELECT id FROM threads
   WHERE project_id  = $1
     AND type        = 'kadai'
     AND starts_on IS NOT NULL
     AND archived_at IS NULL
     AND deleted_at  IS NULL
   ORDER BY starts_on, ends_on, number
   LIMIT 500
),
tree AS (
  SELECT t.id, t.parent_thread_id, 1 AS depth
    FROM threads t JOIN seed ON seed.id = t.id
  UNION ALL
  -- 親は期間が無くても、畳んであっても引き上げる。
  -- 落とすと、子が一段下がっている理由が読めなくなる
  SELECT p.id, p.parent_thread_id, tree.depth + 1
    FROM threads p JOIN tree ON p.id = tree.parent_thread_id
   WHERE p.deleted_at IS NULL AND p.type = 'kadai' AND tree.depth < 50
)
SELECT DISTINCT id FROM tree;

辿る親を課題に限っているので、親が議論や質問なら そこで打ち切られ、その課題は最上位の行になる。行として出せない親の下にぶら下げても、 なぜ下がっているのかが読めないためである。

深さを50で切っているのは、親の付け替えの検査と同じ理由による。 仕様としての階層の上限ではない。

-- 期間未設定の課題（図の下に別枠で並べるもの）
SELECT id, number, title
  FROM threads
 WHERE project_id  = $1
   AND type        = 'kadai'
   AND starts_on IS NULL
   AND progress   < 100
   AND archived_at IS NULL
   AND deleted_at  IS NULL
 ORDER BY number
 LIMIT 100;

この問い合わせがなければ、期間未設定の課題はどこにも現れない。 ガントに載っていない課題があること自体に気づけなくなる。

progress < 100 を入れてあるのは、終わった課題をここに出しても、 もう計画に載せる先が無いためである。 この条件があるので、枠が空なら動いている課題はすべて計画に載っていると読める。

効いている索引

種を選ぶ側は threads_gantt （project_id, starts_on, ends_on の部分索引）に当たる。 条件が索引の絞り込み条件とそのまま重なっている。
