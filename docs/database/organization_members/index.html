Table

organization_members

ユーザーと組織を多対多で結ぶ。役割もここに持つ。 同じ人が組織Aでは管理者、組織Bでは一般メンバー、ということが起こりうるためである。

なぜこのテーブルが必要か

ひとりが複数の組織に所属できると決めたため、 users に organization_id を持たせる形は取れない。

役割を users ではなくこちらに置いているのも同じ理由による。 役割は人の属性ではなく、人と組織の関係の属性である。

DDL

CREATE TABLE organization_members (
  id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid        NOT NULL REFERENCES organizations(id),
  user_id         uuid        NOT NULL REFERENCES users(id),
  role            text        NOT NULL DEFAULT 'member',
  deleted_at      timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT organization_members_role_valid
    CHECK (role IN ('admin', 'member'))
);

CREATE UNIQUE INDEX organization_members_uniq
  ON organization_members (organization_id, user_id) WHERE deleted_at IS NULL;

CREATE INDEX organization_members_by_user
  ON organization_members (user_id) WHERE deleted_at IS NULL;

カラム

カラム型説明
roletextadmin が組織管理者、member が組織メンバー
deleted_attimestamptz組織から外れた時刻。行は残す

role が二値しかない

「ゲスト」のような第三の役割は用意しない。 外部の人に一部だけ見せたい場合は、非公開プロジェクトで代替する。

組織管理者は複数人置ける

role = 'admin' の行数に制限はない。 ひとりに限ると、その人が退職した時点で組織が操作不能になる。

ただし「最後の管理者を外せない」という制約は、データベースではなくアプリケーション側で持つ。 行数の下限は CHECK では表現できないためである。

権限判定での使われ方

-- 組織管理者は非公開プロジェクトも含めてすべて見える
SELECT 1
  FROM organization_members
 WHERE organization_id = $1
   AND user_id         = $2
   AND role            = 'admin'
   AND deleted_at IS NULL;

非公開プロジェクトの閲覧判定は、この結果と project_members の結果の論理和になる。

この判定は src/lib/db.ts の orgAdminExists() という断片にまとめてある。 同じ条件を各所へ書き写すと、片方だけ直したときに穴が開く。 実際に一度開けている。

行が増えるときと、畳まれるとき

行が増える経路は招待の受諾だけである。 一度外れた人を呼び戻したときも、畳んである行を起こさずに新しい行を足す。 入って抜けてを繰り返した人には畳んだ行が何本も並んでいて、 まとめて起こすと生きた行が二本になり、部分一意索引に当たる。

畳むときは deleted_at を埋める。 そのとき、その人の project_members も一緒に畳む。 権限のためではない。 閲覧判定はこの行が残っていても漏れないようにしてあり、 畳むのは意味を失った行を残さないためである。

最後の管理者を守るには、先に鍵をかける

数えてから変えるまでのあいだに、別の要求が同じことをすると、 どちらも「自分のほかにもう一人いる」と読んで通ってしまう。

管理者の行を FOR UPDATE で掴んでから数える。 掴んだ行の中に自分がいるかどうかで、操作してよいかも同時に決まる。
