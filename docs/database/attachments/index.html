Table

attachments

スレッドかコメントのどちらか一方に付く。 実体はファイルシステム側にあり、このテーブルが持つのはその在り処と、元の名前である。

なぜこのテーブルが必要か

ファイルは生成したIDで保存する。 利用者が付けた名前をそのままパスに使うと、 ../../ によるパストラバーサルや、 制御文字で拡張子を偽装する手口の入口になる。

そのため「保存先のキー」と「表示する名前」を分けて持つ場所が要る。

DDL

CREATE TABLE attachments (
  id                 uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id    uuid        NOT NULL REFERENCES organizations(id),
  thread_id          uuid        REFERENCES threads(id),
  comment_id         uuid        REFERENCES comments(id),
  storage_key        text        NOT NULL,
  original_filename  text        NOT NULL,
  byte_size          bigint      NOT NULL,
  declared_type      text,
  is_image           boolean     NOT NULL DEFAULT false,
  uploaded_by_user_id uuid       NOT NULL REFERENCES users(id),
  deleted_at         timestamptz,
  created_at         timestamptz NOT NULL DEFAULT now(),

  -- スレッドかコメントのどちらか一方にだけ付く
  CONSTRAINT attachments_exactly_one_owner
    CHECK ((thread_id IS NULL) <> (comment_id IS NULL)),

  CONSTRAINT attachments_size_limit
    CHECK (byte_size > 0 AND byte_size <= 10 * 1024 * 1024)
);

CREATE UNIQUE INDEX attachments_storage_key_uniq ON attachments (storage_key);
CREATE INDEX attachments_by_thread  ON attachments (thread_id)  WHERE deleted_at IS NULL;
CREATE INDEX attachments_by_comment ON attachments (comment_id) WHERE deleted_at IS NULL;

カラム

カラム型説明
storage_keytext保存先のキー。生成した値で、利用者の入力を含まない
original_filenametext表示用。パスには使わない。画面に出すときはエスケープする
byte_sizebigint10MB を上限とする
declared_typetextアップロード時にブラウザが申告した MIME タイプ。記録のみで、配信には使わない
is_imagebooleanサーバー側の再エンコードに成功したか。真ならインライン表示する

declared_type を信用しない

ブラウザが送ってくる MIME タイプは、送り手が自由に決められる。 配信時の Content-Type にこれを使うと、 text/html と申告されたファイルがブラウザで解釈されうる。

配信は常に application/octet-stream で行い、 この列は「何のつもりで送られたか」を後から調べるためだけに持つ。

is_image が判定のすべて

形式のホワイトリストは持たない。 アップロード時に画像として読み直せたかどうかだけを記録する。

読めればインライン表示し、読めなければダウンロードできるだけの添付になる。 維持すべきリストがどこにも存在せず、デコーダそのものが判定器として働く。

このテーブルが守らないこと

マルウェアの受け渡しは防げない。 形式を制限しないため、実行ファイルを圧縮して添付することは可能である。

配信ヘッダはブラウザ上での実行を防ぐが、 利用者が自分でダウンロードして開くことは止められない。 これに効くのはウイルススキャンだけで、導入の検討はウイルススキャンに記録した。

配信のときに付けるヘッダ

Content-Type:             application/octet-stream
Content-Disposition:      attachment; filename*=UTF-8''<エンコードした original_filename>
X-Content-Type-Options:   nosniff
Content-Security-Policy:  default-src 'none'; sandbox
Cache-Control:            private, max-age=0, no-store

配信は本体と同じオリジンから行う。 実行を防いでいるのはオリジンの分離ではなく、これらのヘッダである。 経緯を機能ページに書いた。

is_image が真のものだけは Content-Type を画像の値にし、 Content-Disposition を inline にする。 この分岐は一箇所に限り、パラメータで切り替えられるようにはしない。
