Table

projects

スレッドの器。閲覧範囲、ガントの範囲、メンションの候補、親子関係の範囲。 このシステムのいくつもの境界が、この一行に紐づいている。

なぜこのテーブルが必要か

プロジェクトは分類のためではなく、境界を引くために存在する。 ガントチャートが何を一枚に描くのか、 メンションの候補に誰が出るのか、 親子関係がどこまで届くのか。 これらすべてがこのテーブルの行を単位にしている。

DDL

CREATE TABLE projects (
  id                 uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id    uuid        NOT NULL REFERENCES organizations(id),
  key                text        NOT NULL,
  name               text        NOT NULL,
  description        text        NOT NULL DEFAULT '',
  visibility         text        NOT NULL DEFAULT 'public',
  archived_at        timestamptz,
  deleted_at         timestamptz,
  created_by_user_id uuid        NOT NULL REFERENCES users(id),
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT projects_key_format
    CHECK (key ~ '^[A-Z0-9]{2,10}$'),
  CONSTRAINT projects_visibility_valid
    CHECK (visibility IN ('public', 'private')),
  CONSTRAINT projects_delete_after_archive
    CHECK (deleted_at IS NULL OR archived_at IS NOT NULL),

  -- threads からの複合外部キーの相手側
  CONSTRAINT projects_id_org_uniq UNIQUE (id, organization_id)
);

CREATE UNIQUE INDEX projects_key_uniq
  ON projects (organization_id, key) WHERE deleted_at IS NULL;

カラム

カラム型説明
keytextプロジェクトキー。半角英大文字と数字で2から10文字。作成後は変更できない
nametext画面に出る名称。変更できる
descriptiontext説明文。空文字を既定とし NULL は使わない
visibilitytextpublic なら組織メンバー全員が閲覧可、private なら project_members と組織管理者のみ
archived_attimestamptzアーカイブの時刻。配下のスレッドが読み取り専用になる
deleted_attimestamptz論理削除。アーカイブ済みでなければ設定できない

key の変更を許さない

データベースの上では変更しても壊れない。 スレッド番号は組織の中で通し番号になっているので、 threads.number だけでスレッドは一意に定まり、キーは表示のための飾りにすぎない。

それでも許さないのは、人の記憶と記録が壊れるからである。 議事録やコミットメッセージに WEB-128 と書かれたものが、ある日から FRONT-128 になると照合できなくなる。

アーカイブを経ないと削除できない

projects_delete_after_archive の CHECK でこれを強制する。 誤操作でいきなり消えることを防ぐためであり、この順序はアプリケーションの実装に頼らずデータベース側で保証する。

id と organization_id の複合一意制約

id は主キーなので単体で一意である。 それでも (id, organization_id) の一意制約を追加しているのは、 threads から複合外部キーで参照するためである。 これにより「スレッドの組織とプロジェクトの組織が食い違う」状態をデータベースが拒否する。

アーカイブが連鎖しないこと

プロジェクトをアーカイブしても、配下の threads.archived_at は書き換えない。 読み取り専用かどうかの判定は、プロジェクトとスレッドの両方を見て行う。

-- 編集できるか
SELECT (p.archived_at IS NULL AND t.archived_at IS NULL) AS editable
  FROM threads t
  JOIN projects p ON p.id = t.project_id
 WHERE t.id = $1;

この形にしておくと、プロジェクトのアーカイブを解除したときに元の状態がそのまま戻る。 スレッド側を書き換えていたら、解除時にどれを元に戻すべきかがわからなくなる。
