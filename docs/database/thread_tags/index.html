Table

thread_tags

スレッドとタグを結ぶ中間テーブル。 このテーブルは、全レコード論理削除という方針から意図的に外してある。

なぜこのテーブルが必要か

ひとつのスレッドに何個でもタグを付けられるため、多対多の関係になる。

DDL

CREATE TABLE thread_tags (
  thread_id  uuid        NOT NULL REFERENCES threads(id),
  tag_id     uuid        NOT NULL REFERENCES tags(id),
  created_at timestamptz NOT NULL DEFAULT now(),

  PRIMARY KEY (thread_id, tag_id)
);

CREATE INDEX thread_tags_by_tag ON thread_tags (tag_id);

論理削除しない理由

他のテーブルはすべて deleted_at を持ち、行を消さない。 このテーブルと watches だけが例外である。

理由は、付け外しが日常的に起きることにある。 deleted_at を置くと、タグを外して付け直すたびに行が積み上がる。 主キーも (thread_id, tag_id) のままでは使えず、 条件付きの一意インデックスに置き換えることになる。

そして、得られるものが少ない。 「いつタグを外したか」は、記録として参照する場面が想定しにくい。

例外として承認済み

「基本的にすべてのレコードは論理削除」という方針からの逸脱にあたるが、 中間テーブルに限った例外として承認されている（2026-09-05 のレビュー）。 同じ扱いを watches にも適用する。

タグの付け外しを記録として残す必要が生じた場合は、 deleted_at を足すのではなく操作ログを別に持つ形（監査ログ）で扱う。
