ドキュメント規約

ビルドを持たない静的なHTMLの集まりである。 共通部分は theme.css と sidebar.js の二つだけが担う。

構成

docs/
├── index.html          全体の入口
├── glossary.html       用語集
├── theme.css           共通スタイル（★仕様書にない追加）
├── sidebar.js          共通サイドバーの注入
├── features/{name}/    機能ごと
├── database/{table}/   テーブルごと
├── ui/
│   ├── principles.html
│   ├── components/{name}/
│   └── pages/{path}/   実際のURLに対応させる
├── issues/{name}/      先送りした課題
├── devops/{slug}/      開発と運用
└── sessions/{YYYYMMDD-HHMM}-{summary}/
theme.css は仕様書からの追加である

ドキュメントの構成に theme.css は含まれていなかった。 共通で持つのは sidebar.js だけという想定である。

しかし約1,000行のスタイルを50近いファイルに複製すると、 色を一つ変えるだけで全ファイルを触ることになる。 sidebar.js に注入させる案もあるが、 defer で読むためスタイルの当たっていない画面が一瞬見える。

意図的な逸脱として追加し、レビューで承認されている（2026-09-05）。

新しいページを作るとき

  1. 既存の近いページを複製する。ゼロから書かない。 機能ページなら features/thread/index.html、 テーブルなら database/threads/index.html を雛形にする
  2. <link rel="stylesheet"> と <script src> の 相対パスを、そのページの階層に合わせる
  3. sidebar.js の groups に追記する。忘れるとサイドバーに出ない
  4. 本文から関連するページへリンクを張る。特に用語集へ

相対パスの数え方

ページプレフィックス
glossary.htmlなし
features/index.html../
features/thread/index.html../../
ui/components/gantt-bar/index.html../../../
ui/pages/o/[slug]/p/[key]/t/[number]/index.html../ を8個

sidebar.js は自身の src からルートを逆算するので、 この数さえ合っていれば file:// でも GitHub Pages でも動く。

用語集を最優先で更新する

この規約が最も重い

会話の中で新しい語が出てきたら、設計や実装より先に 用語集へ書く。

そして、その語を使っている本文の側からも用語集へリンクを張る。 どこからも参照されていない語が残っていたら、 それは使われていない語か、リンクの張り忘れである。

孤立した用語を機械的に見つける

# 用語集の id 一覧と、本文からの参照を突き合わせる
comm -23 \
  <(grep -o 'class="term" id="[^"]*"' glossary.html \
      | sed 's/.*id="//;s/"//' | sort) \
  <(grep -rho 'glossary\.html#[a-z0-9-]*' --include='*.html' . \
      | sed 's/.*#//' | sort -u)

何も出力されなければ、すべての用語がどこかから参照されている。

サイドバーの決まり

  • セッションは直近5件まで。溢れたものは groups から削り、 sessionTotal に総数を入れる。総数が5を超えていれば「全 N 件」と表示される
  • 完了した課題は削る。対応が済んだ Issue はサイドバーから外す。 課題の一覧からは引き続き辿れる
  • 変更した直後はブラウザのキャッシュで反映されないことがある。 Cmd/Ctrl+Shift+R で確認する

文章の書き方

japanese-tech-writing と cognitive-rhythm-writing の規範に従う。 特に守るもの。

  • ダッシュ（2倍ダッシュ）を地の文に使わない。括弧か句点で分ける
  • 中黒を並列に使わない。読点でつなぐ
  • 用語の初出は太字で定義し、以後の言及は「」を使う
  • 決めたことだけでなく、その決定が捨てたものを書く。 「なぜこれがないのか」に答えられる状態を保つ
  • 「重要なのは」「掘り下げる」「多角的に」といった、中身のない語を使わない

UI の作り方

frontend-design の規範に従う。 加えて、この製品固有の基準はUI設計方針に置いた。

コンポーネントの見本は theme.css の 「製品コンポーネントの見本」の節に定義してある。 ドキュメント上の見本と実装が同じCSSを共有できるよう、 クラス名は p- を接頭辞にしている。
