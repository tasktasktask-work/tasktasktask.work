DevOps 07

コミットの流れ

メッセージを用意する側と、コミットする側を分けている。 用意されたものが自動で差し込まれ、使われたら片付く。 その受け渡しを二つのフックが担う。

なぜ分けているか

.claude/CLAUDE.md で、Claude には読み取り以外の Git 操作を禁じている。 そのため作業した本人がコミットを打てない。

作業内容を知っているのは作業した側で、 コミットの粒度とタイミングを決めるのは人である。 この二つを、ファイル一つの受け渡しでつないでいる。

作業する側                     git                      人
    │                                                    │
    │ .git/COMMIT_NEXTMSG へ書く                          │
    │───────────────────────▶                            │
    │                                                    │ git commit
    │                    prepare-commit-msg ◀────────────│
    │                        差し込む                      │
    │                                                    │ 保存して閉じる
    │                    post-commit                      │
    │                        片付ける                      │

メッセージを用意する

prepare-commit-message スキルが .git/COMMIT_NEXTMSG へ書く。 既に何か書かれていて、そこへ統合できる内容なら統合する。

/{使用したスキル}
{修正を加えた内容を5行以内}

5行という上限は、変更内容の記述にかかる。 Co-Authored-By のような帰属の行は、その後ろに置く。

差し込む（prepare-commit-msg）

COMMIT_NEXTMSG があれば、コミットメッセージの先頭へ流し込む。 そして COMMIT_NEXTMSG.used という旗を立てる。

呼ばれ方COMMIT_SOURCE挙動
git commit空差し込む
git commit -m ...message差し込まない
マージ、squash、テンプレートそれぞれ設定される差し込まない

すでに書く内容が決まっている場合に、用意したものが割り込むと邪魔になる。 引数なしの git commit のときだけ働く。

片付ける（post-commit）

旗が立っていれば、COMMIT_NEXTMSG と旗の両方を消す。

旗を見るのが要である

コミットのたびに無条件で消すと、-m で打ったコミットの後にも消える。 そのときのメッセージはまだ使われていないので、次に回すべきものである。

逆に消さないと、次のコミットにも同じ内容が差し込まれる。 旗は「差し込みが実際に起きた」ことだけを伝える。

確かめたこと

二つのフックを続けて動かし、一連の流れを通した。

確認結果
引数なしの git commit で差し込まれるか差し込まれる
-m のときに差し込まれないか差し込まれない
旗が無いときに COMMIT_NEXTMSG を消さないか消さない
旗があるときに片付くか両方消える
続けてもう一度コミットしたとき、再利用されないかされない

フックは版に残らない

clone しても入らない

.git/hooks/ は git が管理する領域の中にあり、コミットの対象にならない。 そのため次の場合に失われる。

  • 他の人がこのリポジトリを clone したとき
  • git を初期化し直したとき
  • devcontainer を作り直したとき

失われても壊れはしない。 COMMIT_NEXTMSG が差し込まれなくなるだけで、 普通にメッセージを書けばコミットはできる。 ただし気づかないまま用意したメッセージが使われない状態にはなる。

版に残すなら

追跡されるディレクトリへ移し、git にそこを見させる。

# 一度だけ
git config core.hooksPath .githooks

.githooks/ に置けばコミットの対象になり、clone した人にも届く。 ただし core.hooksPath の設定自体は各自が一度実行する必要がある。 完全には自動にならない。

いまは .git/hooks/ に直接置いてある。 関わる人が増えたときに移すことになる。
