DevOps 05

継続的インテグレーション

ワークフローは二つある。押した回数だけ動くもの（Deploy）と、 書くたびに動くもの（Test）である。 分けてあるのは、片方が失敗しても、もう片方の判断を邪魔しないためである。

Test

push と pull_request で動く。 型、Biome、共有スタイルの一致、移行の規約、テスト、ビルドをこの順で通す。

手順拾うもの
pnpm schema:apply移行そのものが流れるか
pnpm check型、整形、共有スタイルのずれ、定義の無い class、危ない移行
pnpm test制約と認証の振る舞い（31件）
pnpm build型検査では拾えないビルド時の失敗
ブラウザ試験はここで走らせていない

ブラウザで押して確かめる（pnpm e2e）は、 まず手元で確かめるための道具として入れた。 runner にブラウザを落とす時間が毎回かかるので、必要になったときに決める。

実データベースを立てる

テストは実物に対して行う。 CHECK 制約や複合外部キーが本当に効くかは、実物でしか確かめられない。 そのため postgres:18 をサービスコンテナとして立てる。

作業用データベースは要らない

Atlas が中身を作り直す作業用データベースが要るのは、差分を計算するときだけである。 migrate apply は接続先ひとつで足りる。

scripts/atlas.mjs は、diff のときだけ ATLAS_DEV_URL を要求する。 CI で余分なデータベースを用意しなくて済む。

タイムゾーンは UTC に固定する。 timestamptz の入出力はセッションの設定で変換されるので、 手元と揃っていないとテストの結果が変わる。

Atlas は先に用意し、キャッシュする

Atlas は Node の依存ではなく単体のバイナリである。 pnpm install では入らないので、別に取る。

取り直しを避けるためキャッシュするが、そのためには版が決まっている必要がある。 -latest のままではキャッシュの鍵を作れない。

key: atlas-${{ runner.os }}-${{ runner.arch }}-${{ env.ATLAS_VERSION }}
-latest は canary を返す

鍵の都合とは別に、-latest には避けたい理由がある。 実際に取ってみると v1.3.4-cdeb6c3-canary が入った。 安定版は v1.3.0 である。

スキーマを移す道具が、日によって別のものになる。 版を .atlas-version に固定し、手元の手順と CI と Dockerfile が 同じファイルを読むようにした。

キャッシュから戻したときも通るよう、実行権限と PATH は毎回そろえる。 インストールの手順だけを条件付きにしている。

Deploy

手で起こす（workflow_dispatch）。 イメージを作り、レジストリへ push するところまでを行う。

VPS への反映まではやらない

マイグレーションを流す順序を、人が見て決める必要があるためである。

段階的な変更の手順は 「先にスキーマ、あとからコード」で成り立っている。 自動で up -d まで進むと、その順序を守れない。

secret内容
DOCKER_REGISTRY_HOSTレジストリのホスト
DOCKER_REGISTRY_USERNAMEログインに使う名前
DOCKER_REGISTRY_PASSWORDログインに使うパスワード

権限を絞る

どちらのワークフローも permissions: contents: read で動く。

やることは checkout と、外部のレジストリへの push だけである。 GitHub 側への書き込みは要らない。 公開リポジトリでは、ジョブ中に走るコードすべてにトークンが渡る。 必要のない権限を持たせない。

あわせて checkout に persist-credentials: false を付け、 作業ディレクトリに資格情報を残さない。

アーキテクチャ

runner も VPS も x86_64 である。 この開発環境（devcontainer）は aarch64 なので、手元で作ったイメージは VPS では動かない。 手元のビルドは Dockerfile の確認までにとどめ、送るものは CI が作る。
