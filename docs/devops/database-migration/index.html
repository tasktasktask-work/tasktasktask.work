DevOps 03

スキーマ移行

Atlas を使い、スキーマを宣言的に定義する。 テーブルと索引と制約は Atlas が見る。関数とトリガは見ない。 その線引きが、この構成のいちばん大事なところである。

Atlas を入れる

Atlas は Node の依存ではなく、単体のバイナリである。 pnpm install では入らない。

ARCH=$(uname -m | sed "s/x86_64/amd64/;s/aarch64/arm64/")
curl -fsSL -o atlas "https://release.ariga.io/atlas/atlas-linux-$ARCH-$(cat .atlas-version)"
chmod +x atlas && sudo mv atlas /usr/local/bin/

入っていない状態で pnpm schema:* を実行すると、この手順を案内して止まる。

版は .atlas-version に固定してある

-latest を使わない。canary ビルドが返るためである。 実際に -latest で入れたときの版は v1.3.4-cdeb6c3-canary だった。 スキーマを移す道具が、日によって別のものになるのは避けたい。

この一つのファイルを、手元の手順と CI と Dockerfile が読む。 版を上げるときはここだけを書き換える。

置き場所

schema/            スキーマの正本。Atlas が読む
  02_organizations.sql
  03_users.sql
  ...
  10_notifications.sql

db/
  functions.sql    関数とトリガ。Atlas の管理下に置かない

migrations/        Atlas が生成する。手で書かない
  20260905155615_initial_schema.sql
  atlas.sum

atlas.hcl          接続先と、作業用データベースの指定
Atlas が扱えないもの

無料の範囲では、拡張（CREATE EXTENSION）と関数とプロシージャを扱えない。 schema/ に書くと migrate diff の時点でエラーになる。

Error: extensions are available to logged-in users only. Use 'atlas login' to access this feature
Error: functions and procedures are available to logged-in users only.

この制約が、二つの設計判断を導いた。

  • 拡張を使わない。 citext をやめ、メールアドレスは小文字に揃えて text に保存する
  • 関数とトリガを分ける。 db/functions.sql に置き、マイグレーションの適用後に流す

分けた関数を Atlas が消しにいかないか

確かめた。関数とトリガを手で作った状態で migrate diff を流しても、 Atlas は何も生成しない。読めないものは差分の対象にもならない。

$ atlas migrate diff after_triggers --env local
The migration directory is synced with the desired state, no changes to be made
Atlas Pro に移るときは見直す

この扱いが成り立つのは、Atlas が関数を読めないからである。 atlas login をして Pro の機能が有効になると、 Atlas は関数とトリガも差分の対象にする。 schema/ に無いそれらを「消すべきもの」と判断しうる。

作業用データベースが要る

Atlas は差分を計算するために、空のデータベースを一つ使う。 そこに宣言どおりのスキーマを組み立て、実際のデータベースと比べる。 実行のたびに中身を作り直すので、他と共有してはいけない。

# .env
DATABASE_URL="postgres://.../tasktasktask_work_local?sslmode=disable"
ATLAS_DEV_URL="postgres://.../tasktasktask_work_atlas?search_path=public&sslmode=disable"

Docker があるなら docker://postgres/18/dev?search_path=public でもよい。 その場合はコンテナを都度立ち上げるので、データベースを用意しなくて済む。

.env はスクリプトが読む

atlas は別のプロセスなので、.env の中身は自動では渡らない。 シェルに環境変数を入れずに atlas を直接叩くと、接続先が空になって sql/sqlclient: missing driver で止まる。

pnpm schema:* は scripts/atlas.mjs を経由し、 .env を読んでから atlas を起動する。 atlas を直接叩かず、pnpm のスクリプトを使うこと。

手順

コマンドすること
pnpm schema:diff <名前>schema/ と現状の差を migrations/ に書き出す
pnpm schema:apply未適用のマイグレーションを流し、続けて db/functions.sql を流す
pnpm schema:statusどこまで適用されているかを見る
pnpm schema:functions関数とトリガだけを流し直す
pnpm schema:lint生成された移行を、下の規約に照らして検査する
pnpm schema:hashatlas.sum を作り直す（手で直したときだけ）

変更するときは schema/ のファイルを編集し、pnpm schema:diff で差分を作る。 migrations/ を手で書かない。atlas.sum が合わなくなる。

生成されたSQLを必ず読む

これを守らないと壊れる

Atlas は「宣言に合わせる」ためのSQLを作る。 列の名前を変えたつもりでも、古い列を削除して新しい列を追加するSQLが生成されることがある。 データは失われる。

列名の変更、型の変更、制約の追加。 このいずれかを含む差分は、生成されたファイルを開いて確認する。 必要なら手で書き換え、pnpm schema:hash で atlas.sum を作り直す。

移行の検査

atlas migrate lint は v0.38 から Pro 限定になった。 代わりに pnpm schema:lint が、以下に書く規約そのものを検査する。 汎用の検査より、この構成で守りたいことを直接かけるほうが効く。

規則拾うもの
destructiveDROP TABLE / DROP COLUMN / DROP CONSTRAINT
column-type-changeALTER COLUMN ... TYPE
index-not-concurrentCONCURRENTLY のない索引作成
check-not-validNOT VALID のない CHECK 制約の追加
set-not-nullSET NOT NULL

下の三つは、その移行で新しく作られたテーブルが対象なら見逃す。 走査すべき既存の行が無いためである。 最初の移行が素通りするのはこの理由による。

承知のうえで通したいときは、その文の直前に理由を書く。

-- lint-ok: 空のテーブルなので走査するデータがない
CREATE INDEX "threads_by_x" ON "threads" ("x");

理由を書かせるのは、抑制した判断が後から読めるようにするためである。

破壊的な変更の手順

列の削除や型の変更は、一度のデプロイで行わない。 アプリケーションの新旧が同時に動く瞬間があるためである。

  1. 足す。新しい列を NULL 許容で追加する。既存のコードは触らない
  2. 両方書く。新旧の列に同じ値を書くコードをデプロイする
  3. 埋める。既存行の新しい列を埋めるスクリプトを流す
  4. 読み替える。読み取りを新しい列に切り替えてデプロイする
  5. 消す。古い列を削除する

各段階のあいだに、実際に動いていることを確認する時間を置く。 問題が起きたら前の段階に戻れる。

制約の追加

既存のテーブルに CHECK 制約や NOT NULL を足すとき、 Postgres はテーブル全体を走査してロックを取る。 数万件なら一瞬だが、習慣として NOT VALID を経由する。

-- 1. 既存行を検査せずに制約を足す（ロックが短い）
ALTER TABLE threads
  ADD CONSTRAINT threads_progress_range
  CHECK (progress BETWEEN 0 AND 100) NOT VALID;

-- 2. 別途、既存行を検査する（この間も書き込める）
ALTER TABLE threads VALIDATE CONSTRAINT threads_progress_range;

インデックスの追加

必ず CONCURRENTLY を付ける。 付けないと、作成中そのテーブルへの書き込みが止まる。

CREATE INDEX CONCURRENTLY threads_by_assignee
  ON threads (assignee_user_id, ends_on) WHERE deleted_at IS NULL;

この文はトランザクションの中で実行できない。 Atlas の生成したファイルに他の文と混ざっていたら、別のファイルに分ける。

分けたファイルの先頭に、トランザクションを張らせない指示を置く。 Atlas の既定は「ファイル一つにつき一トランザクション」である。

-- atlas:txmode none

-- 巡回が拾う行の索引を張り替える
DROP INDEX "notifications_pending_email";

CREATE INDEX CONCURRENTLY "notifications_pending_email"
  ON "notifications" ("created_at")
  WHERE ((emailed_at IS NULL) AND (email_gave_up_at IS NULL));
指示の後ろに空行が要る

-- atlas:txmode none の直後にコメント行が続くと、 Atlas はこの指示を読まない。 黙って無視され、適用したときに CREATE INDEX CONCURRENTLY cannot run inside a transaction block で落ちる。

指示は一行目に置き、その次を空行にする。 説明を書くのは、そのあとである（2026-09-08 に踏んだ）。

索引の条件だけを変えるときは、先に落としてから張る。 張ってから落とす順にすると、途中で同じ名前の索引が二つ要ることになり、 スキーマの正本と食い違う。 そのあいだ総なめになるだけなので、使い手が巡回しか居ない索引ならこれで足りる。

途中で落ちたとき

トランザクションを張らないファイルは、途中まで進んだ状態で止まりうる。 落とすところまでは通って、張るところで落ちる、という止まり方である。

そのまま流し直してよい。 Atlas は文の単位で進み具合を記録しており、続きから再開する。 落とす文が二度実行されて index ... does not exist になることはない。

$ atlas migrate status --dir file://migrations --url "$DATABASE_URL"

Migration Status: PENDING
  -- Current Version: 20260908004350 (1 statements applied)
  -- Next Version:    20260908004350 (1 statements left)
  -- Executed Files:  4 (last one partially)

Last migration attempt had errors:
  -- SQL:   CREATE INDEX CONCURRENTLY "notifications_pending_email" ...
  -- ERROR: ...

記録は atlas_schema_revisions にあり、 applied と total の食い違いが、途中で止まった印である。 原因を取り除いてから流す。 原因が残ったまま流し直しても、同じ文で同じように落ちる。

無効な索引が残ることがある

CREATE INDEX CONCURRENTLY は、走っている途中で落ちると 使われない索引を残す。行は増え続けるのに検索には使われない、という状態になる。

SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;

出てきたら手で落とす。落としてから流し直せば、張り直される。 Atlas は索引が有効かどうかまでは見ない。

ここに書いたことは、2026-09-08 に手元で確かめた。 索引の作成だけが失敗するイベントトリガを仕掛けて途中で落とし、 取り除いてから流し直して、正本と一致するところまでを見ている。

適用のタイミング

アプリケーションの起動時に自動で流さない。 コンテナが複数立ち上がると、同時に流れて衝突する。

デプロイの手順として、アプリケーションを入れ替える前に、独立した手順として実行する。 上の段階的な手順が成り立つのは、この順序を守る場合に限られる。

適用したあとに確かめる

制約が意図どおり効いているかは、実物でしか確かめられない。 pnpm test が、実データベースに対して次を検査する。

  • 議論と質問に期間を入れられないこと
  • 議論と質問の進捗率が 0 か 100 しか取らないこと
  • 親子がプロジェクトをまたげないこと
  • アーカイブを経ないと削除できないこと
  • スレッド番号が組織の中で一意であること
  • updated_at のトリガが効いていること
  • date 列が文字列として返ること

各テストはトランザクションの中で走り、最後に巻き戻す。 後片付けを書かずに済み、テストどうしが干渉しない。
