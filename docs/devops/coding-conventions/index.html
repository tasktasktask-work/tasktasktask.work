DevOps 02

コーディング規約

ORM を使わない構成では、規律の一部を人が持つことになる。 ここに書くのは、機械が守ってくれないものだけである。

権限の条件を落とさない

マルチテナントで最も起きてはならないのは、他社のデータが混ざることである。 WHERE organization_id = $1 を書き忘れると、それが起きる。

規約

データベースへのアクセスは、必ず組織を第一引数に取る関数を通す。 ページやAPIのハンドラから pool.query を直接呼ばない。

// 良い例：組織を型で強制する
type OrgScope = { organizationId: string; userId: string };

export async function listThreads(scope: OrgScope, projectId: string) {
  return db.query(
    `SELECT ... FROM threads
      WHERE organization_id = $1 AND project_id = $2 AND deleted_at IS NULL`,
    [scope.organizationId, projectId],
  );
}

// 悪い例：呼ぶ側が条件を足すかどうかに依存する
export async function listThreads(projectId: string) { ... }

すべてのテーブルが organization_id を直接持つのは、 この条件を結合なしで書けるようにするためである。

スコープに書いてある役割を、信用しない

OrgScope には isOrgAdmin が入っている。 所属から組み立てた値なので正しいが、正しさは組み立てた経路を通ったときだけ保証される。 呼ぶ側は好きな値のスコープを作れる。

規約

scope.isOrgAdmin は画面の出し分けにだけ使う。 書き込みの可否と、出す情報の絞り込みは、そのつど SQL の中で確かめる。

// #lib/db.ts が断片を持っている。引数の位置を渡して埋め込む
export function orgAdminExists(orgParam: string, userParam: string): string;
export function orgMemberExists(orgParam: string, userParam: string): string;

// 良い例：更新できるかを SQL の側で決める
await pool.query(
  `UPDATE organizations
      SET name = $3
    WHERE id = $1 AND deleted_at IS NULL
      AND ${orgAdminExists('$1', '$2')}`,
  [scope.organizationId, scope.userId, name],
);

// 悪い例：呼ぶ側の申告で決める
if (scope.isOrgAdmin) { await pool.query(`UPDATE organizations SET name = $2 ...`); }

返す情報を絞るときも同じである。 メンバー一覧のメールアドレスは CASE WHEN ... THEN u.email ELSE NULL END で出し分ける。 呼ぶ側で絞る形にすると、その一箇所を忘れたときに漏れる。

この「信用しない」は、偽ったスコープを渡すテストで固定してある （tests/organization.test.ts の fakedAdminScope）。

フォームから届く id を信じない

Server Action が受け取ってよいのは、URL に現れる名前だけである。 組織の slug と、プロジェクトのキー。 対象の id は、その名前からサーバ側で引き直す。

// 良い例：slug とキーを受け取り、閲覧の判定を通して引き直す
const found = await currentScope(slug);
const project = await resolveProject(found.scope, key);

// 悪い例：フォームの hidden から id を受け取る
const projectId = form.get('projectId');

悪い例では、他のプロジェクトの id を書いたフォームを投げるだけで 閲覧の判定が丸ごと飛ぶ。 引き直す形にしておけば、見えないものは掴めない。

id を隠しても守りにはならない。 推測できないから安全なのではなく、 受け取った値を確かめているから安全である。

書き換える動線を、リンクにしない

Next.js の Link は、画面に現れた時点で行き先を先読みする。 押していないのに、そのパスのサーバ側が動く。

だから GET で状態を変えてはいけない。 通知を押すと既読になる動線を素直に書くとリンクになるが、そうすると マウスを乗せただけで既読になり、押していない通知が消える。

規約

状態が変わる動線は、フォームの送信にする。 行全体を押させたいなら、行そのものを <button type="submit"> にする。 見た目はリンクでも、実体は POST である。

// 良い例：押すと既読にして、行き先はサーバが決める
<form action={openNotificationAction}>
  <input type="hidden" name="id" value={row.id} />
  <button className="p-notif" type="submit">…</button>
</form>

// 悪い例：先読みで既読になる
<Link href={`/o/${slug}/n/${row.id}`}>…</Link>

引き換えに、新しいタブで開けなくなる。 絞り込みや並べ替えのように、状態を変えない切り替えはリンクのままでよい。

他人の見え方で引くときも、判定は一つ

閲覧できるプロジェクトの判定は #lib/db.ts にしか無い。 ほとんどの問い合わせはログイン中の一人について引くので、 VISIBLE_PROJECT_IDS（$1 と $2 を埋めたもの）で足りる。

足りないのは通知の宛先を絞るときである。 ウォッチしている人ごと、指名された人ごとに、その人から見えるかを問う。 引数の位置ではなく、行の列（w.user_id など）を渡すことになる。

// 断片を組み立てる関数。埋め込む先ごとに引数の位置が変わる
export function visibleProjectIds(orgParam: string, userParam: string): string;

// いちばん多い呼ばれ方を固定したもの
export const VISIBLE_PROJECT_IDS = visibleProjectIds('$1', '$2');

// 行ごとに違う人で引く
AND $6::uuid IN (${visibleProjectIds('$1', 'w.user_id')})

形が違うからといって書き写さない。 同じ判定が二箇所にある状態は、片方だけ直したときに穴が開く。 実際に一度開けた（権限判定のテスト）。

組織のスコープを取らないもの

データベースを触る関数は OrgScope を第一引数に取る。 例外は二つある。認証と、アカウントの設定である。

// #features/account/queries.ts
export async function setEmailNotifications(userId: string, enabled: boolean)

これは組織の境界を越えているのではない。 users.email_notifications_enabled は組織の外側にある値で、 所属しているすべての組織に効く。

見分け方は「どの組織で操作したかを問えるか」である。 問えないなら、スコープを渡しても嘘の引数になる。 画面の URL も揃える。この設定は /o/{slug}/... ではなく /me にある。

外への呼び出しを、取引の中で待たない

SMTP のような外部への呼び出しは、いつ返るかを決められない。 行のロックを握ったまま待つと、相手が詰まっているあいだ、その行に触れる問い合わせが並ぶ。

// 掴む取引。ここで試行の回数を増やし、閉じる
const rows = await claim(RECIPIENTS_PER_PASS);
// 取引の外。ここでようやく送る
await sender.send(composeNotificationMail(...));
// 結果を書き戻す
await markSent(ids);

回数を掴む側で増やすのは、送信の途中で落ちる束を外すためである。 送ってから増やす形だと、その束は回数が永久に 0 のまま、 起動のたびに同じ場所で落ち続ける。

拾って送る仕掛けには、決着の付け方が要る

送らないと決めた行にも印を付ける。 付けないと、その行は毎回の巡回に拾われ続ける。

拾う順が古い順なら、居座った行が枠を先に取り、後ろに並んだものへ永久に届かない。 送らないことと、拾うのをやめることは、同じ操作でなければならない。

繰り返しの殻に、判断を置かない

一定間隔で回るものは、一巡ぶんを関数に切り出す。 ループのほうは間隔を計るだけにする。

判断をループの中に置くと、確かめるのに間隔ぶん待つ仕掛けになる。 そうなると誰も確かめなくなる。

// 判断はここ。テストから直接呼べる
export async function deliverPendingNotifications(
  sender: MailSender = mailSender,
  origin: string = env.APP_ORIGIN,
): Promise<DeliveryReport>

// 殻。間隔を計るだけ
export function startNotificationMailLoop(): void

外へ出るものは引数で受け取り、既定値に本物を置く。 テストは記録するだけの偽物を渡す。 文面の組み立ては、さらにその外へ出してデータベースも要らなくしてある。

互いを呼びそうになったら、判定の無い側を切り出す

機能が増えると、二つの模組が互いを必要とする場面が出る。 タグとスレッドがそうだった。スレッドを立てるときにタグを付けるので #features/thread/queries.ts がタグ側を呼ぶ。 一方でタグ側は、書き込みの可否を判定するために THREAD_WRITABLE を読む。

逃げ道は二つある。判定を書き写すか、書き写さずに済む形へ分けるかである。 書き写さないほうを採る。

src/features/tag/
  queries.ts   THREAD_WRITABLE を読む。判定を持つ側
  attach.ts    判定を持たない。行を入れるだけ

src/features/thread/queries.ts
  attach.ts だけを読む

切り出す境目は「判定を持つかどうか」に置く。 attach.ts の関数は、呼ぶ側が可否を確かめ終えている前提で書く。 そのことを模組の先頭に書いておかないと、 次に触る人が「ここには判定が無い」を欠落と読む。

画面の側から読まれるものにも同じ切り分けが要る。 色見本の定義は colors.ts にある。 queries.ts に置くと、色を出したいだけの部品が pg ごとブラウザ向けの束に入る。

URL の組み立てを一枚に閉じ込める

typedRoutes は、動的な区間がひとつなら Link に渡す文字列をそのまま検査してくれる。 /o/{slug}/p/{key} のように二つ並ぶと推論が通らず、型を当て直すことになる。

// src/features/project/path.ts
export function projectPath(slug: string, key: string): Route {
  return `/o/${slug}/p/${key}` as Route;
}

当て直した箇所では綴りの誤りも検査されない。 だから画面の側では URL の文字列を書かず、この関数を呼ぶ。 検査の効かない範囲を、探せる大きさに保つためである。

閲覧できるかの判定を一箇所に置く

非公開プロジェクトの判定は、 公開設定、プロジェクトメンバー、組織管理者の三つを見る必要がある。 この論理を各所に散らすと、必ずどこかで漏れる。

// #lib/db.ts に一箇所だけ書く
export const VISIBLE_PROJECT_IDS = `
  SELECT p.id FROM projects p
   WHERE p.organization_id = $1
     AND p.deleted_at IS NULL
     AND EXISTS (...組織のメンバーであること...)
     AND (p.visibility = 'public'
          OR EXISTS (...project_members...)
          OR EXISTS (...組織管理者...))`;
組織の所属は、いちばん外側で見る

枝の中に入れると、project_members の枝だけが所属を見ないことになる。 組織から外された人でも、プロジェクトのメンバー行が残っていれば非公開が見えてしまう。

実際にこの形で書いていた。tests/permission.test.ts で振る舞いを固定してある。

スレッドの一覧も、担当スレッド一覧も、 将来の検索も、この副問い合わせを使う。

一覧の取得は一回のクエリで済ませる

ORM がないため N+1 は自動では検出されない。 一覧を作るとき、行ごとにクエリを投げない。

スレッド一覧はタグと担当者と子の件数を必要とするが、 LEFT JOIN LATERAL や json_agg でまとめて取る。

SELECT t.*,
       u.display_name AS assignee_name,
       COALESCE(tags.list, '[]'::json) AS tags,
       (SELECT count(*) FROM threads c
         WHERE c.parent_thread_id = t.id AND c.deleted_at IS NULL) AS child_count
  FROM threads t
  LEFT JOIN users u ON u.id = t.assignee_user_id
  LEFT JOIN LATERAL (
    SELECT json_agg(json_build_object('name', g.name, 'color', g.color)) AS list
      FROM thread_tags tt JOIN tags g ON g.id = tt.tag_id
     WHERE tt.thread_id = t.id
  ) tags ON true
 WHERE ...

SQL の書き方

  • SQL は文字列リテラルとして書き、値は必ずプレースホルダで渡す。文字列連結で値を埋め込まない
  • キーワードは大文字、識別子は小文字
  • SELECT * を本番のコードで使わない。列が増えたときに何が返るかが変わる
  • 論理削除の条件（deleted_at IS NULL）を書き忘れない。削除済みが混ざる

データベースが守れない不変条件

制約の多くはスキーマ側に置いた。 親子がプロジェクトをまたがないことのように、 複合外部キーで表現できるものもある。

それでも次の三つは、書く手段がない。 アプリケーション側で守る。守り忘れても、データベースは何も言わない。

親子の循環参照

階層に深さの制限がないため、CHECK では表現できない。 親を設定するときに祖先を辿り、自分自身が現れないことを確認する。

WITH RECURSIVE ancestors AS (
  SELECT id, parent_thread_id, 1 AS depth
    FROM threads WHERE id = $1        -- 親にしようとしているスレッド
  UNION ALL
  SELECT t.id, t.parent_thread_id, a.depth + 1
    FROM threads t
    JOIN ancestors a ON t.id = a.parent_thread_id
   WHERE a.depth < 50                 -- 万一の循環で問い合わせが止まらなくなるのを防ぐ
)
SELECT EXISTS (SELECT 1 FROM ancestors WHERE id = $2) AS would_cycle;

深さ50は仕様上の上限ではなく、暴走を止める安全弁である。

最後の組織管理者を外せない

行数の下限は CHECK では書けない。 役割を変更するときと、メンバーを外すときの両方で確認する。

ただし、数えてから変えるまでのあいだが空く。 二人の管理者が同時に互いを降ろすと、どちらも「自分のほかにもう一人いる」と読んで通る。 先に管理者の行を掴んでから数える。

-- 同じトランザクションの中で、先に鍵をかけてから数える
SELECT user_id
  FROM organization_members
 WHERE organization_id = $1
   AND role = 'admin'
   AND deleted_at IS NULL
 ORDER BY user_id
   FOR UPDATE;

二つめの要求は、一つめが終わるまで待つ。 管理者が増える側は待たせない。増えるぶんには下限を割らないためである。

掴んだ行の中に自分がいるかどうかで、操作してよいかも同時に決まる。 役割の確認と、数の確認と、順番待ちが、この一本にまとまっている。

これを怠ると、組織が誰にも操作できない状態になる。 復旧にはデータベースへの直接の介入が要る。

プロジェクトキーは作成後に変更できない

形式は CHECK で縛れるが、「作成後は変えられない」は更新時の判断になる。 プロジェクトを更新する関数で、key を受け取らない形にするのが確実である。

// 良い例：更新できる項目だけを引数にする
type ProjectUpdate = { name: string; description: string; visibility: Visibility };

// 悪い例：全項目を受け取り、key を無視する実装に頼る
type ProjectUpdate = Partial<Project>;

型で受け取れなくしておけば、うっかり渡す経路そのものがなくなる。

モジュールの読み込みで実行時の設定を要求しない

接続先や送信先といった実行時の設定は、 最初に使われるときに読む。読み込んだ瞬間に読まない。

// 書かない：読み込みだけで DATABASE_URL を要求する
export const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

// 書く：最初に触られたときに作る
export const pool = lazy(createPool);
イメージを作るのに本番の設定が要る状態になる

next build はページの情報を集めるために、モジュールを読み込む。 読み込みで設定を要求すると、ビルドが接続先を求めて失敗する。

この誤りは長く隠れる。開発機には .env があり、 それがビルド文脈へ写り込んでいるあいだは通ってしまう。 .dockerignore で .env を外した時点で、 初めて表に出た。

#lib/lazy.ts がこの遅延を引き受ける。 呼ぶ側の書き方は変わらない。

対象読み込み時最初に触ったとき
env何もしない環境変数を検証する
pool何もしない接続プールを作る
mailSender何もしない送信の実装を選ぶ

設定が足りなければ、触った時点で落ちる。 黙って動き出して、後の画面で初めて壊れることはない。

タイミングが仕様なので、tests/lazy.test.ts で固定してある。

日付と時刻の扱い

型は二つしか使わない。

用途型例
課題の期間datestarts_on, ends_on
記録の時刻timestamptzcreated_at, expires_at, read_at

タイムゾーンを持たない timestamp は使わない。 この型は壁掛け時計の読みをそのまま保存し、基準点を持たない。 異なる地域から書かれた二つの行を並べても、どちらが先かを比較できない。

期間を date にしたのは、 組織ごとにタイムゾーンを設定できるようにしたためである。 締切に時刻を持たせると、組織の設定を変えた瞬間に既存の日付が前後する。 日付だけなら、その事故が構造的に起きない。

セッションの TimeZone に頼らない

timestamptz はタイムゾーンを保存していない。 格納されているのは UTC における時刻の一点だけで、 入力と出力の変換にはセッションの TimeZone 設定が使われる。

規約

データベース側のセッション TimeZone は UTC に固定する。 表示のための変換は、アプリケーションが organizations.timezone を引数として渡して行う。

接続プールがその理由である。 ひとつのプールが複数の組織のリクエストを処理するので、 リクエストごとに SET TIME ZONE を実行すると、 返却された接続に設定が残って次のリクエストへ漏れる。

-- 良い例：組織のタイムゾーンを引数で渡す
SELECT id, body, created_at AT TIME ZONE $2 AS created_local
  FROM comments
 WHERE thread_id = $1;

AT TIME ZONE は付けた側の型によって逆向きに働く。 timestamptz に付けると timestamp になり、 timestamp に付けると timestamptz になる。 読むときに向きを取り違えやすいので、 この演算子は表示のための変換にだけ使い、保存する値には使わない。

画面に出すときの変換

timestamptz はドライバが Date にして返す。 Date は UTC の一点なので、この値は正しい。 ずれるのは、それを文字にするときである。

toLocaleString() をそのまま呼ぶと、 サーバのタイムゾーンで書き出される。 複数の組織を捌く一台のサーバが、全員に同じ壁掛け時計を見せることになる。

// 悪い例：サーバの時計で書き出される
row.updatedAt.toLocaleString('ja-JP');

// 良い例：組織のタイムゾーンを渡す
import { formatDateTime } from '#lib/datetime.ts';
formatDateTime(row.updatedAt, scope.timezone);

変換は src/lib/datetime.ts に集めてある。 組織のタイムゾーンは組織のスコープが運んでくるので、 画面はそれを渡すだけでよい。

date 列はこの変換を通さない。 '2026-09-08' という文字列のまま来ており、一度 Date にした時点でずれる。

インデックスに使える式と使えない式

timestamptz から日付を取り出す式は、 セッションの設定によって結果が変わるため STABLE であり、 インデックスや生成列に使えない。

-- 不可。timestamptz::date はセッション設定で結果が変わる
CREATE INDEX ON comments ((created_at::date));

-- 可。タイムゾーンを定数で固定すれば結果が一意に定まる
CREATE INDEX ON comments (((created_at AT TIME ZONE 'Asia/Tokyo')::date));
実装時に確認すること

後者が通るのは timezone(text, timestamptz) が IMMUTABLE として 登録されているためだが、まだ実機で確認していない。 使う前に \df+ timezone で volatility を確かめる。

pg ドライバの型変換を上書きする

pg の既定の型変換には、上の設計を壊す挙動がある。

OID型既定で返るもの
1184timestamptzJS の Date。Date は UTC の一点なので正しい
1114timestampJS の Date。Node プロセスのローカル時刻として解釈される
1082dateJS の Date。ローカルの午前0時になる

問題は三行目である。 starts_on に 2026-09-08 が入っていても、 ドライバはこれを「ローカルの9月8日0時」の Date にする。 Node が JST で動いていれば、その瞬間は UTC では9月7日15時である。

const { rows } = await db.query('SELECT starts_on FROM threads WHERE id = $1', [id]);
rows[0].starts_on.toISOString().slice(0, 10);
// → "2026-09-07"   日付が1日ずれる
選んだ型が、ドライバの既定動作で無効になる

タイムゾーンの事故を避けるために期間を date にしたのに、 pg がそれを Date へ引き戻す。 接続を作る場所で、必ず型パーサを差し替える。

import pg from 'pg';

// date は Date に変換せず 'YYYY-MM-DD' の文字列のまま扱う
pg.types.setTypeParser(pg.types.builtins.DATE, (v) => v);

// timestamp（タイムゾーンなし）は使わない方針なので、
// 混入したら気づけるようにしておく
pg.types.setTypeParser(pg.types.builtins.TIMESTAMP, (v) => {
  throw new Error(`timestamp 型が使われています。timestamptz か date にしてください: ${v}`);
});

二つ目のパーサは、値を返さず例外を投げる。 timestamp の列が現れることは設計の誤りなので、 黙って動くよりも止まったほうがよい。

利用者が書いた文章を画面に出す

スレッドの本文とコメントは、利用者が書いた文字列である。 これを HTML にして出すので、書いた人が仕込んだ <script> が 他人のブラウザで動かないことを、こちらが保証しなければならない。

保証しているのは streamdown である。 自前で無害化を書かない。書き足す形にもしない。

守ること

描画は必ず #features/comment/Markdown.tsx を通す。 dangerouslySetInnerHTML を新しく書かない。 無害化を通っていない経路が一本できると、そこだけが穴になる。

本文を渡す前に #lib/markdown.ts の prepare を通す。 チェックボックスと指名を、こちらのタグに置き換えるのがこの関数である。 同時に、利用者が書いた <task> と <mention> を無効にする。 通さずに渡すと、他人を指名したように見せかける文章が書けてしまう。

本文の走査は #lib/markdown.ts にだけ置く。 コードブロックとインラインコードの中を避ける判定が入っている。 書き写すと、数え方が食い違ったときに別のチェックボックスへ印が入る。

streamdown が出す class は Tailwind のユーティリティで、このプロジェクトには効かない。 体裁は data-streamdown 属性を手がかりに docs/theme.css で当てている。 表とコードブロックに付いてくる操作ボタンは controls={false} で消してある。 あれらの見た目は Tailwind でしか組まれていない。

制御構文のブロックを省略しない

if や for の本体が一文でも、必ず波括弧で囲む。

// 書かない
if (!user) redirect('/login');

// 書く
if (!user) {
  redirect('/login');
}

省略した形は、あとから一行足すときに壊れる。 波括弧が無いまま二行目を書くと、二行目は条件の外に出る。 しかも見た目のインデントは揃うので、読んでも気づけない。

Biome の style/useBlockStatements で機械的に止めている。 pnpm check が失敗するので、書いた本人が気づく。

import の書き方

解決系が三つある。TypeScript、Next（webpack）、そして Node である。 テストは Node が src/ のファイルを直接読むため、三つすべてが解決できる形に揃える。

拡張子を必ず書く

Node の ESM は拡張子を補わない。相対でもエイリアスでも省略しない。

import { pool } from '#lib/db.ts';
import { hashToken } from './token.ts';
import { LoginForm } from '#features/authentication/LoginForm.tsx';

TypeScript 側は allowImportingTsExtensions で許可している。 出力は Next が作るので、TypeScript が書き換える必要はない。

エイリアスは package.json の imports で定義する

tsconfig.json の paths は使わない。TypeScript しか知らないためである。 Node の subpath imports なら三つとも同じ定義を読む。

"imports": {
  "#lib/*":      "./src/lib/*",
  "#features/*": "./src/features/*"
}

next/headers を読み込む場所を絞る

Node からは解決できない

next パッケージには exports の定義が無く、 next/headers は Node の ESM では解決できない。 これを読み込んだファイルは、リクエストの外から動かせなくなる。

つまり next/headers を使うファイルはテストできない。

そのため、Cookie やヘッダに触る部分と、データベースに触る部分を分ける。

ファイル役割試せるか
session.tsセッションの記録、引き当て、失効試せる
cookie.tsnext/headers との橋渡しだけ試せない

分けた結果、アカウントロックの解除や マジックリンクの一度きりといった、 間違えると締め出しか乗っ取りに直結する振る舞いを、実データベースに対して試せるようになっている。

すでにある値を書き換える欄は、値を画面の側で持つ

フォームに action を渡すと、React はその処理が終わったあとに フォームを自動で戻す。戻し先は、組み立てたときの既定値である。

新しく書く画面ではこれでよい。投稿し終えた欄は空に戻ってほしい。 困るのは、すでにある値を書き換える画面のほうである。

// これだと、保存できているのに欄だけが元へ戻る
<select name="assignee" defaultValue={assigneeUserId ?? ''}>

保存そのものは通り、データベースも書き換わる。 戻るのは画面だけなので、読み込み直すまで気づけない。 「保存できていないのか、表示だけの話なのか」が使う側からは分からない。

// 値を画面の側で持ち、サーバ側が動いたら合わせ直す
const [value, setValue, settled] = useField(assigneeUserId ?? '');

<select name="assignee" value={value} onChange={(e) => setValue(e.target.value)}>

useField は src/lib/field.tsx にある。 三つめに返るのは「見えている値が、保存されている値と揃っているか」で、 保存できたことを知らせてよいかの判断に使う。

知らせは、揃っているあいだだけ出す

「保存しました」を出しっぱなしにすると、続けて欄をいじったときに 保存していない値の横に「保存しました」が残る。

同じ判断を Told にまとめてある。 settled が偽のあいだは知らせを出さない。 失敗の知らせは、揃っているかに関わらず出す。

defaultValue を使ってよいのは、戻るのが正しい欄だけである。 新しく作るフォームの初期値、招待の役割、追加する人の選択欄がこれにあたる。

この形は2026-09-08に本番で踏んだ。 スレッドの担当者を変えると、保存はされるのに選択欄が元へ戻っていた。 同じ書き方が7箇所にあり、まとめて直した。
