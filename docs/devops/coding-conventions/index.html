DevOps 02

コーディング規約

ORM を使わない構成では、規律の一部を人が持つことになる。 ここに書くのは、機械が守ってくれないものだけである。

権限の条件を落とさない

マルチテナントで最も起きてはならないのは、他社のデータが混ざることである。 WHERE organization_id = $1 を書き忘れると、それが起きる。

規約

データベースへのアクセスは、必ず組織を第一引数に取る関数を通す。 ページやAPIのハンドラから pool.query を直接呼ばない。

// 良い例：組織を型で強制する
type OrgScope = { organizationId: string; userId: string };

export async function listThreads(scope: OrgScope, projectId: string) {
  return db.query(
    `SELECT ... FROM threads
      WHERE organization_id = $1 AND project_id = $2 AND deleted_at IS NULL`,
    [scope.organizationId, projectId],
  );
}

// 悪い例：呼ぶ側が条件を足すかどうかに依存する
export async function listThreads(projectId: string) { ... }

すべてのテーブルが organization_id を直接持つのは、 この条件を結合なしで書けるようにするためである。

閲覧できるかの判定を一箇所に置く

非公開プロジェクトの判定は、 公開設定、プロジェクトメンバー、組織管理者の三つを見る必要がある。 この論理を各所に散らすと、必ずどこかで漏れる。

// 一箇所にだけ書く
export function visibleProjectsSubquery(userId: string): string {
  return `
    SELECT p.id FROM projects p
     WHERE p.deleted_at IS NULL
       AND (p.visibility = 'public' AND EXISTS (...組織メンバー...)
            OR EXISTS (...project_members...)
            OR EXISTS (...組織管理者...))`;
}

スレッドの一覧も、担当スレッド一覧も、 将来の検索も、この副問い合わせを使う。

一覧の取得は一回のクエリで済ませる

ORM がないため N+1 は自動では検出されない。 一覧を作るとき、行ごとにクエリを投げない。

スレッド一覧はタグと担当者と子の件数を必要とするが、 LEFT JOIN LATERAL や json_agg でまとめて取る。

SELECT t.*,
       u.display_name AS assignee_name,
       COALESCE(tags.list, '[]'::json) AS tags,
       (SELECT count(*) FROM threads c
         WHERE c.parent_thread_id = t.id AND c.deleted_at IS NULL) AS child_count
  FROM threads t
  LEFT JOIN users u ON u.id = t.assignee_user_id
  LEFT JOIN LATERAL (
    SELECT json_agg(json_build_object('name', g.name, 'color', g.color)) AS list
      FROM thread_tags tt JOIN tags g ON g.id = tt.tag_id
     WHERE tt.thread_id = t.id
  ) tags ON true
 WHERE ...

SQL の書き方

  • SQL は文字列リテラルとして書き、値は必ずプレースホルダで渡す。文字列連結で値を埋め込まない
  • キーワードは大文字、識別子は小文字
  • SELECT * を本番のコードで使わない。列が増えたときに何が返るかが変わる
  • 論理削除の条件（deleted_at IS NULL）を書き忘れない。削除済みが混ざる

データベースが守れない不変条件

制約の多くはスキーマ側に置いた。 親子がプロジェクトをまたがないことのように、 複合外部キーで表現できるものもある。

それでも次の三つは、書く手段がない。 アプリケーション側で守る。守り忘れても、データベースは何も言わない。

親子の循環参照

階層に深さの制限がないため、CHECK では表現できない。 親を設定するときに祖先を辿り、自分自身が現れないことを確認する。

WITH RECURSIVE ancestors AS (
  SELECT id, parent_thread_id, 1 AS depth
    FROM threads WHERE id = $1        -- 親にしようとしているスレッド
  UNION ALL
  SELECT t.id, t.parent_thread_id, a.depth + 1
    FROM threads t
    JOIN ancestors a ON t.id = a.parent_thread_id
   WHERE a.depth < 50                 -- 万一の循環で問い合わせが止まらなくなるのを防ぐ
)
SELECT EXISTS (SELECT 1 FROM ancestors WHERE id = $2) AS would_cycle;

深さ50は仕様上の上限ではなく、暴走を止める安全弁である。

最後の組織管理者を外せない

行数の下限は CHECK では書けない。 役割を変更するときと、メンバーを外すときの両方で確認する。

-- 同じトランザクションの中で、外したあとに管理者が残るかを見る
SELECT count(*) > 0 AS has_admin
  FROM organization_members
 WHERE organization_id = $1
   AND role = 'admin'
   AND deleted_at IS NULL
   AND user_id <> $2;

これを怠ると、組織が誰にも操作できない状態になる。 復旧にはデータベースへの直接の介入が要る。

プロジェクトキーは作成後に変更できない

形式は CHECK で縛れるが、「作成後は変えられない」は更新時の判断になる。 プロジェクトを更新する関数で、key を受け取らない形にするのが確実である。

// 良い例：更新できる項目だけを引数にする
type ProjectUpdate = { name: string; description: string; visibility: Visibility };

// 悪い例：全項目を受け取り、key を無視する実装に頼る
type ProjectUpdate = Partial<Project>;

型で受け取れなくしておけば、うっかり渡す経路そのものがなくなる。

モジュールの読み込みで実行時の設定を要求しない

接続先や送信先といった実行時の設定は、 最初に使われるときに読む。読み込んだ瞬間に読まない。

// 書かない：読み込みだけで DATABASE_URL を要求する
export const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

// 書く：最初に触られたときに作る
export const pool = lazy(createPool);
イメージを作るのに本番の設定が要る状態になる

next build はページの情報を集めるために、モジュールを読み込む。 読み込みで設定を要求すると、ビルドが接続先を求めて失敗する。

この誤りは長く隠れる。開発機には .env があり、 それがビルド文脈へ写り込んでいるあいだは通ってしまう。 .dockerignore で .env を外した時点で、 初めて表に出た。

#lib/lazy.ts がこの遅延を引き受ける。 呼ぶ側の書き方は変わらない。

対象読み込み時最初に触ったとき
env何もしない環境変数を検証する
pool何もしない接続プールを作る
mailSender何もしない送信の実装を選ぶ

設定が足りなければ、触った時点で落ちる。 黙って動き出して、後の画面で初めて壊れることはない。

タイミングが仕様なので、tests/lazy.test.ts で固定してある。

日付と時刻の扱い

型は二つしか使わない。

用途型例
課題の期間datestarts_on, ends_on
記録の時刻timestamptzcreated_at, expires_at, read_at

タイムゾーンを持たない timestamp は使わない。 この型は壁掛け時計の読みをそのまま保存し、基準点を持たない。 異なる地域から書かれた二つの行を並べても、どちらが先かを比較できない。

期間を date にしたのは、 組織ごとにタイムゾーンを設定できるようにしたためである。 締切に時刻を持たせると、組織の設定を変えた瞬間に既存の日付が前後する。 日付だけなら、その事故が構造的に起きない。

セッションの TimeZone に頼らない

timestamptz はタイムゾーンを保存していない。 格納されているのは UTC における時刻の一点だけで、 入力と出力の変換にはセッションの TimeZone 設定が使われる。

規約

データベース側のセッション TimeZone は UTC に固定する。 表示のための変換は、アプリケーションが organizations.timezone を引数として渡して行う。

接続プールがその理由である。 ひとつのプールが複数の組織のリクエストを処理するので、 リクエストごとに SET TIME ZONE を実行すると、 返却された接続に設定が残って次のリクエストへ漏れる。

-- 良い例：組織のタイムゾーンを引数で渡す
SELECT id, body, created_at AT TIME ZONE $2 AS created_local
  FROM comments
 WHERE thread_id = $1;

AT TIME ZONE は付けた側の型によって逆向きに働く。 timestamptz に付けると timestamp になり、 timestamp に付けると timestamptz になる。 読むときに向きを取り違えやすいので、 この演算子は表示のための変換にだけ使い、保存する値には使わない。

インデックスに使える式と使えない式

timestamptz から日付を取り出す式は、 セッションの設定によって結果が変わるため STABLE であり、 インデックスや生成列に使えない。

-- 不可。timestamptz::date はセッション設定で結果が変わる
CREATE INDEX ON comments ((created_at::date));

-- 可。タイムゾーンを定数で固定すれば結果が一意に定まる
CREATE INDEX ON comments (((created_at AT TIME ZONE 'Asia/Tokyo')::date));
実装時に確認すること

後者が通るのは timezone(text, timestamptz) が IMMUTABLE として 登録されているためだが、まだ実機で確認していない。 使う前に \df+ timezone で volatility を確かめる。

pg ドライバの型変換を上書きする

pg の既定の型変換には、上の設計を壊す挙動がある。

OID型既定で返るもの
1184timestamptzJS の Date。Date は UTC の一点なので正しい
1114timestampJS の Date。Node プロセスのローカル時刻として解釈される
1082dateJS の Date。ローカルの午前0時になる

問題は三行目である。 starts_on に 2026-09-08 が入っていても、 ドライバはこれを「ローカルの9月8日0時」の Date にする。 Node が JST で動いていれば、その瞬間は UTC では9月7日15時である。

const { rows } = await db.query('SELECT starts_on FROM threads WHERE id = $1', [id]);
rows[0].starts_on.toISOString().slice(0, 10);
// → "2026-09-07"   日付が1日ずれる
選んだ型が、ドライバの既定動作で無効になる

タイムゾーンの事故を避けるために期間を date にしたのに、 pg がそれを Date へ引き戻す。 接続を作る場所で、必ず型パーサを差し替える。

import pg from 'pg';

// date は Date に変換せず 'YYYY-MM-DD' の文字列のまま扱う
pg.types.setTypeParser(pg.types.builtins.DATE, (v) => v);

// timestamp（タイムゾーンなし）は使わない方針なので、
// 混入したら気づけるようにしておく
pg.types.setTypeParser(pg.types.builtins.TIMESTAMP, (v) => {
  throw new Error(`timestamp 型が使われています。timestamptz か date にしてください: ${v}`);
});

二つ目のパーサは、値を返さず例外を投げる。 timestamp の列が現れることは設計の誤りなので、 黙って動くよりも止まったほうがよい。

制御構文のブロックを省略しない

if や for の本体が一文でも、必ず波括弧で囲む。

// 書かない
if (!user) redirect('/login');

// 書く
if (!user) {
  redirect('/login');
}

省略した形は、あとから一行足すときに壊れる。 波括弧が無いまま二行目を書くと、二行目は条件の外に出る。 しかも見た目のインデントは揃うので、読んでも気づけない。

Biome の style/useBlockStatements で機械的に止めている。 pnpm check が失敗するので、書いた本人が気づく。

import の書き方

解決系が三つある。TypeScript、Next（webpack）、そして Node である。 テストは Node が src/ のファイルを直接読むため、三つすべてが解決できる形に揃える。

拡張子を必ず書く

Node の ESM は拡張子を補わない。相対でもエイリアスでも省略しない。

import { pool } from '#lib/db.ts';
import { hashToken } from './token.ts';
import { LoginForm } from '#features/authentication/LoginForm.tsx';

TypeScript 側は allowImportingTsExtensions で許可している。 出力は Next が作るので、TypeScript が書き換える必要はない。

エイリアスは package.json の imports で定義する

tsconfig.json の paths は使わない。TypeScript しか知らないためである。 Node の subpath imports なら三つとも同じ定義を読む。

"imports": {
  "#lib/*":      "./src/lib/*",
  "#features/*": "./src/features/*"
}

next/headers を読み込む場所を絞る

Node からは解決できない

next パッケージには exports の定義が無く、 next/headers は Node の ESM では解決できない。 これを読み込んだファイルは、リクエストの外から動かせなくなる。

つまり next/headers を使うファイルはテストできない。

そのため、Cookie やヘッダに触る部分と、データベースに触る部分を分ける。

ファイル役割試せるか
session.tsセッションの記録、引き当て、失効試せる
cookie.tsnext/headers との橋渡しだけ試せない

分けた結果、アカウントロックの解除や マジックリンクの一度きりといった、 間違えると締め出しか乗っ取りに直結する振る舞いを、実データベースに対して試せるようになっている。

_at と _on を分けているのは、 時刻を持つかどうかを名前から判別するためである。 期間は日付だけを持つので _on になる。

ドメインの語彙をコードでも使う

用語集で定めた語を、そのままコードの識別子に使う。

用語コード上の表現
課題'kadai'
議論'giron'
質問'shitsumon'

'issue' や 'discussion' という英語を当てない。 この製品の「課題」は他所の issue とは意味が違うので、 英語に置き換えた瞬間に、読む人が他所の意味で受け取る。
