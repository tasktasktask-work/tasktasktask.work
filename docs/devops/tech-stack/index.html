TypeScript 7 と Next.js 16 は組で決まっている

TypeScript 7 は Go で書き直された実装である。 型検査は速くなったが、従来の JavaScript コンパイラ API を持たない。 require('typescript') は版番号を返すだけになり、 新しい API は typescript/unstable/* に分かれた。

測ったものTypeScript 5.9.3TypeScript 7.0.2
tsc --noEmit（3回平均）1020 ms335 ms
next build の型検査—181 ms

ファイル数が少ないので起動の時間が支配的である。規模が増えれば差は開く。

API が無いことの影響

Next.js は設定ファイルの読み込みとビルド時の型検査で、この API を使っていた。 そのため 16.2.11 より前の Next では TypeScript 7 が動かない。 Next 自身が版を見て拒否する。

TypeScript 7.0.2 is not supported by this version of Next.js.
The TypeScript 7 native compiler does not provide the JavaScript compiler API
that Next.js requires. Install TypeScript 6 ... or upgrade to a Next.js
v16.2.11 or later to get support for TypeScript 7.

つまりこの二つは片方だけ上げられない。 どちらかを戻すなら、もう一方も戻すことになる。

あわせて二つの調整が要った。

  • CSS の副作用 import に型宣言が要る。 types/assets.d.ts に declare module '*.css'; を置いた
  • エディタは typescript.tsdk を指定しない。 TypeScript 7 は lib/tsserver.js を持たず、言語サーバは LSP として提供される。 指すと VSCode が読み込みに失敗する

整形と Lint に Biome を使っていることも、 この移行を軽くしている。 typescript-eslint は TypeScript の API に依存するため、 ESLint を使っていたら移行できなかった。

ORM を使わない

SQLを直接書く。 threads のように制約が集中したテーブルでは、 スキーマそのものが設計書として読める状態を保ちたいためである。

複合外部キーによる「親子は同じプロジェクトに閉じる」という保証は、 多くの ORM では自然に表現できない。 スキーマ定義がSQLのままであれば、この種の制約を素直に書ける。

この選択が背負うもの

型の安全は自分で作ることになる。 クエリの結果に型を付ける仕組みを、実装の早い段階で決める必要がある。

また、N+1 の検出も自動では行われない。 コーディング規約でクエリの置き場所を定め、 一覧の取得は必ず一回のクエリで済ませる方針を守る。

メール送信を抽象で包む

Cloudflare Email Service を使うが、アプリケーションからは MailSender 越しにしか呼ばない。

interface MailSender {
  send(mail: { to: string; subject: string; text: string }): Promise<void>;
}

// 開発中
class ConsoleMailSender implements MailSender { /* 標準出力に書く */ }
// 本番
class SmtpMailSender implements MailSender { /* smtp.mx.cloudflare.net:465 */ }

SMTP で送るため、Cloudflare 固有の実装に縛られない。 別のサービスへ移すときも接続設定の差し替えで済む。 クライアントは nodemailer である。 Node に組み込みの SMTP クライアントは無く、自前で書くと認証方式と TLS と MIME の組み立てを抱えることになる。

抽象は二つ目の役目も持っている。 引数で受け取る形にしてあるので、巡回のテストは 記録するだけの偽物を渡して呼べる。

送れなかった理由を、抽象の側で分けている

MailFailure は恒久（宛先が無い）と一時（いまは受けられない）を持つ。 SMTP の 5xx と 4xx にあたる。

呼ぶ側がこの区別を持たないと、諦めるかもう一度試すかを回数だけで決めることになり、 送信先が数分止まっただけで、その間の通知がまとめて捨てられる。

無料枠の上限を見込んでおく

Cloudflare Email Service の無料枠は月3,000通である。 100人規模で通知が動けば、 ひとりあたり月30通で上限に達する。実運用では有料枠が前提になる。

任意の宛先へ送るには Workers Paid プランと送信ドメインのオンボーディングが要る。 それを済ませるまでは、検証済みの宛先にしか届かない。
