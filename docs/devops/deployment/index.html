DevOps 04

デプロイ構成

VPS では複数のサービスが動いている。 このアプリはそこへ相乗りする。 ソースコードは VPS に置かず、ビルド済みのイメージだけを送る。

構成

クライアント ═SSL═> Cloudflare ──> VPS
                                    │
                                    ├── nginx-proxy   （稼働中）
                                    │     VIRTUAL_HOST で振り分ける
                                    │
                                    ├── postgres      （稼働中）
                                    │
                                    └── tasktasktask-work-app
                                          Next.js / :3000
                                          通知メールの巡回（60秒ごと）
                                          ボリューム: ./data/attachments

ネットワークは二つに参加する。 nginxproxy-network で振り分けを受け、 postgres-network でデータベースへ届く。 どちらも既にあるものへ external として繋ぐ。

ポートはホストに晒さない。expose だけを書き、 nginx-proxy からのみ到達できるようにする。

常駐も定期実行も無い

cron の枠も、常駐プロセスの置き場も、この構成には無い。 巡回はアプリと同じプロセスで回している （src/instrumentation.ts）。

app を二つに増やせない

巡回は行を掴むときに FOR UPDATE SKIP LOCKED を使うが、 ロックは掴む取引の終わりで放される。送るのはそのあとである。

したがって app を二つ動かすと、同じ通知が二通届きうる。 増やすときは、掴んだ印を行に持たせるところから直す必要がある。

期限が近い課題の通知も、同じ壁の前で止まっている （通知の拡張）。

VPS に置くもの

/path/to/tasktasktask-work/
├── compose.yaml          deploy/compose.yaml を写す
├── .env                  deploy/.env.example をもとに手で作る
└── data/attachments/     空のディレクトリ

これだけである。ソースコードも schema/ も置かない。

ディレクトリの持ち主

コンテナは node（uid 1000）で動く。 data/attachments がそのユーザーで書けなければ、 添付のアップロードだけが失敗する。 画面は動くので、試すまで気づけない。

イメージ

アプリの実行とマイグレーションの適用を、ひとつのイメージが兼ねる。 実行時のイメージに Atlas と migrations/ を持ち込んである。

入っているもの用途
.next/standaloneアプリ本体。必要な依存だけが同梱される
atlasマイグレーションの適用
migrations/ db/functions.sql適用する中身
scripts/apply-functions.mjs関数とトリガの適用

pg と @node-rs/argon2 は Next の standalone 出力に取り込まれるので、 マイグレーション側からもそのまま使える。

HOSTNAME を明示する

Next の standalone 出力は、待ち受ける先をこう決める。

const hostname = process.env.HOSTNAME || '0.0.0.0'

一見 0.0.0.0 に落ちるように見えるが、 Docker はコンテナに HOSTNAME を必ず設定する。 右側には落ちず、そのホスト名に bind する。 nginx-proxy から届かない構成になりうるので、 Dockerfile で ENV HOSTNAME=0.0.0.0 を明示する。

リクエストから絶対URLを組まない

上の HOSTNAME は、待ち受け先を決めるだけでは終わらない。 NextRequest の nextUrl にもそのまま出る。 Host ヘッダは見ない。

$ curl -D - http://127.0.0.1:3000/auth/magic -H "Host: tasktasktask.work"
location: http://0.0.0.0:3000/?magic=invalid

$ curl -D - ... -H "X-Forwarded-Proto: https" -H "X-Forwarded-Host: tasktasktask.work"
location: https://0.0.0.0:3000/?magic=invalid

プロトコルは X-Forwarded-Proto が効くのに、ホストは効かない。 リダイレクト先をここから組むと、ブラウザが 0.0.0.0 へ飛ばされ、 ERR_CONNECTION_REFUSED になる（2026-09-08 に本番で踏んだ）。

行き先は相対で返す。 相対の Location は RFC 7231 が認めており、 ブラウザはいま見ているオリジンに対して解決する。 NextResponse.redirect() は絶対URLしか受け取らないので、 Response を直に組む。

return new Response(null, { status: 307, headers: { Location: '/' } });

メールに載せるリンクだけは相対に書けないので、そちらは APP_ORIGIN から組む。組み立てが二通りあるのは、 リクエストがある側と無い側で、正しい答えが違うためである。

作って送る

GitHub Actions の Deploy ワークフローを手で起こす。 イメージを作り、レジストリへ push するところまでを行う。

secret内容
DOCKER_REGISTRY_HOSTレジストリのホスト
DOCKER_REGISTRY_USERNAMEログインに使う名前
DOCKER_REGISTRY_PASSWORDログインに使うパスワード

押した回数だけ動く形にしてある（workflow_dispatch）。 VPS への反映まではやらない。 マイグレーションを流す順序を人が見て決める必要があるためである。

手元から送ることもできる。

docker build -t "$REGISTRY/tasktasktask.work:latest" .
docker push "$REGISTRY/tasktasktask.work:latest"
アーキテクチャは揃っている

GitHub の runner も VPS も x86_64 である。 揃っていなければ Exec format error で起動に失敗するので、 片方を変えるときは確かめること。

この開発環境（devcontainer）は aarch64 なので、 手元で作ったイメージは VPS では動かない。 手元のビルドは Dockerfile の確認までにとどめ、送るものは CI が作る。

入れ替える

ssh VPS
cd /path/to/tasktasktask-work

docker compose pull
docker compose run --rm migrate        # ← アプリを入れ替える前
docker compose up -d
順序を守る

マイグレーションを up -d のあとに流すと、 新しいコードが古いスキーマの上で動く瞬間ができる。

この順序が守れることが、段階的な変更の手順の前提になっている。 足す、両方書く、埋める、読み替える、消す。 どの段階も「先にスキーマ、あとからコード」で成り立っている。

migrate は別のサービスにする

常駐向けの再起動方針を、一時的な処理に引き継がせない

app には restart: unless-stopped が付いている。 落ちても起き上がってほしいからである。

この方針は終了コードに関わらず起動し直す。 一時的な処理に付くと、終わるたびに走り直して止まらなくなる。 migrate は Atlas と Node を毎回立ち上げてデータベースを叩くので、 回り続ければ CPU を食い尽くす。

そのため migrate を別のサービスとして定義し、 restart: "no" を明示してある。 profiles を付けているので up -d では起動しない。

データベースに届けばよいので、 添付の置き場も nginxproxy-network も持たせていない。

docker exec ではなく run を使う

docker exec でも同じ処理は流せるが、 アプリが動いていることが前提になる。 つまり up -d を先に済ませることになり、 新しいコードが古いスキーマの上で動く時間ができる。

run なら使い捨てのコンテナで完結するので、 アプリを入れ替える前に流せる。 段階的な変更の手順は、この順序で成り立っている。

起動時に自動で流さない

migrate は使い捨てのコンテナとして明示的に呼ぶ。 アプリの起動処理に混ぜない。 コンテナが複数立ち上がったときに同時に流れて衝突する。

作業用データベースを本番に向けない

Atlas は作業用データベースの中身を作り直す

ATLAS_DEV_URL が本番を指したまま実行すると、そこにあるデータが消える。

コンテナの中で走る migrate は atlas.hcl を経由せず、 --url "$DATABASE_URL" を直に渡している。 apply に作業用データベースは要らないので、渡す口ごと無くしてある。

手元の pnpm schema:* にも、二つが同じ値なら止まる検査を入れた。

Cloudflare と VPS のあいだ

SSL は Cloudflare が終端し、そこから VPS へは平文で届く。

この構成が抱えるもの

VPS の IP へ直接届く経路があれば、そこを通る内容は読める。 セッションの Cookie も、マジックリンクのURLも含まれる。 加えて X-Forwarded-For を偽装できるので、 sessions.created_ip の値は本物とは限らなくなる。

塞ぐには、VPS のファイアウォールで 80 番を Cloudflare の IP 範囲だけに限る。 ただし VPS では他のサービスも動いており、制限はそのすべてに及ぶ。 Cloudflare を通していないホスト名や、IP で直接叩いている経路が先に壊れる。

そのため、何が壊れるかの調査を含む手順として オリジンまでの経路に切り出した。 まだ適用していない。

アップロードの上限

開発では通り、本番でだけ落ちる

nginx の client_max_body_size は既定 1MB である。 添付は一度の送信で合計30MBまで許しているので、 そのままだと本番でだけ 413 で落ちる。

nginx-proxy はコンテナ側の CLIENT_MAX_BODY_SIZE を読んで そのバーチャルホストの設定に反映するので、compose.yaml で 34m を指定してある。 30MB そのものではないのは、多部分形式の包みぶんを見込んでいるためである。

上限は三箇所にある。ここと、 next.config.ts の bodySizeLimit（32mb）と、 機能の側の定数（30MB）である。 外側ほど大きくしてある。逆にすると、内側が断る前に外側が切ることになり、 利用者には理由の分からない失敗として届く。

開発コンテナの逆プロキシ

本番の振り分けは nginx-proxy が VIRTUAL_HOST を見て行うが、 開発コンテナは自前の nginx を持っている （.devcontainer/reverse-proxy/etc/nginx/nginx.conf）。 app.tasktasktask.work.localhost への要求を app:3000 へ渡す、 server ブロック一つぶんの設定である。

proxy_pass の宛先に変数を使うと 502 になる

宛先を set $upstream_app app:3000; で変数に入れ、 proxy_pass http://$upstream_app; と書くと、 nginx は名前解決を起動時ではなく要求ごとに回す。 そのとき参照するのが resolver ディレクティブで、この設定には置いていない。 引く先を持たないまま要求時に解決しようとして、502 になる。

宛先を proxy_pass http://app:3000; と直に書けば、起動時に一度引いて済む。

引き換えに入るものがある。起動時に引いた住所を持ち続けるので、 app のコンテナだけを作り直して IP が変わると、 nginx は古い住所へ送り続ける。逆プロキシごと起こし直せば直る。 どうしても変数で書く必要が出たときは、 resolver 127.0.0.11 valid=10s;（Docker の内蔵DNS）を添える。

同じファイルには proxy_http_version 1.1; も置いてある。 nginx は既定で上流に HTTP/1.0 で話し、 Next.js の動的ページは Transfer-Encoding: chunked で返る。 1.0 のままだと本文の終わりが分からず、接続が閉じるまで待つことになる。

Stripe を繋ぐ

課金を動かすのは BILLING_MODE=stripe のときだけである。 off にしてある間は判定そのものを行わず、すべての組織が書き込める。 切り替えるのは環境変数ひとつで、課金に詳しい。

変数中身
BILLING_MODEoff / fake / stripe
STRIPE_SECRET_KEYダッシュボードの「開発者 > API キー」
STRIPE_WEBHOOK_SECRETWebhook の署名の秘密

Webhook の送り先は https://tasktasktask.work/api/stripe/webhook である。 購読するのは invoice.paid と invoice.payment_failed の二つだけでよい。 署名を確かめる前には何も読まないし、何も書かない。

Managed Payments に弾かれる

アカウントで Managed Payments が既定で有効になっていると、 支払い方法を預かる画面が作れない。 mode: 'setup' は受け付けず、payment か subscription にしろと返る。

この実装はどちらにも寄せられない。登録の時点で課金しないので payment ではなく、 サブスクリプションも使っていない。預かるのはカードだけである。

リクエストごとに切ってある（managed_payments: { enabled: false }）ので、 ダッシュボードの設定を変える必要は無い。 アカウント側でも既定を切れるが、そちらに頼っていない。 設定が戻された日に、支払いの入口だけが黙って壊れるためである。

他の API でも同じ理由で弾かれたときは、まずリクエストの側で切れないかを見る。

自動再試行は、探して切らなくてよい

一度の失敗で凍結すると決めてあるので、数日後に再試行が通ると、 入金は済んでいるのに凍結だけが残る。これは避けたい。

ただし、その心配はコードの側ですでに閉じている。 請求書を auto_advance: false で作り、決済は invoices.pay() で 一度だけ呼ぶので、Stripe が次の試行を予約する経路に入らない。 ダッシュボードの Smart Retries はサブスクリプション向けの設定で、 この実装はサブスクリプションを使っていない。

確かめたいときは、テストカード 4000 0000 0000 0341 で一度失敗させ、 その請求書の「次回の支払い試行日」が空欄であることを見る。 日付が入っていたら、そのときに設定を探せばよい。

Stripe Tax は使わない。 適格請求書発行事業者の登録をしていないので、税を別記した請求書を出さない。 単価そのものが税込である。

決済は USD で行う。金額はセントの整数で渡す（100 が $1.00）。 請求先の住所は税の計算には要らないが、請求書の宛先として集めている。

請求の確定は app の中で 5 分ごとに回る巡回が行う。 cron も常駐プロセスも要らない代わりに、 app を二つに増やすと、同じ月を二つの巡回が掴みうる。 通知メールに続いて、増やせない理由がもう一つ増えたことになる。
