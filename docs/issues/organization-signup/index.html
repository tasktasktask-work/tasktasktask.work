宿題答え
slug の取り合い 早い者勝ち。予約語はアプリケーション側の一覧で断る。作成後の変更は用意しない
捨てアドレスの扱い アドレスの確認を先に済ませる。組織の行は確認のリンクを踏んだ先で生まれる

先送りの理由だった課金とプランは、まだ決まっていない。 それでも入口を開けたのは、費用の持ち主を組織に紐づける形（組織単位の契約）を想定しており、 入口を先に開けても、後から紐づける先が消えないためである。

概要（先送りしていた当時の記録）

組織に人が増える経路は招待だけで、 招待を送れるのは組織管理者だけである。 すると最初の組織管理者を作る手段が、画面のどこにも無い。

いまは手元の実行で作っている。

pnpm org:create --name "株式会社アクメ" --slug acme \
                --admin someone@example.com --admin-name "佐藤 明日香"

組織と、組織管理者としての所属と、ログイン用リンクを作って出力する。 出力されたリンクは、こちらから本人へ渡す。

先送りとした理由

誰でも組織を作れる状態にすると、その組織の費用を誰が持つのかという問いが立つ。 課金とプランが決まる前に入口だけ開けると、 作られた組織の扱いを後から決めることになる。

いまの利用者数では、手元の実行で足りている。 この手順が回らなくなる規模になったときが、作るときである。

再検討のきっかけ

  • 問い合わせから組織を作る回数が、週に何度も発生するようになったとき
  • 料金の形が決まり、支払いの主体を組織に紐づけられるようになったとき

実装するとしたら（当時の見通し）

登録した人がその場で組織管理者になる。 pnpm org:create がやっていることと同じで、 違うのは実行する人だけである。

決めることが二つ残る。

  • slug の取り合い 早い者勝ちにするか、予約語を置くか。 admin や login のような語が取られると、後から URL を分けにくくなる
  • 捨てアドレスの扱い 誰でも作れる状態は、誰でも作り捨てられる状態でもある。 アドレスの確認を挟んでから組織を作る形にする
