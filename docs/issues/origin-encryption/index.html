オリジンまでの経路

概要

SSL は Cloudflare が終端する。そこから VPS へは平文で届く。

クライアント ═══SSL═══> Cloudflare ───平文───> VPS:80

VPS の IP へ直接届く経路があれば、そこを流れる内容は読める。

  • セッションの Cookie（そのままログインした状態を再現できる）
  • マジックリンクのURL（48時間、一度きり有効）
  • スレッドの本文とコメント（非公開プロジェクトのものを含む）

加えて X-Forwarded-For を偽装できる。 sessions.created_ip の値は本物とは限らなくなる。

この記述は公開されている

リポジトリを公開しているため、このページも誰でも読める。 弱点を隠しても安全にはならないので記述は残すが、 塞ぐまでのあいだ、住所つきで公開されている状態である。 これが優先度を高くしている理由でもある。

なぜまだ塞いでいないか

VPS では他のサービスも動いている。 80番と443番への到達を制限すると、そのすべてが影響を受ける。

特に次の二つが壊れうる。

  • Cloudflare を通していないホスト名。 DNS の設定が「DNS only」（灰色の雲）のものは VPS の IP へ直接解決される。 制限をかけると、そのホスト名は届かなくなる
  • IP で直接叩いている経路。 監視、バックアップ、社内からの疎通確認など

作業そのものは数分で終わるが、何が壊れるかを先に洗い出す必要がある。 その調査を伴うため、機能の実装とは別の枠として切り出した。

手順

1. 壊れるものを洗い出す

Cloudflare の DNS 設定で、このゾーンのレコードを見る。 プロキシされていない（灰色の雲）A / AAAA レコードが、そのまま影響を受ける。

# VPS で、いま 80 / 443 に来ている接続元を見る
ss -tn state established '( sport = :80 or sport = :443 )' | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn

# nginx のアクセスログから、Cloudflare 以外の接続元を数える
# （X-Forwarded-For ではなく、接続元そのものを見ること）
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

ここに出た接続元のうち、Cloudflare の範囲に入らないものが、制限で切れる相手である。

2. Cloudflare の IP 範囲を取る

公開されている。IPv4 が15件、IPv6 が7件（2026年9月時点）。

curl -s https://www.cloudflare.com/ips-v4 -o /etc/cloudflare/ips-v4
curl -s https://www.cloudflare.com/ips-v6 -o /etc/cloudflare/ips-v6

変更を検知したい場合は https://api.cloudflare.com/client/v4/ips が etag を返すので、前回の値と比べる。

3. 戻す手立てを先に用意する

締め出されないように

ファイアウォールの作業で最も多い事故は、自分が入れなくなることである。 規則を入れる前に、時間で元に戻す仕掛けを置く。

# いまの設定を控える
nft list ruleset > /root/nftables.before

# 20分後に必ず元へ戻す。うまくいったら at のジョブを消す
echo "nft -f /root/nftables.before" | at now + 20 minutes
atq   # 登録されたことを確認する

SSH（22番）は制限の対象に入れない。 作業中に別の端末からもう一本 SSH を繋いでおくと、なお安全である。

4. 規則を入れる

# nftables の例。80 と 443 を Cloudflare の範囲だけに限る
nft add set inet filter cf4 '{ type ipv4_addr; flags interval; }'
nft add element inet filter cf4 "{ $(paste -sd, /etc/cloudflare/ips-v4) }"

nft add set inet filter cf6 '{ type ipv6_addr; flags interval; }'
nft add element inet filter cf6 "{ $(paste -sd, /etc/cloudflare/ips-v6) }"

nft add rule inet filter input tcp dport { 80, 443 } ip  saddr @cf4 accept
nft add rule inet filter input tcp dport { 80, 443 } ip6 saddr @cf6 accept
nft add rule inet filter input tcp dport { 80, 443 } drop

ufw を使っているなら、同じことを次のように書く。

for ip in $(cat /etc/cloudflare/ips-v4 /etc/cloudflare/ips-v6); do
  ufw allow proto tcp from "$ip" to any port 80,443 comment 'cloudflare'
done
ufw deny 80/tcp
ufw deny 443/tcp

5. 確かめる

# 外から。IP で直接叩いて、届かなくなっていること
curl -sI --connect-timeout 5 http://<VPS の IP>/ | head -1   # 応答が無ければ成功

# ホスト名では、これまでどおり届くこと
curl -sI https://tasktasktask.work/ | head -1

# 1 で洗い出した、Cloudflare を通していない経路も忘れずに確認する

問題がなければ atrm で戻しの予約を消し、規則を永続化する。

6. 範囲の更新を仕込む

Cloudflare の IP 範囲は変わる。 更新が反映されないと、ある日から一部の利用者だけ届かなくなる。

# 週次で取り直し、変わっていれば集合を入れ替える
# 変更があった日を記録しておくと、障害の切り分けが早い

これで直ること、直らないこと

項目結果
平文を読まれる経路Cloudflare と VPS のあいだだけになる
X-Forwarded-For の偽装できなくなる
Cloudflare と VPS のあいだの暗号化直らない

三行目まで求めるなら、Cloudflare の設定を Full (strict) にし、 nginx-proxy に証明書を置く。 Cloudflare Origin CA の証明書は無料で15年有効なので、 acme-companion を足さずに済む。 ただしこれも nginx-proxy を共有する他のサービスに影響するため、同じ調査が要る。

もうひとつの道

Cloudflare Tunnel を使うと、VPS に入ってくるポートそのものを開けずに済む。 ただし他のサービスの経路も付け替えることになるので、この構成では変更の幅が大きい。

再検討のきっかけ

  • 手順 1 の調査が終わり、壊れるものが無いと分かったとき（そのまま 3 へ進める）
  • VPS の IP が外から直接叩ける状態だと確認できたとき
  • アクセス元のIPを記録として使う機能を作るとき（いまは sessions に持つだけで使っていない）
