スレッドの可変性

概要

スレッドについて、三つのことができない。

  1. プロジェクト間の移動。置き場所を間違えたら立て直すしかない
  2. 種別の変換。議論を課題に作り変えられない
  3. 編集履歴。本文は編集できるが、以前の内容は残らない

先送りとした理由

移動

移動を認めると、子孫の一括移動が発生する。 親子関係はプロジェクトをまたげないので、 親を移すと子も全部ついていく必要がある。

また、スレッド識別子の見た目が変わる。 番号は組織で通しているので同一性は保たれるが、 WEB-7 が BILL-7 になると、過去の記録との照合ができなくなる。

種別の変換

課題から議論への変換では、期間と進捗率を捨てることになる。 議論から課題への変換は情報が増えるだけなので成立するが、 片方向だけ許すと利用者が混乱する。

代わりに、議論を親、課題を子にするという手段を用意した。 「この課題はどの議論から出てきたのか」を辿る経路は確保されている。

編集履歴

履歴を残すと、差分の表示UIが必要になる。 そしてコメントを不変にした設計との重みのバランスが崩れる。 コメントは記録として一切変えられないのに、本文だけ細かく追跡するのは一貫しない。

残っている歪み

本文が黙って書き換わると、それを前提に書かれたコメントが宙に浮く。 「編集済み」の印は付くが、何がどう変わったかはわからない。

コメント欄で合意した内容が、後から本文の書き換えで実質的に覆されても、 それを検出する手段がない。

再検討のきっかけ

  • プロジェクトの切り方を変えたいという要望が出たとき（1）
  • 議論と課題の親子付けを忘れる事例が繰り返されたとき（2 の代替手段が機能していない合図）
  • 本文の書き換えをめぐる認識の食い違いが起きたとき（3）

実装するとしたら

1 は、識別子の表示規則を先に決める必要がある。 移動後も元のキーで表示し続けるか、新しいキーに変えるか。 元のキーを残すなら、threads にキーの列を持たせることになり、 プロジェクトとの正規化が崩れる。

3 は thread_revisions テーブルを作り、編集のたびに旧内容を書き込む。 監査ログと一緒に設計するのが素直である。
