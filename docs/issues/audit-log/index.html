監査ログ

概要

誰がいつ何をしたかを追う仕組みがない。 各テーブルは created_at と updated_at を持つが、 誰が更新したかは記録していない。

特に追えないものを挙げる。

  • スレッドの本文を誰が書き換えたか（編集履歴と重なる）
  • 論理削除を誰が実行したか
  • プロジェクトの公開設定を誰が切り替えたか
  • アカウントロックがどこからの試行で起きたか
  • 非公開プロジェクトのメンバーを誰が追加したか

先送りとした理由

記録する対象を決めるのが難しい。 すべての更新を残すと行が膨大になり、 絞ると「必要になったときに記録されていない」という事態が起きる。

そして記録しただけでは役に立たず、検索と絞り込みの画面が要る。 全文検索すら持たない段階では、 ログを見る手段のほうが先に問題になる。

今すぐ困る場面

アカウントロックの原因が調べられない。 第三者による意図的な締め出しなのか、本人の入力ミスなのかを区別できない。 ロックが繰り返される利用者がいても、対処の判断材料がない。

再検討のきっかけ

  • 「誰がこれを消したのか」という問い合わせが発生したとき
  • 非公開プロジェクトの情報が意図せず広まったとき
  • 顧客のセキュリティ要件として求められたとき

実装するとしたら

汎用のイベントテーブルを一つ置く。

CREATE TABLE audit_events (
  id              bigserial PRIMARY KEY,
  organization_id uuid NOT NULL,
  actor_user_id   uuid,
  action          text NOT NULL,        -- 'thread.archive' など
  target_type     text NOT NULL,
  target_id       uuid,
  detail          jsonb NOT NULL DEFAULT '{}',
  ip              inet,
  created_at      timestamptz NOT NULL DEFAULT now()
);

detail を jsonb にすると、対象ごとに違う情報を同じテーブルに入れられる。 ただしスキーマが緩い分、書き込む側の規律が要る。 どの操作でどのキーを入れるかを、実装前に一覧として決めておく。
