Issue · 優先度 低

行の無いファイル

概要

データベースとファイルシステムは同じ取引に入らない。 添付ファイルを保存するとき、 必ずどちらかが先になる。

いまは行を先に入れ、次に実体を書き、最後にコミットしている。 途中で落ちれば、この呼び出しで書いたぶんの実体を消してから投げ直す。 それでも「実体は書けたが、コミットで落ちた」窓だけは閉じられない。

そこに残るのは、どの行からも指されていないファイルである。 誰にも見えず、消す手立ても画面には無く、容量だけを食い続ける。

先送りとした理由

先に閉じるべき窓ではないと判断した。

まず、起きる条件が狭い。 実体の書き込みが終わってからコミットが返るまでのあいだに、 プロセスかデータベースへの接続が落ちる必要がある。

次に、被害が容量だけである。 誰にも見えないので、情報が漏れることも、画面が壊れることもない。 添付の合計は 行を数えるので、この分は数字にも出ない。 つまり気づくのはディスクが埋まってからになる。ここだけが痛い。

逆順にする手もある。実体を先に書き、行が入らなければ消す。 こちらは「行を入れる側が落ちた」ときに消す処理まで届かないので、 窓はむしろ広がる。順序を変えても消えない性質の問題である。

再検討のきっかけ

  • ディスクの使用量と、attachments の合計が目に見えて食い違ったとき
  • アプリの異常終了が日常的に起きるようになったとき
  • 保存先をオブジェクトストレージへ移すとき（同じ問題が別の形で出る）

実装するとしたら

置き場を走査し、attachments のどの行からも指されていないキーを探す。 見つけたものをすぐ消さず、一定の時間を置いてから消す。 いま書いている最中のファイルを、掃除が追い越して消してしまうためである。

-- 置き場にあるキーの一覧を作ってから
SELECT storage_key FROM attachments;
-- 差集合のうち、更新から24時間が経ったものだけを消す

走らせる間隔は、日に一度で足りる。 巡回のような分単位の仕掛けは要らない。

複数のインスタンスで動かすときは、掃除が二重に走らないようにする必要がある。 これは通知の拡張で 期限通知に必要になる仕掛けと同じものである。
