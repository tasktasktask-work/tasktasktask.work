状態のカスタマイズ

概要

状態は進捗率という数値ひとつで固定されており、 組織ごとに状態の集合を定義することはできない。

「未着手 / 進行中 / レビュー中 / 検証待ち / 完了」のような工程を持つチームは、 それを進捗率の数値に読み替えて運用することになる。 80%がレビュー中を意味するかどうかは、人によって解釈が分かれる。

先送りとした理由

カスタム状態は、単独では成立しない。 状態を定義できるようにすると、次に「どの状態からどの状態へ遷移できるか」を決めたくなる。 ワークフローの定義、遷移の権限、遷移時の自動処理。ここまで来ると機能の規模が数倍になる。

そしてガントチャートのバーの塗り分けは、 進捗を連続値として扱うことを前提にしている。 状態を離散値にすると、塗り分けの根拠が失われる。

再検討のきっかけ

  • 複数の組織から同じ工程名（レビュー中など）の要望が出たとき
  • 進捗率の値に組織独自の意味を持たせた運用ルールが、社内文書として作られはじめたとき

実装するとしたら

進捗率を捨てるのではなく、状態と進捗率を併存させる案を第一候補とする。 状態は工程を表し、進捗率はガントの塗り分けに使う。 役割が違うので、両立できる。

CREATE TABLE thread_statuses (
  id              uuid PRIMARY KEY,
  organization_id uuid NOT NULL REFERENCES organizations(id),
  name            text NOT NULL,
  sort_order      smallint NOT NULL,
  is_terminal     boolean NOT NULL DEFAULT false
);
-- threads に status_id を足す

遷移の制限は、最初は設けない。 どの状態からどの状態へも移れる形にすれば、定義するのは名前と並び順だけで済む。
