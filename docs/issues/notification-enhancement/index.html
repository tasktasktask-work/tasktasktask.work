通知の拡張

概要

三つを先送りにした。

  1. ウォッチの自動付与。作成者、担当者、コメントした人を自動でウォッチ扱いにしない
  2. きっかけごとの通知設定。メール通知はユーザー単位のオンオフひとつだけ
  3. 期限が近い課題の通知。終了日が迫ったことを知らせる仕組みがない
  4. 通知の消去と保持期間。行は増え続ける。消す手立ても、古い行を畳む仕組みもない

先送りとした理由

ウォッチの自動付与

自動で付けると、関わっただけのスレッドの通知が延々と届く。 それを嫌ってメール通知を切る人が出ると、必要な通知まで届かなくなる。 申し込み制にすれば、届く通知はすべて自分で選んだものになる。

この判断が抱える穴

自分が立てたスレッドに返信が来ても、ウォッチしていなければ気づけない。 これを補うのはメンションだけである。

「返信するときは相手を @ で呼ぶ」という運用が前提になっているが、 これは仕組みではなく規律に頼っている。 忘れる人が一定数いれば、質問が放置される。

きっかけごとの設定

設定項目が増える割に、細かく設定する人は少ないと見込んだ。 ユーザー単位のオンオフひとつがあれば、迷惑メール報告による送信ドメインの劣化は防げる。

期限通知

日次で走るバッチが要る。 常駐プロセスの配置、失敗時の再実行、多重起動の防止。 デプロイ構成に新しい要素が加わるため、 アプリケーションだけで完結する機能を先に固めることにした。

壁の半分は、2026-09-08 に崩れた

通知メールの巡回ができ、 定期的に何かを走らせる場所そのものは手に入った。

残っているのは、日をまたいで一度だけ送る仕掛けである。 通知メールは行が積まれたことをきっかけにするが、期限は誰も行を積まない。 毎分の巡回から「今日はもう送ったか」を判断する必要があり、 notifications だけでは足りない。

多重起動の防止も残る。 いま巡回が一つで済んでいるのは、app が一つだからである。

通知の消去と保持期間

一覧は未読を全部と既読を直近20件しか出さないので、行が増えても画面は伸びない。 伸びるのはテーブルだけである。

読まれない行を持ち続ける費用より、消す判断を誤る危険のほうが大きいと見た。 「半年前に指名された」という事実を、こちらの都合で消してよい根拠がない。

再検討のきっかけ

  • 「質問したのに誰も答えてくれない」という声が出たとき（1 の穴が顕在化した合図）
  • メール通知をオフにしている人の割合が高いとき（2 が必要な合図）。 2026-09-08 にメールが飛ぶようになり、/me で切れるようになったので、 この割合はもう数えられる
  • 期限切れの課題が放置される事例が繰り返されたとき（3 が必要な合図）

実装するとしたら

1 は watches に行を作るきっかけを増やすだけで、スキーマの変更は要らない。 ただし既存のスレッドに遡って付けるかどうかという判断が要る。 遡ると、大量の人が突然通知を受け取りはじめる。

2 は users にフラグを足すか、設定用のテーブルを作る。 きっかけが三つしかないので、三つの boolean で足りる。 いまある一つのスイッチを、三つに割ることになる。

3 は送信済みを記録する仕組みが要る。 走らせる場所は巡回がある。 同じ課題について毎日通知が飛ばないよう、 notifications の kind に due_soon を足したうえで重複を避ける。
