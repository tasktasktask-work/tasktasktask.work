本文の書式

対応済み

コメントを作ったときに一緒に入れた。 本文もコメントも Markdown で描画する。 見出し、強調、箇条書き、リンク、コードブロック、引用、表、チェックボックスまで通る。

下に残してあるのは、当時どう考えていたかである。 実際に選んだ道は、そのとき書いた「実装するとしたら」とは違っている。

何を選んだか

streamdown を入れた。 解釈も無害化も、こちらでは書いていない。

先送りしたときの見立てでは、解釈するライブラリと無害化するライブラリを別々に選び、 その噛み合わせ方を自分たちで決めることになるはずだった。 そこが一つにまとまっていたので、選ぶ対象が三つから一つに減った。

生の HTML は、受け付けない方針を撤回して通すことにした。 禁じた理由が「無害化のコストが表現力に見合わない」ことだったので、 そのコストを引き受ける相手ができた時点で、理由のほうが先に消えた。

残っている弱点

無害化の正しさを、外部のライブラリが握っている。 自前で書けば「HTML の文字列を一度も作らない」形にでき、 無害化の失敗という状態そのものを消せた。そちらは選んでいない。

<script> が消えること、onerror 付きの画像が差し止められること、 javascript: のリンクが無効になることは、実際に投げて確かめてある。 確かめたのはその三つであって、無害化の全体ではない。

先送りしていたときの記録

以下は 2026-09-05 に書いたものである。

概要

スレッドの本文は、いま改行を保つだけで表示している。 見本の画面には箇条書きと インラインコードとリンクが出ているが、そこまでは動いていない。

いま出るものまだ出ないもの
改行、空行見出し、箇条書き、コードブロック、リンク、強調

先送りとした理由

Markdown を解釈すると、文字列が HTML になる。 そこから先は、書いた人が入れた <script> が他人のブラウザで動かない、という保証を こちらが持たなければならない。解釈するライブラリと、無害化するライブラリと、 その二つの噛み合わせ方の三つを選ぶ話になる。

そして同じ仕組みをコメントでも使う。 コメントにはメンションがあり、 @佐藤 明日香 という書き方を本文の解釈と噛み合わせる必要がある。 先にスレッドだけで組むと、コメントを作るときに作り直すことになる。

本文が素のテキストのままでも、スレッドは使える。 読めない本文にはならない。改行が残れば、箇条書きは - のまま読める。

この判断の弱点

見本の画面と、実際の画面が食い違ったままになる。 設計ドキュメントを読んで「書式が使える」と受け取った人が、 書いてみて初めて出ないことに気づく。

食い違いは、見本の側ではなく機能ドキュメントの断り書きで示している。 見本を素のテキストに描き直すと、これから作るものの姿が消えるためである。

再検討のきっかけ

  • コメントを実装するとき。そのときに一緒に入れる
  • 本文に手順や表を書く使われ方が出てきたとき

実装するとしたら

解釈と無害化を分け、無害化を最後に通す。 解釈するライブラリが安全な出力を約束していても、それに寄りかからない。

受け付ける記法は絞る。 見出し、箇条書き、コードブロック、インラインコード、強調、リンク、引用。 生の HTML は通さない。表を入れるかどうかは、使われ方を見てから決める。

リンクは http と https だけに限る。 javascript: が通ると、無害化を一段抜けられる。
