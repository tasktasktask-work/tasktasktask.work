却下の表現

概要

状態を進捗率ひとつで表す設計にしたため、 「やらないと決めた課題」を表す手段がない。

実際の状況進捗率
まだ手をつけていない0
やらないと決めた0
途中まで進めたが中止した40
他チーム待ちで止まっている40

同じ理由で「レビュー中」「検証待ち」のような工程も表せない。 進捗率の80%がレビュー中を意味するかどうかは、人によって違う。

先送りとした理由

終了理由の軸（open と closed、閉じた理由）を別に持つ案を検討したが、採らなかった。 代わりに、扱いを各組織の運用に委ねる方針とした。

取りうる手段は三つある。

  • アーカイブする。進捗率は途中のままでよく、一覧からも消える
  • 進捗率を100にして完了として扱う
  • タグで 却下 や 保留 を付ける
この先送りが生む問題

却下の表し方が組織ごとにばらつく。 ある組織はアーカイブし、別の組織は進捗率100にする。 同じ組織の中でも人によって分かれうる。

そうなると、後から集計やレポート機能を作るときに、どのデータを完了として数えるかが決められなくなる。 「完了した課題の数」という単純な問いに答えられない。

再検討のきっかけ

  • 完了した課題を数える機能（実績の集計、消化率のグラフ）を作ることになったとき
  • 利用者から「却下と未着手が区別できない」という声が出たとき
  • アーカイブされたスレッドの中身を調べる必要が繰り返し生じたとき

実装するとしたら

threads に二列を足す。

closed_at     timestamptz,
closed_reason text CHECK (closed_reason IN ('done', 'rejected', 'duplicate'))

既存データの移行が問題になる。 進捗率100のものを done とみなすことはできるが、 アーカイブで却下を表していた組織のデータは、機械的には判別できない。 移行時に人が仕分ける作業が発生する。 先送りするほどこの作業が重くなる。
