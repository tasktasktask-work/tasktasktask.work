課金とプラン

2026-09-09 に対応した

この課題は課金を入れる回で解決した。 仕様は機能 / 課金にある。

下に残してあるのは、先送りにしたときの判断とその理由である。 このページで「早めに見ておく」とした課金の単位の一覧が、そのまま今回の決定の根拠になった。

概要

複数の組織が使うマルチテナントの構成だが、料金を受け取る仕組みがない。 プラン、上限、支払い、請求。どれも存在しない。

先送りとした理由

課金は、利用者がついてから作るもので、その逆ではない。 何をどう課金するかは、実際の使われ方を見なければ決められない。 人数あたりか、プロジェクト数か、保存容量か。

そして課金を入れると、機能の側にも制限の仕組みが必要になる。 「無料プランではプロジェクトは3つまで」といった判定が、 プロジェクト作成、メンバー招待、ファイルアップロードなど各所に入り込む。

先に決めておくべきこと

実装は先送りでよいが、何を課金の単位にしうるかは早めに見ておく。 後から数えられないものを課金単位にはできないためである。

候補今のスキーマで数えられるか
組織のメンバー数数えられる（organization_members）
プロジェクト数数えられる（projects）
スレッド数数えられる（threads）
添付ファイルの総容量数えられる（attachments.byte_size の合計）
月間の活動量数えられない（操作の記録がない）

最後の行が問題になりうる。 活動量に応じた課金を将来選ぶなら、監査ログが先に要る。

再検討のきっかけ

  • 社外の組織に提供することが決まったとき
  • インフラの費用が無視できない額になったとき

実際にどう決着したか

この表のうち、選んだのは一行目のメンバー数である。 税込 $1.00 を掛けた額を、後払いで毎月受け取る。 数えられない一行目以外の心配、つまり活動量に応じた課金は選ばなかったので、 監査ログは前提から外れた。

もうひとつの懸念だった「制限の判定が各所に入り込む」ほうは、プランを一つに絞ることで避けた。 機能ごとの上限を作らず、組織が凍結されているかどうかだけを見る。 判定を書く場所は currentScope() と、書き込みの SQL に足す条件の断片の二つで足りた。
