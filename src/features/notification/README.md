# 通知とウォッチ

三つのきっかけで飛ぶ。アプリ内とメールの両方へ。
ウォッチは自動では付かない。

仕様は [docs/features/notification/index.html](../../../docs/features/notification/index.html) にある。
先にそちらを読むこと。決めた理由まで書いてある。

## ここに置くもの

- 通知の作成（メンション、担当者設定、ウォッチ中のコメント） … `queries.ts`
- 既読の管理、ウォッチの付け外し … `queries.ts`
- 通知メールの文面 … `mail.ts`
- 未送信の行を拾って送る巡回 … `mailer.ts`

メール通知の入り切りは `#features/account/` にある。
`users` の列で、組織をまたいで効くためである。

## 行を作る関数は、取引のクライアントを受け取る

`notifyUsers` と `notifyWatchers` は `pg.PoolClient` を第一引数に取る。
呼ぶのはコメントの投稿とスレッドの担当者設定で、どちらも自分の取引の途中にある。
分けて後から積むと、コメントは残ったのに通知だけ飛ばなかった状態が起きる。

**宛先を絞る判定は、この二つの関数の中にしか無い。**
呼ぶ側で絞らない。増えたきっかけがこの関数を通れば、絞り込みは自動的に付いてくる。

## ウォッチは、権限より長生きする

`watches` の行は、そのプロジェクトが見えなくなっても残る。
公開だったものが非公開に変わる、メンバーから外される、組織から抜ける。三つの経路がある。

だから宛先は書くときに絞り、一覧に出すときにもう一度絞る。
書く側は行を積ませないため、読む側は最後の砦。
メールは積まれた行から文面を作るので、書く側を抜かすとそこが漏れ口になる。

## 送るのは巡回で、リクエストの中ではない

コメントを書いた人のリクエストの中で SMTP の応答を待つと、
相手が詰まったときに投稿の押しボタンまで詰まる。
行だけを先に積み、60秒ごとの巡回が拾う。

`deliverPendingNotifications()` が一巡ぶんである。
`startNotificationMailLoop()` は間隔を計るだけの殻で、判断を持たない。
持たせると、確かめるのに一分待つ仕掛けになる。

**送らないと決めた行にも、決着を付ける。**
付けないと毎分の巡回に拾われ続け、拾う順は古い順なので、
居座った行が枠を先に取り、後ろに並んだ人へ永久に届かない。

## 決まりごと

- データにさわる関数は、組織のスコープ（`OrgScope`）を第一引数に取る
  （`notifyUsers` などは取引のクライアントが先、スコープが第二引数）
- 閲覧できるプロジェクトの判定は `#lib/db.ts` の `visibleProjectIds` を使う。ここに書き写さない
- 通知を開く動線はリンクにしない。先読みで既読になる（[理由](../../../docs/glossary.html#read-state)）
- 外へ出るもの（`MailSender`、`APP_ORIGIN`）は引数で受け取り、既定値に本物を置く。
  テストは記録するだけの偽物を渡す
- 文面の組み立て（`mail.ts`）はデータベースを触らない。
  三件まとまったときの書き方を、下ごしらえ無しで確かめられるようにするため
- import には必ず拡張子を書く（[規約](../../../docs/devops/coding-conventions/index.html#imports)）
